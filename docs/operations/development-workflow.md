# 开发流程与交付记录入口

更新：2026-10-10。本文维护开发与修复规则；当前任务、应用版本和下一动作只维护[计划索引](../workflow/project-plan-index.md)，检查范围沿[验证策略](development-verification-policy.md)，稳定边界沿[AGENTS](../../AGENTS.md)。

应用名称采用[已确认的SemVer规则](application-versioning.md)：A是暂存的待发布版本，B是后续开发线；具体版本与分支见执行卡。只保留一个待发布基准和一条后续开发线，不建设长期多版本分支体系；A发布后按实际维护需要收尾临时分支，不自动删除。

## 按任务选择流程

| 任务 | 主流程与结束条件 |
| --- | --- |
| 状态查询 | 读执行卡及必要证据，说明来源与时点；不启动测试或服务 |
| 文档／计划整理 | 修改所属权威文件、核对差异/链接；交付文档，计划完成不等于实施启动 |
| 已授权功能／修复 | 沿下方一轮开发完成使用路径，必要检查按验证策略；同类低风险反馈集中处理 |
| 提供用户体验 | 先核实入口、实际账号获取、权限与数据前置，提供简短步骤；用户本人确认对应范围和版本 |
| A/B修复同步 | 按下方两线规则核对适用版本，保留未同步／未验证项，不建立平行待办 |
| 正式发布 | 按最终来源及原runbook执行适用门禁，满足发布条件后按具体授权整合/迁移/部署；普通交付不触发 |

Skill与Agent只在[使用指南](../workflow/skill-stack.md)中选择；本文件不复制第二套搭配或测试清单。

涉及导入/导出时，同时沿[导入导出数据约定](../workflow/import-export-data-contract.md)明确来源路径、必要字段、允许自动整理的范围、中文问题定位、导出用途/版本及再导入语义。该约定适用于后续所有相关功能；已正常运行的入口保持，实际改动只覆盖当前任务，不另建审批表或要求历史全面整改。

## 一轮开发

1. 核对实际来源和相关已有修改，只读当前任务及必要依赖。明确要交付的完整使用路径；同一使用路径的已授权低风险反馈合并实现，重大取舍或用户指定逐项复验除外。
2. 集中完成实现。用已有目标测试定位真实缺陷，只有未覆盖的关键行为才补回归；不为微小改动反复写计划、派发角色、审批或验证。
3. 先走通本次交付功能及适用异常状态，再执行必要的其他检查。必需构建、启动、安全前置和解除阻塞的检查可以先做；有效证据按相关变化复用。
4. 内联审查本轮差异。交付实际可用入口、必要前置、简短操作及预期结果；内部文档交付审阅文件，不制造业务体验界面。
5. 用户确认仅关闭明确范围和版本。反馈只修复和复验受影响路径，开发、体验、正式验收分别记录。完成当前可用结果后收尾；可继续不依赖待确认项且已获授权的独立工作。

## 页面交互修复与完整功能融合（2026-10-27）

适用于页面切换、操作向导、多入口整合及体验包更新。沿本轮原任务条目记录，无需新增审批表或测试平台。

1. **先核对运行版本，再定位可见故障。** 核对实际工作树、当前构建、启动脚本及浏览器加载的资源。页面空白或点击无反应时，先保留截图与当时网址，不先刷新或重新切页覆盖现场；再对照URL、选中状态、可访问内容、布局尺寸和实际点击结果。DOM有内容、API成功或刷新恢复均不能单独关闭问题。未确认根因时明确保留不确定性，不一概归因于旧缓存；同版本再次反馈即重开原问题，暂未复现和用户反馈“目前正常”只记当前恢复，不记根治或整批验收。
2. **展示、导航与表单分工。** 页面内容与页签使用稳定普通容器，原生fieldset只负责具体表单字段的禁用，避免将整张动态主从页和折叠区作为一个表单布局。响应式动态面板避免无必要的嵌套尺寸隔离；零布局问题须核对实际容器查询边界，不把更换fieldset当作通用根因。订单列表开合按订单／筛选上下文管理，页签、弹窗或刷新产生新历史项不能自动重置开合；刷新保留当前路径与业务上下文。加载／读取失败仍须封锁适用操作、保留输入与焦点恢复；保存中、结果未知、权限不足及未保存离开保护继续生效。局部优化沿已确认设计，不顺手更改共享导航或全局主题。
3. **默认入口先融合，原有能力不缩水。** 在同一任务内核对页面、详情、关联记录与历史草稿的入口，普通操作复用同一表单／向导及事实写入合同。多订单、混合来源、关联安排等确需不同字段的路径，复用共同步骤和校验，保留专用字段。官方输出、人工原表与标准模板仍按各自合同处理；保留的兼容／高级入口须有明确用途和可达入口，不能让用户无提示地回到缺少本轮功能的旧主流程。
4. **先在真实浏览器走完整路径。** 依本次影响验证默认入口、详情及关联入口、页签切换、折叠、前进后退、刷新，以及手工／导入、草稿续办、核对、确认和适用失败恢复。检查目标内容实际可见、可点击、URL与选中状态相符，必要时核对非零布局及截图。组件测试不覆盖浏览器排版，源码已改也不证明运行版本已更新。只在任务所有的虚构数据中做必要写入，保留用户已有草稿及真实数据。
5. **交付一个有明确身份的可用版本。** 固定构建完成后更新对应启动入口，保留旧包；仅重启确需更换且已核实归属的服务。在保存或明确放弃输入后载入新包，核对浏览器资源、关键页面与直接关联结果属于同一版本。既有打开标签未同步时明确提醒，不把所有标签统称为已更新。未解决的显示／功能问题继续登记；开发检查与用户确认、正式门禁及发布分别记录。

本轮验证范围与复用仍沿[验证策略](development-verification-policy.md#ui-visible-state)，不把上述要求外推为每次全仓回归、正式发布或重写全部历史入口。

## 候选准备

按[验证策略的冻结前检查](development-verification-policy.md#冻结前的低成本检查2026-09-28)先清除已知的低成本阻塞，集中完成同类修复，再按授权形成候选并进入昂贵正式链。已有冻结候选不就地修改，正式runner、采样、跨SHA证据限制及首失败停止仍按原合同。

这项流程调整不代表本轮已运行检查、生成候选、通过验收或改变远端CI。不要借候选准备再建设一套测试平台。

## 待上线维护线与后续开发线

用户延后上线时，A 保留已经确认的发布范围与准确 SHA/tree，B 从该基准承接后续开发。实际分支与状态沿[当前执行卡](../workflow/project-plan-index.md)，这里只维护规则。两条分支不代表已经部署，也不要求先上线才能开展已授权且不依赖发布结果的工作；阶段、数据和运行环境前置继续适用。

1. 缺陷默认在 B 的短修复分支实现、核验，再将必要修复回移 A。A 只接影响本版本的修复；不整体合并 B 的新功能。A 独有、B 已重写或修复无法直接移植时，可先修 A，再判断 B 不受影响或按 B 的结构修复。
2. 在原问题和修复 PR 中写明原触发条件、受影响版本、来源修复提交、每个目标修复提交/关联 PR，以及实际验证。A/B 分别记“待同步”“待验证”“已修复并验证”或“不受影响及原因”；回移提交可用 `git cherry-pick -x` 保留来源。冲突须按目标版本解决，保留原修复关联。
3. 修复后先在每个适用版本复现路径上确认结果，再按验证策略做相关检查；已有有效结果复用。涉及关键业务行为且缺少覆盖时补定向回归；纯文案/静态改动不补形式化测试。CI 绿灯、无合并冲突和相同提交说明都不能独自证明另一版本已经修复。
4. 所有适用版本处理完才关闭原问题；B 的功能分支继续开发时及时吸收 B 主线修复。A 的必要修复产生新候选，保留旧 SHA/tree、历史 CI 和用户确认，不把原 A 的证据冒充修正版或 B 的验证。
5. 两条线的运行配置、数据库迁移和兼容性按实际影响分别处理；B 的迁移不作用于现有 A 本地副本或生产库。工作树仅在实际开发需要隔离时创建，不复制整套依赖或恢复备份来完成分支准备。

修复 PR 的简短记录示例（填写实际结果，不是新增审批表）：

```text
问题与触发条件：……
B：目标分支/修复提交｜验证结果；或不受影响及原因
A：目标分支/回移提交或 PR｜验证结果；或不受影响及原因
剩余：待同步/待验证的具体版本；全部处理完才关闭原问题
```

分支准备不自动授权 commit/push/merge、正式 Collect、迁移或上线。修复记录沿用原任务/PR，不设置独立PR模板或自动同步平台。

参考：[Microsoft 分支指南](https://learn.microsoft.com/en-us/azure/devops/repos/git/git-branching-guidance?view=azure-devops)、[GitLab Flow](https://about.gitlab.com/topics/version-control/what-are-gitlab-flow-best-practices/#fix-bugs-in-main-first-and-release-branches-second)、[CPython 回移](https://devguide.python.org/getting-started/git-boot-camp/#backporting-merged-changes)、[Kubernetes cherry-pick](https://github.com/kubernetes/community/blob/main/contributors/devel/sig-release/cherry-picks.md)。借鉴同步原则与关联记录，验证范围仍按本项目策略。

## 状态定义

| 状态 | 可以说明什么 |
| --- | --- |
| `development_complete` | 本次实现及所需开发检查完成，只覆盖记录的功能、来源与环境 |
| `ready_for_user_review` | 本次体验入口、权限、账号获取和所需数据已核实，未齐备处明确列出 |
| `user_verified` | 用户明确确认了指定范围和版本；开发批准、截图和自动操作不能代替 |
| `integration_status` | 有关联任务时单独说明真实接口、身份和上下游结果是否已核对，不以开发完成代替集成结果 |
| `release_validation` | 正式发布门禁进度，按适用run和候选来源记录；PR CI成功不等于正式验收 |
| `accepted` | 对应范围的正式条件及适用体验要求满足，不等于已经部署 |
| `deployed`／`UI_deployed` | 对应制品实际部署并有记录；后端切换不能推断新版UI也上线 |

状态更新只写当前执行卡的所属条目，日志和制品记录引用原文件。业务版本记录、应用SemVer、文档修订号、Stage/Phase及历史测试A/B批次各自标注对象；不能由其中一项完成推断其他项完成。

## 记录与交付

- 当前任务和追加反馈沿用[计划索引](../workflow/project-plan-index.md)中的已有条目；大块命令日志和运行证据引用其原文件。批次记录只写实际变化、验证范围/耗时、证据位置、未覆盖影响及体验状态，同项连续修订不生成重复待办。
- 日常交付围绕结果和实际验证简短说明。存在实质后续工作时给出推荐及依据；没有则明确收尾，不强制填写空的紧急程度、成本或审批表。
- 规则变化改其权威文件，状态变化改执行卡；不再把整段实时状态复制到AGENTS、Skill表与本文件。历史事实与失败证据保留，不倒改成通过。
