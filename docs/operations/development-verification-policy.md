# 开发快检与部署前完整验证

本策略落实用户的风险匹配测试要求，适用于后续任务。开发任务交付实现和定向验证；完整测试集中到部署准备阶段，在正式上线前完成。用户另行明确要求的专项验收按指定范围执行，不因普通功能完成、提交、合并准备或计划收尾而启动完整门禁。

## 历史耗时证据（Stage 2）

Stage 2 曾在候选 `ced3adb863d2f8036affa1358def9135dcdb8506` 的 attempt3 中，MySQL 8.0 scoped tests 耗时 1500.74 秒：2 failed、211 passed、40 errors。两个 catalog 部分迁移测试留下了不一致的 schema，后续错误为连锁污染。此前迁移 shard 耗时约 41 分钟（前序执行记录）。

修复后，`test_catalog_schema.py` 的 3 项定向 MySQL 8.0 测试耗时 87.29 秒并通过。46 项迁移/版本合同耗时 2.66 秒。新候选 `5d888d0c9d7cfa6d867df21715136c3074929c69` 的 ubuntu-full 为 91.43 秒，windows-smoke 为 29.46 秒。

这些数据表明，主要开发阻塞来自数据库重建、完整矩阵以及失败后重新开始整个验收；削减几秒钟的静态检查不是首要优化。87 秒与完整矩阵覆盖范围不同，不能解释为相同覆盖获得了等比例提速。

## 默认工作流

1. 实施前按影响范围选验证级别和最小命令。
2. 实现后先检查 diff，再运行目标节点/文件与必要静态检查。
3. 失败时只诊断首个有效失败，修复后重跑目标范围。隔离/清理问题要验证后续用例不会被污染。
4. 通过后标记开发完成，准备可用入口和简短步骤交给用户本人体验；体验状态单独记录，只有用户明确确认才标记通过。列出阶段验收尚未覆盖的内容，等待体验期间可以继续独立开发任务。
5. 功能和已知缺陷集中收敛后，记录部署前待验事项；进入部署准备或用户明确要求的专项验收时才冻结候选并执行约定门禁，不能自动阻塞独立开发。
6. 完整验收失败则记录首因及已通过的开发证据，返回定向修复；不自动再启动整轮。

普通定向验证预算约 3 分钟；数据库定向验证约 10 分钟。超过预算应缩小范围或解释高风险检查的必要性。不得仅因预算到时强杀迁移，也不得把未跑项目报为通过。

## 选什么检查

| 改动或情况 | 开发期最小充分验证 | 不自动执行 |
| --- | --- | --- |
| 文档、文案、纯样式 | 相关 diff、链接或语法检查；影响显示时按需快检 | 新建形式化测试、pytest、完整构建、E2E |
| 业务逻辑、API、UI 交互 | 已有目标节点或文件；只在缺陷或关键规则缺少覆盖时补测试 | 无关模块测试、每一步红绿循环、完整浏览器回归 |
| 数据库、权限、并发、公共接口 | 目标测试及必要的受影响集成验证；数据库只用任务专用可抛弃容器 | 双版本矩阵、性能、恢复及部署演练 |
| 用户反馈缺陷 | 保留能识别原问题的复现，修复后验证同一问题及直接影响 | 两套排错流程从头执行、失败后完整 Collect |
| 相关代码、依赖、配置和环境未变 | 引用已有开发证据并注明版本与范围 | 为完成声明、换一条消息或提交而再次运行 |

每条命令要对应具体风险。纯文档任务不要求启动服务；页面入口检查也不等于完整 E2E。完整测试的范围和来源约束仍按发布合同执行，改变执行时点不等于减少覆盖。

## 可直接采用的最小命令

从目标工作树运行，Python 优先使用现有 `D:\CLSEN_Data_Web\.venv\Scripts\python.exe`。

```powershell
# 单文件示例；实际任务优先选择文件内受影响节点
./scripts/run-dev-check.ps1 -Kind Backend -Targets backend/tests/unit/worker/test_runner.py

# 只检查修改文件
D:\CLSEN_Data_Web\.venv\Scripts\python.exe -m ruff check --config backend/pyproject.toml backend/app/worker/runner.py

# 从工作树根目录运行已有受影响组件测试
./scripts/run-dev-check.ps1 -Kind Frontend -Targets frontend/src/features/admin/AdminConsole.test.tsx
```

需要临时文件时，为本轮创建唯一的 D 盘目录并传入 `--basetemp`；不要复用包含其他运行数据的目录，因为 pytest 会清空显式 basetemp。`-x` 用于开发定向检查，不擅自注入已冻结的正式验收命令。

`test-mysql-matrix.ps1 -DevelopmentTests` 已支持套件内显式文件/节点，默认一个 MySQL 8.0 实例并 fail-fast；其他工作树需先确认有该参数。不要为单项验证调用整个 `mysql-p0`。使用方式及交付流程见 [开发流程](development-workflow.md)。

## 部署前验收的处理

- Stage 2 已按 [开发流程中的历史收尾记录](development-workflow.md) 完成；旧候选 `5d888d0` 不作为当前运行状态。新验收开始时读取对应候选和实际状态；如有活动 Collect，保持其代码、依赖和环境冻结。
- 自动跟进优先读取证据中的完成状态；核对进程启动时间与命令，不能只根据 PID 认定仍在运行，PID 可能被复用。
- Collect 成功后保留一次同 SHA 的独立 Validate：虽然 Collect 已校验内存中的结果，独立 Validate 还会读取最终落盘 JSON 并扫描其脱敏状态。这是低成本的必要验收，不会再次运行测试；成功后不重复执行。
- Collect 失败后停止验收重试循环，报告首因并定向修复。新一轮完整收集应作为集中验收安排，不能作为每次修复的默认后续动作。
- 正式验收证据必须符合对应合同及已批准的版本限定例外。复用旧版本开发测试结论不能代表新版本获得正式验收，Stage 2 的历史例外不推广到后续候选。

这些规则约束代理主动运行的检查。当前 GitHub PR/master 自动兼容测试尚未调整；部署来源校验与其绑定，迁移范围和时点见开发流程中的 CI 待办，不宣称远端已采用开发快检。

## 后续脚本优化的实施顺序

以下区分已实现的开发入口和按需安排的进一步优化。不要为了完善测试设施再次占用整个功能开发周期。

1. 已实现：后端/前端显式快检入口、MySQL 套件内文件/节点选择、开发 fail-fast、默认单版本、拒绝正式证据环境；复用正式容器初始化、TLS、四类账户和清理。已验证选择/拒绝逻辑；真实容器开发模式尚待一次定向联调。
2. 为每个验收命令实时输出经过脱敏的进度与耗时，记录失败节点和执行状态，解决当前整条命令结束才写日志导致的长时间不可见问题。
3. 设计同 SHA 的断点续跑：仅复用已成功且命令、测试集合摘要、环境、依赖及产物校验均匹配的步骤；新尝试写新记录，保留失败证据。实现前不得手工拼接出通过结果。
4. 对迁移耗时做单次定向计时分析，再判断能否减少重复建库；不能先放宽迁移覆盖、共享有污染风险的 schema 或同时争抢资源运行双版本性能测试。

## 交付格式

每个开发任务说明：改了什么、定向验证结果与耗时、人工体验入口/步骤与确认状态、尚待阶段验收的项目。人工体验不触发全量测试，也不能替代必要的权限、数据一致性和正式发布检查。无需为文档或流程规则修改运行 Python 全量、前端构建、MySQL 或 E2E。
