# 统一测试与验证流程 v2.0（规则整理）

2026-09-17。适用于本项目主工作区及后续工作树。本文件是测试范围、入口、复用和失败处理的统一依据；AGENTS及Skill搭配表引用本文件，不再各建一套流程。显式用户授权、当前冻结候选合同及数据边界继续有效。

2026-10-10整理：本文件维护验证规则；实际脚本能力须核对任务来源，当前版本/CI/发布状态只读[执行卡](../workflow/project-plan-index.md)。本轮不改runner、CI或正式顺序，正式断点续跑尚未实现。

## 1. 一条流程，按风险选择范围

### 完整功能优先（2026-09-23用户明确要求）

后续先由代理完整测试本次交付功能，再测试其他项目。功能范围以本次交付或约定体验范围为准；整批交付须逐项覆盖，不以单一成功页面代替整批功能，也不自动扩大到无关模块的全仓回归。

- 在目标体验环境或已说明差异的隔离环境，实际走通入口、登录/角色、数据与初始化前置、主要操作、结果展示及刷新后状态；包含直接关联页面和上下游结果核对。
- 同时检查适用的未初始化、部分就绪、空数据、权限不足、业务失败与恢复路径，确认提示和下一步操作准确。合成数据或隔离账号用于需要状态变化的场景；不得为测试擅自确认真实来源、批准映射或修改业务数据。
- 运行功能所必需的构建、启动和安全前置可先完成；功能有阻塞时先诊断、修复并复验该路径，不先堆叠无关测试。功能完整走通后，再按风险执行必要的单元/组件、静态、集成、性能等其他检查。必要的缺陷复现和修复检查可用于解除该阻塞。
- 健康探针、API 200、导入成功、mock/组件测试通过都不能单独替代完整功能测试。缺少环境、数据或授权时标记具体未测步骤及阻塞，不能把发现基础缺陷的责任留给用户体验。
- 交付记录逐项写明功能路径、版本/环境、实际结果及未覆盖部分；仅确认已走通且前置齐备的功能可体验。用户本人确认仍单独记录，代理测试不能标为`user_verified`。

本要求覆盖旧的“先目标测试、后体验入口检查”顺序；文档等无运行功能的任务仍按文档检查处理。完整功能测试优先不删减正式门禁，也不改变canonical内部顺序或自动授权新一轮Collect；已验证且版本、环境、数据前置未变的同批完整功能结果无需为重复汇报重跑。

### 部署准备快速检查与正式上线验收（2026-09-18用户确认）

部署准备中的定向诊断/快速检查可按已确认的短采样方案使用3次35秒真实心跳窗口，只支持对应开发/诊断结论。必须显式选择快速模式、隔离证据并标记`formal_evidence=false`；未选择时不得静默缩短正式协议。历史代码与合同保护记录见文末归档；具体工作树是否具备该能力须读实际脚本，不能按文档自动执行。

真正上线必须对选定发布候选完成规定的完整测试、审计及运维准入：全量回归、既有双版本/性能/恢复等正式门禁、权限与数据一致性/安全审查、部署配置与迁移检查、可恢复备份、回退方案、日志监控/告警及上线后健康核验。复用有效证据须符合正式合同，不把“完整”理解为每次小修或每条消息全部重跑。各项范围、适用版本、责任与未完成项在正式发布安排中列清。

正式心跳目前保持原每轮3预热+20测量、3轮协议，不受诊断短采样影响。正式validator必须拒绝快速证据，不能将其拼接为正式PASS；快速检查通过不等于accepted、可部署或已上线。未完成正式条件时，只能继续前置允许的独立工作，不能跳过发布准入。正式测试和实际迁移/部署仍按明确授权执行。

**确认任务和版本 → 预检输入/环境 → 集中实现 → 代理完整测试交付功能（阻塞先修复）→ 其他必要检查 → 交付用户体验 → 到发布准备再完成正式门禁。**

状态查询不启动测试；纯文档从diff检查直接交付。已获授权的实现不为选择测试方式反复审批。新一轮昂贵正式Collect仍须符合当前授权，不因“继续开发”自动启动。

| 档位 | 适用改动 | 必须回答的风险 | 默认执行及入口 |
| --- | --- | --- | --- |
| 文档/静态 | 计划、注释、纯文案/局部样式 | 链接、语法或显示是否错误 | 定向diff/链接，必要预览；不启动应用测试 |
| 功能快检 | 独立UI交互、局部逻辑 | 当前行为和直接调用者是否回归 | run-dev-check显式节点/文件；必要的受影响静态检查 |
| 关键集成 | 权限、SKU关联、数据库、并发、幂等、公共接口 | 越权、错配、重复记账、事务及兼容是否正确 | 目标规则测试+必要的真实边界检查；MySQL DevelopmentTests单版本 |
| 体验交付 | 一个可用业务路径 | 入口、角色、数据是否就绪、操作是否顺手 | 验证入口和前置，提供3–5步；已有有效结果不重跑，用户本人确认 |
| 正式发布 | 冻结候选与批准的发布范围 | 整体能否发布、恢复、回退，证据是否属于本候选 | 既有canonical runner及规定完整门禁，完成finalize/validate等合同步骤 |

档位不等于每次必须依次跑五套。一个任务可只需要其中一档；关键规则的真实集成检查不能由mock通过代替。界面可访问性影响登录、操作或数据理解时属于功能风险，不能一律列为低优先级。此前讨论中的35%/30%等投入比例无实测依据，不作为选测或删门禁标准。

### UI 与前端 CI 按影响范围执行（2026-10-09用户确认）

用户明确同意后续采用：基础检查每次运行，功能测试覆盖受影响路径；视觉检查只测修改的组件及关联页面，完整检查留给大范围改版或发布。

- 含前端代码改动的 PR 保留基础 lint、类型、Token 与构建检查；组件与浏览器测试覆盖本次行为和直接消费者，包括适用的 URL 状态、权限、失败恢复和刷新结果。纯文档仍按文档检查处理。
- 局部 UI 改动使用已有明确目标，视觉与可访问性检查选择受影响的组件、故事、关联页面及适用尺寸；普通文案不默认执行全套浏览器或截图。共享样式、Design System、路由或依赖改动须按实际影响扩大消费者范围，不能只测一个示例。
- 大范围 UI 改版、整合和正式发布保留规定的完整检查；权限、业务状态及可访问操作等关键风险继续验证。截图比较发现显示变化，不判断设计质量，也不替代用户体验确认。
- 自动选测必须能说明覆盖范围；影响范围无法可靠确定时执行相应完整套件。零执行、收集成功、跳过或取消不算通过；失败不能靠缩小范围、更新基线或降低阈值消除。

本条是已批准的后续策略；PR自动影响范围选择尚未实现。现行CI的具体SHA、完成状态及下一动作只读[执行卡](../workflow/project-plan-index.md)，不在策略文档保留“正在运行”的快照。实施选测须在对应授权及非活动来源进行，沿用稳定汇总门禁；正式发布合同及数据边界保持。

### 页面可见状态与融合入口验证（2026-10-27）

页面切换／向导／多入口整合的具体执行沿[开发流程](development-workflow.md#ui-integration)。只覆盖本次修改和直接消费者，保留仍有效的业务合同测试。

- 回归应识别已暴露的行为：URL、选中项、可见内容与实际操作一致；加载或读取失败不丢输入且不可提交；有修改时离开提示可继续填写或明确放弃；草稿与最终确认使用当前修订，结果未知时不重复记账。
- 显示布局、原生fieldset／details、inert、焦点和浏览器历史等行为须有真实浏览器证据。JSDOM只证明其支持的逻辑；零布局、不可点击、旧内容残留或无匹配目标不能用DOM存在断言代替。无新变化的有效结果继续复用，不因写文档另跑业务测试。
- 本次影响响应式或列表开合时，覆盖宽窄窗口跨断点→收起／展开列表→切换页签的组合，而非只在固定尺寸分别截图；核对面板非零布局、列表开合不被同单页签／刷新重置，以及内容是否被推离当前视区。自动操作超时、快捷键未改变历史项或目标仍在加载时不计通过，也不直接判为产品故障；保留现场后区分原因。
- 功能整合核对普通入口、必要高级／兼容入口及历史草稿：手工、模板／原表导入、导出、核对、确认和失败恢复按本次承诺保留；多订单、混合来源或关联安排的原关系不因共用UI丢失。
- 体验包变更后核对实际启动配置、页面加载资源与关键结果属于最终包。浏览器显示异常刷新后消失仅算恢复证据，根因及回归范围未闭合时不得记为修复完成。浏览器写入只使用已授权虚构样本，不借验证扩大真实数据范围。

## 2. 选测与预检

### 冻结前的低成本检查（2026-09-28）

已授权准备修复候选时，优先在非冻结来源排除已知的低成本阻塞，再形成新候选和安排昂贵producer/Collect：

- 复用已有有效结果；本轮新增或修改的测试文件同样进入受影响的lint/类型检查，不能只验证业务文件。类型检查无法可靠局部化时使用项目现有必要范围并说明原因。
- 对已暴露的测试隔离、fixture、schema/触发器清单、精确节点收集问题，集中核对同一根因直接涉及的合同和最小回归。收集成功只证明可收集，不能替代必要测试体或真实数据库验证。
- 按本次实际服务核对启动参数传递、可绑定端口和HTTP就绪；已有同环境有效结果可复用，不因改一条文案重启全部服务。所需依赖、私有输入或真实资源访问仍限原授权。
- 先集中修完当前已知同类问题，再按该次授权提交/冻结；不要为每一个测试断言单独创建候选。首因已定位就不扩为全仓审计，也不为预检增建平台。

这是正式链之外的来源准备，不调整canonical内部顺序、不减少正式采样、不增加跨SHA复用或断点续跑。显式停止/不重试规则继续有效。冻结候选仍不得就地修改；文档、普通功能交付不因此增加一轮候选预检。

### 范围内连续执行，真实扩面才决策

已授权结果所必需的实现、复现、定向验证和原失败复核连续完成，不按测试节点重复申请。普通检查沿用项目时间预算；预计超出时解释耗时位置和剩余必要工作，不强杀迁移或把未执行算通过。

拟增加无关模块、数据库版本、真实资源范围、昂贵正式运行或测试平台时，先说明：现有证据未回答的具体风险、它阻塞哪项交付、最小新增范围与预计成本，以及延期影响和推荐动作。证据不足说明未知，待缺少的决定明确后再执行新增范围。正式合同尚缺的必需证据也是发布阻塞，不能随意删减。

紧急程度只在真实决策需要时标明：数据损坏/越权风险先暂停受影响操作；已确认的当前交付阻塞优先解决；后续风险列触发时点；无当前影响的优化列待办。标签不授予额外权限。已有授权不再次索取，未回复也不等于新增授权；等待时继续可独立完成的已授权工作。

开工只记录一行：`版本/改动范围｜风险→目标检查｜预计耗时｜可沿用证据｜剩余发布检查`。沿用现有任务记录，不另建台账。

- 优先函数/节点，其次文件，最后必要的直接消费者；新增测试只覆盖明确缺陷或未覆盖的关键行为。
- 同一使用路径集中改完再验证，不按每次保存重跑。静态检查仅选适用项，不机械叠加全仓lint、类型、构建、浏览器和Storybook。
- 普通快检预算约3分钟，数据库约10分钟。超预算说明耗时在收集、初始化还是执行，以及剩余必要工作；不强杀迁移，不把未执行写成通过。
- 复用现有依赖；任务专用临时目录优先D盘。不下载镜像或重装依赖来碰运气。不并行争抢重型MySQL/性能资源，不复用被污染的schema。
- `ListOnly`用于预览选中的命令，不算测试通过；过滤后全部跳过、没有测试、收集失败或进程退出异常不能算验证成功。

正式运行前，在授权范围内先检查实际候选SHA/tree、清单与洁净状态、有效的非秘密输入、依赖/端口、证据存在性及身份/摘要。优先现有ValidateOnly，不改变canonical实际执行顺序。不要打印整个环境、读取秘密、自动替换环境变量或补造证据字段；涉及私有样本/业务库的预检仍须原授权。

性能证据预检可使用现有`run-product-catalog-performance.ps1 -ValidateOnly`，显式传入SourceSha、PythonExecutable、MySql80EvidencePath和MySql84EvidencePath。它核对实际来源及字段，不启动性能矩阵；不得附加GenerateEvidence或SetUserEnvironment。必须在对应候选工作树运行。本次未替当前候选执行该命令，也未认可任何尚未核对的证据。

注意：其他ValidateOnly可能建临时目录或读取私有输入，使用前核对实际副作用，不能仅凭参数名认定无访问或无写入。发现前置失败先解决前置，不先运行其依赖的昂贵套件。

## 3. 统一使用已有入口

从任务所在工作树执行，不把主工作区脚本改动注入冻结候选。先确认该工作树支持所需参数。

```powershell
# 后端：已有目标文件或 ::节点；默认排除MySQL
./scripts/run-dev-check.ps1 -Kind Backend -Targets backend/tests/unit/worker/test_runner.py -ListOnly

# 前端：明确文件；需要时增加完整测试名正则
./scripts/run-dev-check.ps1 -Kind Frontend -Targets frontend/src/features/admin/AdminConsole.test.tsx -ListOnly
# -TestName '实际已存在的测试名称正则' 可缩小上述前端范围
# 确认范围后移除 -ListOnly 执行；示例测试文件不代表每个任务都应运行它
```

- Backend：pytest显式节点/文件、`-x`、`not mysql`，唯一basetemp；临时目录不能与其他任务复用，因为pytest可能清空它。
- Frontend：Vitest显式文件、`--bail=1`；可选`-TestName`只适用于前端。使用名称过滤时检查JSON结果，至少一项实际通过且无失败才成功；报告保留在任务工作树`.tmp/dev-check-<唯一ID>`，不是正式发布证据。
- MySQL：`test-mysql-matrix.ps1 -DevelopmentTests`，指定对应Suites、PythonExecutable及套件内已有文件/节点；默认8.0单版本、fail-fast。`-ListDevelopmentTests`预览仍须先核对脚本前置；不使用全mysql-p0代替单项检查。
- 浏览器：仅跨页面/API联动或实际缺陷需要时走一条受影响路径；普通文案不用E2E。无法用现有前端快检入口选择的E2E，使用所属runner的明确目标，不扩大入口支持整个回归。
- 静态检查：使用现有Ruff/ESLint等明确文件命令。类型检查若无法可靠局部化，可说明共享类型风险后运行必要范围；不伪装工具支持不存在的文件级能力。
- Java：进入6a后按所选构建器接入目标测试入口，保留同样的档位/状态合同；当前不创建Java测试平台。

快检成功/失败均显示执行耗时。未改变正式runner、GitHub PR/master CI或完整矩阵；远端自动门禁继续按原合同。

## 4. 失败与证据复用

| 情况 | 下一动作 |
| --- | --- |
| 环境/输入前置失败 | 说明首因，修正授权范围内的前置，再重查该前置；不以业务全套诊断环境 |
| 当前功能失败 | 修复后重跑原失败和直接受影响检查；数据库污染需必要隔离验证 |
| 无关历史失败 | 在原任务记录保留，继续独立功能；不宣称完整通过 |
| 相同相关代码、输入、依赖、配置、环境已有通过结果 | 引用版本、范围及结果，不因换对话、完成声明或评审重跑 |
| 公共接口/规范化/依赖变化 | 使相应旧证据失效，只补受影响开发检查；正式证据按发布合同判定 |
| 正式Collect失败 | 按首因停止，保存原证据；不自动循环或拼接其他run。新运行按当前授权和合同执行 |

开发证据复用不等于正式断点续跑。当前正式baseline仍要求符合既定来源和运行合同；没有实现可靠续跑前，不能跳过步骤组装PASS。旧SHA不得冒充新SHA。Stage2历史版本限定例外不推广到新候选。

不因为一次测试调整就推翻用户所有体验确认，只复体验受影响路径。完整体验入口的准备不天然要求再跑全套；若具体发布/体验任务明确规定先验收，则遵守该前置。此前笼统“所有用户体验必须在完整验收之后”的说法不是本项目通用要求。

## 5. 交付、体验与发布

开发、可体验、用户确认、正式验收和已部署分别记录，定义见[开发流程](development-workflow.md#delivery-states)。验证结果必须注明实际来源与范围，不能用自动检查或批准开发代替用户确认。

正式发布：冻结候选及环境 → 授权范围内预检 → 原合同Collect → finalize及同SHA独立validate-run（按runner合同）→ 汇总未覆盖和发布限制。独立Validate核对落盘证据和脱敏，不是再执行整个测试套件；成功后无需反复运行。适用体验及所有正式条件满足才能accepted，之后提交/整合/迁移/部署按相应授权。

活动Collect期间不修改其工作树、依赖、环境或启动另一份完整门禁。跟进核对进程启动时间和命令，不仅凭PID。正式环境、私有输入、data/及真实业务库沿用项目访问限制；数据库验证只用任务所有的可抛弃容器，真实数据库不做测试迁移。

交付只写适用信息：实际改动与来源、验证/复用范围、未执行或失败及影响、体验入口或文档审阅方式；存在必要下一动作时再说明。不以通过测试数量代替功能完成，不隐去允许跳过或未处理错误。

每批说明实际结果、必要验证和剩余影响。只有存在实质下一项时才给出具体推荐、依据及需要用户决定的范围；无必要后续工作就明确收尾，不凑风险等级、成本表或新测试。已有授权内的必要工作继续完成，超范围建议按第2节处理。

未执行检查须如实记录，不推测结果或工具副作用。`ruff format --check`只检查并报告，不修改文件；格式检查、自动格式化及是否修复既有格式差异分别判断。未执行时不能声称一定会出现整文件问题或以“检查会重写”为由跳过。

## 6. 规则归属与历史

- 本文只维护检查范围、执行入口、证据复用及正式合同边界；脚本能力须核对任务来源，运行状态与未决动作只记[执行卡](../workflow/project-plan-index.md)。
- 同SHA正式断点续跑未实现且延期；开发证据复用、短采样和CI拆分都不能代替正式续跑或跨SHA验收。
- [整理前原文](development-verification-policy.history-2026-10-10.md)保留旧A/B快速检查批次、实现记录、历史耗时和当时CI状态。测试效率批次A/B与应用待上线/开发线A/B不是同一对象。
- 本轮只整理规则，没有运行示例命令或验证业务数据，未修改runner/CI或减少原门禁。
