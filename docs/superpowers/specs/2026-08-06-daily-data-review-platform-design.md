# 每日数据审核与可视化平台设计规格

日期：2026-08-06
状态：需求与书面规格已确认；阶段 4 门禁及阶段 5 后端实现与本地 MySQL 8.0 专项验收已完成。当前本地正式库保持在 `0006`，测试库已确认为 `0008`；MySQL 8.4 由 PR 兼容矩阵 CI 验证，正式库升级和真实机器强制断电恢复尚未完成

## 1. 背景

当前数据源位于 `表格` 目录，共 62 份 CSV：31 份经营报告和 31 份亚马逊物流买家退货报告。经营报告不含独立的报告日期字段，日期来自文件名；退货报告同时包含文件名日期和记录级 `return-date`。

系统首先在本地运行，后续部署到服务器，预计约 20 名用户。未来可能接入 Agent，用于只读分析、异常识别和纠错建议。

## 2. 目标

系统需要完成以下工作：

1. 按报告日期和报表类型隔离数据。
2. 上传后先解析、清洗和校验，不直接进入正式数据。
3. 允许人工对照原始值与处理值，确认应用录入是否准确。
4. 允许人工纠正处理错误，并在批次、行或字段层级添加备注。
5. 审核确认后才发布给看板和 Agent。
6. 允许修改任意一天的已发布数据，同时保留完整版本、差异和审计记录。
7. 支持本地单机使用，并能平滑迁移为约 20 人使用的服务器部署。

## 3. 非目标

首版不包含：

- 强制录入人与审核人分离的双人审批。
- 多级审批流。
- Agent 自动修改或自动发布数据。
- 直接覆盖或删除原始 CSV。
- 面向超大规模数据仓库的分布式计算。

## 4. 核心术语与隔离边界

### 4.1 每日数据集

每日数据集的唯一业务边界为：

`报告日期 + 报表类型`

报表类型首版固定为：

- `business_report`：经营报告。
- `return_report`：亚马逊物流买家退货报告。

例如，`2026-07-31 + business_report` 与 `2026-07-31 + return_report` 是两个互相独立的数据集。

### 4.2 日期口径

- `detected_report_date`：系统从文件名识别出的日期，作为只读溯源信息保存。
- `report_date`：用户最终选择的数据所属日，使用 MySQL `DATE` 类型，不参与时区转换。
- `return_date`：退货记录中的实际事件时间。当前样本包含 `+00:00` 时区偏移，按偏移转换为 UTC 保存；若未来文件不含时区，必须使用该站点已配置的源时区，未配置时作为阻断错误，禁止猜测时区。

站点源时区和报表统计时区都是独立、版本化的 IANA 时区配置，禁止继承宿主机或浏览器时区。当前美元样本默认归属 `amazon_us`，首版报表统计时区设为 `America/Los_Angeles`；管理员可以通过有审计记录的新配置版本调整。源时区变化只影响之后的新解析尝试，统计时区变化则触发该站点全部退货事件日汇总重算，原始 UTC 时间不变。

上传前可以先选择 `report_date`；未选择时，界面可把 `detected_report_date` 作为待人工确认的默认建议，但识别结果不能自动成为权威日期。`report_date` 在解析确认时由人工保存，并独立于解析是否成功：失败重解析可以保留本次人工日期选择，但不能切换当前成功解析指针或当前生效报表类型。服务同时提供独立 `ChangeReportDateCommand`；它只允许尚未被 `version_input_batches` 物化且状态既非 `processing` 也非 `rejected` 的导入批次直接更新 `report_date`，并写入一条结果为 `applied` 的审计。该命令不递增属于解析确认的 `confirmation_revision`，不创建 `parse_attempts`、源行或解析基线，也不切换当前成功解析指针或当前生效报表类型。批次物化后的日期调整进入阶段 5 的草稿日期迁移事务；已发布后的跨日期移动仍只能由管理员执行，并生成修订记录。

当前 31 份退货报告共 449 行，全部横跨两个 UTC 事件日，其中 141 行的事件日与文件名报告日不同。因此“数据集隔离日”和“退货事件日”必须作为两个独立维度保存和展示，不能互相替代。

### 4.3 数据层次

每个每日数据集包含：

- 原始层：原始 CSV 文件、文件哈希、每次解析尝试及其解码出的源行和单元格字符串；所有记录永久只读。
- 草稿层：经过解析和清洗的类型化数据；允许纠错和备注。
- 发布层：已审核并供看板与 Agent 使用的版本。
- 历史层：过去发布版本和废弃草稿；均可查看和复制，但只有曾成功发布且属于同一每日数据集的不可变版本可以回滚为当前版本。

同一每日数据集任意时刻最多有一个当前发布版本，并允许存在一个活动草稿。新上传或修改请求若已有活动草稿，必须继续该草稿或显式废弃后重建，不能静默覆盖。

### 4.4 状态模型

导入批次状态固定为：

`uploaded → processing → staged`

解析失败进入 `processing_failed`；该状态可以通过创建一次新的不可变解析尝试重新进入 `processing`。用户明确放弃的批次进入 `rejected`。失败或放弃批次不能创建发布版本。

数据版本状态固定为：

`draft → ready_for_publish → published`

`draft` 或 `ready_for_publish` 可以进入 `discarded`。版本一旦成功发布，内容和状态永久只读；“当前”“被新版替代”“已跨日期迁出”均由发布指针和发布事件表达，不修改历史版本。废弃草稿不能直接回滚或发布，只能复制为一个新草稿。当前状态由服务端状态机校验，客户端不能跳过审核直接改写状态。

## 5. 推荐架构

```text
React 前端
  ├─ 数据日历与上传
  ├─ 数据审核工作台
  ├─ 版本与审计记录
  ├─ 经营看板
  └─ Agent 分析面板（后续）
          ↓ HTTPS / JSON API
FastAPI 后端
  ├─ 身份认证与权限
  ├─ 文件接收与报表识别
  ├─ 报表解析器
  ├─ 校验与对账引擎
  ├─ 草稿与版本服务
  ├─ 发布服务
  ├─ 看板查询服务
  └─ Agent 工具网关（后续）
          ↓
MySQL 8 + 原始文件存储目录
```

### 5.1 技术选择

- 前端：React、TypeScript、ECharts。
- 后端：Python、FastAPI。
- 主数据库：MySQL 8.4 LTS。
- 原始文件：按 SHA-256 内容寻址保存在文件系统；数据库只保存相对存储键、哈希、大小和元数据，不保存宿主机绝对路径。
- 本地与服务器：使用同一套 Docker Compose 服务定义，通过环境配置区分端口、密码、文件目录和域名。

MySQL 从首版开始使用，以避免未来多人部署时迁移草稿、版本和审计数据。约 20 名用户只需单个 MySQL 实例和常规连接池，不需要分布式数据库。

### 5.2 模块边界

- 报表识别器只负责识别类型、日期、编码和字段版本。
- 解析器只负责把原始字符串转换为标准类型，并保留原值。
- 校验器只生成问题和对账结果，不自动发布或覆盖数据。
- 版本服务负责草稿、修订、差异和回滚。
- 发布服务负责以事务方式切换当前发布版本。
- 看板服务只读取当前发布版本。
- Agent 工具网关只暴露受控、只读的业务查询和建议能力。

## 6. 概念数据模型

以下为概念表，实施计划可进一步确定字段和索引：

### 6.1 用户与权限

- `users`：账号、密码哈希、状态、最后登录时间。
- `roles`：`admin`、`data_manager`、`viewer`。
- `user_roles`：用户与角色关联。
- `site_config_versions`：站点代码、版本、源 IANA 时区、报表统计 IANA 时区、币种、生效时间和修改审计；导入批次和解析尝试引用具体版本。

### 6.2 文件与导入

- `raw_files`：原始文件元数据、SHA-256、相对存储键、上传人、上传时间。
- `file_ingest_leases`：文件落盘期间的短期租约、哈希、状态和过期时间，防止孤儿对账任务移动仍在提交的内容对象。
- `import_batches`：分别保存系统识别类型、人工确认类型、当前成功解析的生效类型、识别日期、人工选择日期、批次状态、当前成功解析尝试指针、行数和错误摘要；三种类型不能互相覆盖。活动解析只在批次上保存处理 token、完整命令摘要和开始时间，并以追加式审计记录开始、超时放弃和终态。
- `parse_operation_tokens`：确认并解析命令的不可变全局 token 归属账本；每个 UUID 在该命令类型内永久绑定一个批次和一份完整命令摘要。
- `report_date_operation_tokens`：独立日期修改命令的不可变全局 token 归属账本；每个 UUID 在该命令类型内永久绑定一个批次和一份完整命令摘要。
- `parse_attempts`：只保存不可变的成功或失败终态结果，包括操作 token 及完整命令摘要、编码、分隔符、字段映射、解析器版本、规则版本、开始/完成时间和结果摘要；不创建需要 UPDATE 才能终结的 `running` 记录。重新解析始终新建终态记录，每个成功尝试恰好生成一个不可变解析基线。
- `parsed_source_rows`：所属解析尝试、原始行号和完整解码字段 JSON，用于单元格级对照；解析尝试写入完成后不可修改。

### 6.3 数据集与版本

- `daily_datasets`：`report_date`、`report_type`；两者建立唯一约束。
- `daily_dataset_locks`：服务必须为每个数据集维护一条专用同步记录，`dataset_id` 同时为主键和指向 `daily_datasets` 的外键；数据库可保证锁行不孤立且每个数据集最多一条锁行，但单向外键不能独立保证每个父数据集都有锁行。运行账号只获得 `UPDATE(lock_revision)` 列权限，不能更新主键。该技术列只用于取得排他行锁，不属于业务数据、版本号或审计依据。
- `dataset_versions`：数据集、版本号、状态、数据修订号、审核修订号、规则集版本、创建人和创建时间。
- `version_parent_versions`：版本与一个或多个父版本的关系，并标记 `base`、`draft_predecessor`、`merge_target`、`merge_source` 或 `moved_source` 等谱系类型。
- `version_input_batches`：版本与一个或多个来源批次的多对多关系，用于合并和替换溯源。
- `parse_baselines`：每个成功解析尝试生成的不可变类型化基线，记录解析器版本、规则集版本、数据摘要哈希、行数和合计。
- `business_parse_baseline_rows` / `return_parse_baseline_rows`：两类报表解析基线的不可变类型化行。
- `version_base_snapshots`：每个数据版本创建时冻结的唯一基础快照，记录有序的解析基线和父版本成员、合并决策、摘要哈希和合计。
- `version_base_rows` 与 `business_version_base_rows` / `return_version_base_rows`：版本基础快照的不可变行身份、`row_state` 和类型化当前值；当前草稿的所有人工变化均相对它记录。
- `dataset_drafts`：每个数据集活动草稿的唯一指针；没有草稿时不存在对应记录。
- `draft_operation_tokens`：阶段 5 草稿写命令的不可变全局 token 归属账本；每个稳定 UUID 永久绑定命令类型、完整命令摘要和操作者。
- `draft_operation_results`：每个草稿写 token 的不可变首次终态结果，冻结结果类型、数据集、版本号、状态、两类修订号和来源谱系；后续重试不得按版本当前状态重新计算这些字段。
- `draft_disposition_events`：草稿被废弃、替代、强制重建或改日时的追加式终态事件，记录终态修订号和后继版本；事件只描述处置，不复制前任的人工修改历史。
- `dataset_publications`：每个数据集当前发布版本的唯一指针。
- `business_report_rows`：经营报告的类型化处理结果，包含版本 ID、跨版本稳定的逻辑行 ID 和原始行 ID。
- `return_report_rows`：退货报告的类型化处理结果，包含版本 ID、跨版本稳定的逻辑行 ID 和原始行 ID。
- `publication_events`：首次发布、替换、回滚、撤下和跨日期移动的不可变事件。
- `publication_outbox`：与发布指针在同一事务写入的后续重算事件，由后台任务可靠消费并重试。

业务行使用数据库生成的代理主键。SKU、ASIN、订单号等用于校验和查询，不直接作为不可变主键，以免源数据中的重复项导致整批无法保存。逻辑行 ID 用于跨版本跟踪同一业务行；人工新增、排除、恢复或删除处理行时保留该逻辑标识。

成功解析尝试先固化为解析基线，避免未来解析器代码变化后历史结果漂移。创建任何草稿时，再把所选解析基线和父版本按明确顺序合成为一次不可变版本基础快照；替换只有一个解析基线成员，普通修订以父发布版本为成员，合并则列出全部成员、优先级和逐行冲突决定。草稿处理行从该基础快照复制，之后只能通过追加式修改事件产生差异。

活动草稿生成后继草稿或迁往另一日期时，系统把前任处理行的当前值、`row_state` 和 `logical_row_id` 冻结为后继版本的新基础快照，使后继草稿从用户最后确认的处理结果继续工作。`field_changes`、`row_changes` 等追加式修改事件仍只属于产生它们的前任版本，不复制到后继版本；审计界面通过 `version_parent_versions` 谱系回溯前任事件。这样既保留修改结果，也不会把旧事件错误地解释为针对新基础快照的再次修改。

数据库必须落实以下不变量：

- `daily_datasets` 对 `(report_date, report_type)` 唯一。
- `dataset_versions` 对 `(dataset_id, version_no)` 唯一。
- `dataset_drafts.dataset_id` 和 `dataset_publications.dataset_id` 分别为主键，表达最多一个活动草稿和一个当前发布版本。
- 草稿指针和发布指针使用包含 `dataset_id` 的复合外键，保证所指版本属于同一数据集。
- 创建草稿、分配版本号和首次发布前，后端按 `dataset_id` 升序更新对应 `daily_dataset_locks.lock_revision` 取得排他行锁，再普通读取不可变的 `daily_datasets`。新建数据集必须在同一事务创建锁行；`0008` 升级为全部既有数据集回填锁行。不得通过联表 `FOR UPDATE` 把不可变数据集表重新纳入写权限范围。只有两个并发事务同时发现目标日期尚不存在、其中一个先完成创建时，失败方才以一次 `FOR SHARE` 当前读发现唯一键竞争的胜者，随后仍通过技术列更新锁定专用同步行；该窄路径不要求 `daily_datasets` 的写权限。
- 活动批次的 `(processing_token, id, processing_operation_digest)` 与成功或失败终态尝试的 `(processing_token, batch_id, operation_digest)` 都通过复合外键引用 `parse_operation_tokens` 的 `(operation_token, batch_id, operation_digest)`，数据库直接拒绝 token、批次或摘要错配。
- 每个阶段 5 草稿写 token 只能有一条首次终态结果；token、结果和草稿处置账本均为追加写，结果字段在首次写入后不随关联版本的后续状态或修订号变化。

### 6.4 校验、修改与备注

- `validation_runs`：版本、数据修订号、规则集版本、执行时间、结果和数据摘要哈希。
- `validation_issues`：所属校验运行、问题级别、规则、行、字段、原值和处理值；生成后不可修改，当前解决状态由审核事件计算。
- `issue_review_events`：警告确认、阻断项解决和重新打开等追加式审核事件。
- `field_changes`：版本、行、字段、修改前值、修改后值、修改人、时间和原因。
- `row_changes`：处理行的新增、排除、恢复或删除记录、修改人、时间和原因。
- `notes`：可关联批次、数据集版本、行或字段。首版批次备注强制为 `internal`，不会进入查看人员页面；版本、行和字段备注包含 `internal` 或 `viewer_visible` 可见级别，默认仅内部可见。
- `audit_events`：上传、修改日期、编辑、发布、回滚、登录和权限变更等操作事件。

`publication_events`、`audit_events`、`field_changes`、`row_changes` 和 `issue_review_events` 均为追加写记录，普通应用数据库账号无更新或删除权限。`parse_operation_tokens`、`report_date_operation_tokens`、`draft_operation_tokens`、`draft_operation_results` 与 `draft_disposition_events` 同样只允许运行账号 `SELECT` 和 `INSERT`，不授予 `UPDATE` 或 `DELETE`。`daily_dataset_locks` 是例外的纯同步表：运行账号拥有 `SELECT`、`INSERT` 和仅限 `lock_revision` 的列级 `UPDATE`，没有整表 `UPDATE` 或 `DELETE`；`lock_revision` 的值不得进入任何业务判断。撤销操作通过写入反向事件表达；备注修改创建新修订，不覆盖旧备注。数据库迁移账号与运行账号分离。

### 6.5 类型约定

- 金额保存为 `DECIMAL`，同时保存币种；禁止使用浮点类型。
- 百分比以比例值保存，例如原始 `15.90%` 保存为 `0.159000`，展示时还原为 `15.90%`。
- 计数和数量保存为整数。
- `report_date` 保存为 `DATE`。
- 事件时间统一保存为 UTC `DATETIME`。
- 长文本完整保存，不截断买家留言。

## 7. 导入与审核流程

### 7.1 正常流程

```text
选择日期或直接上传
  → 保存原始文件并计算哈希
  → 识别报表类型和文件名日期
  → 人工确认类型、日期、编码和站点配置
  → 创建终态解析尝试，保存不可变源行快照并生成类型化解析基线
  → 以解析基线创建或更新待审核草稿
  → 执行结构、字段、转换和合计校验
  → 打开待审核数据集
  → 人工查看差异、纠错和备注
  → 执行发布前检查
  → 事务化发布新版本
  → 看板与 Agent 读取新版本
```

### 7.2 重复文件

SHA-256 完全相同的文件再次上传时，系统显示已存在的批次、日期和状态，并默认阻止重复导入。管理员可以进入已有批次，但不能用重复上传覆盖原始文件。

### 7.3 目标日期已有数据

目标日期已有同类数据时，数据管理员或管理员必须选择：

- 合并为草稿：若已有活动草稿，系统锁定并封存其当前状态，把其当前值、`row_state` 和逻辑行身份与新解析基线合成为不可变基础快照并创建后继草稿；前任修改事件不复制，历史由版本谱系追溯。成功后在同一事务中废弃旧草稿并切换活动草稿指针。若没有活动草稿，则基于当前发布版本和新解析基线创建草稿。版本通过 `version_input_batches` 关联全部来源批次，并通过版本基础快照固定成员顺序和逐行取舍。
- 替换为新草稿：新草稿仅包含新文件处理结果；当前发布版本在新草稿发布前保持不变。数据管理员可以执行普通替换，但仍须完成全部校验和审核。
- 取消上传。

同一数据集不能创建第二个活动草稿。数据管理员可以废弃自己正在处理的未发布草稿后重建；管理员可以“强制重建草稿”，即在保留审计记录后废弃现有活动草稿。任何角色都不能绕过校验直接替换已发布数据。

单文件内部的潜在重复默认是警告。合并时，若两个来源批次出现相同业务指纹并可能造成重复计数，则为阻断冲突；审核人员必须选择保留来源行、保留目标行或明确保留两行。选择保留两行必须填写原因，解决阻断后保留一条已确认警告。同一指纹在目标或来源侧出现多行时，必须为目标行 × 来源行的每个具体行对提供决定，并拒绝让同一行同时处于保留与排除状态。完整行对决定保存在基础快照成员中；只有一行恰好关联一个决定时，才把该决定投影到基础行的 `merge_action` 和 `merge_reason`。上述操作不会直接改变当前发布版本。

### 7.4 日期变更

- 尚未被 `version_input_batches` 物化的导入批次：通过 `ChangeReportDateCommand` 直接修正批次日期；一旦物化，服务必须拒绝直接改批次日期，避免已冻结版本的来源归属与批次日期漂移。
- 待审核草稿：对于仅来自尚未发布上传批次的草稿，数据管理员或管理员可更改 `report_date`。版本的所属数据集不能就地改写；系统在目标每日数据集中创建新版本，把原草稿的来源关系以及处理行当前值、`row_state` 和逻辑行身份冻结进新基础快照，但不复制追加式修改事件，历史通过版本谱系追溯。成功后在同一事务中废弃原草稿并切换活动草稿指针。若草稿包含某个已发布版本并意图把该版本迁出原日期，则属于跨日期移动，只能由管理员执行。
- 已发布数据：只有管理员可创建跨日期移动修订。
- 移动到已有同类型数据的日期时，必须进入合并或替换审核流程。
- 原始识别日期和原始记录时间始终保留。

若目标日期已有活动草稿，日期变更必须选择并入该草稿或取消；只有管理员可以先强制废弃目标草稿。日期变更全过程不能直接修改任何历史版本的 `dataset_id`。

已发布数据跨日期移动前，来源日期不能存在另一个活动草稿；管理员必须先发布或废弃它，避免移动后旧草稿再次发布回来源日。系统随后在目标日期创建关联原版本的新草稿；若目标日期已有发布版本并选择合并，新草稿通过 `version_parent_versions` 同时记录目标基础版本和移动来源版本。来源日期的当前发布版本继续生效，直到目标草稿通过审核。最终发布按数据集 ID 固定顺序锁住来源和目标数据集，并在一个管理员事务中完成：验证两侧指针、数据修订号和审核修订号未变化，清除来源日期的发布指针，切换目标日期的发布指针，写入两侧发布事件和 outbox 后提交。事务成功后，来源日期不再进入默认看板，但原版本仍作为不可变历史保留。事务失败时，来源与目标日期均保持原状。撤销一次跨日期移动也必须执行对应的双数据集原子事务，不能只在一侧单独回滚。

## 8. 审核工作台设计

审核页采用“差异优先”的单表工作台，而不是将两个 22 列宽表永久并排。

### 8.1 页面区域

- 页面标题区：报告日期、报表类型、文件名、识别日期、状态、版本和上传人。
- 校验摘要：原始行数、处理行数、正常项、警告项、阻断项和人工修改项。
- 筛选区：全部、仅异常、仅人工修改、未解决、按 SKU/ASIN/订单号搜索。
- 数据网格：冻结关键标识列，支持列筛选、排序和横向滚动。
- 对照抽屉：显示当前单元格的原始值、处理值、转换规则、修改历史和备注。
- 异常导航：上一个/下一个异常。
- 批次操作：保存草稿、调整解析设置并重新解析、运行校验、确认发布、废弃草稿。

### 8.2 单元格状态

- 未发生转换且通过校验：普通状态。
- 发生合法格式转换：显示转换标记，可查看原值。
- 警告：黄色标记。
- 阻断错误：红色标记。
- 人工修改：蓝色标记，并展示修改记录。

每个可编辑处理值按来源提供明确的恢复操作：

- “撤销本次修改”：恢复到本次编辑前的值。
- “恢复父版本值”：仅在该逻辑行存在父版本时可用。
- “恢复源文件值”：仅在该逻辑行和字段关联到成功解析尝试的源单元格时可用；人工新增行没有源值，该操作禁用。

多个来源批次合并时必须先选择具体来源再恢复源文件值。所有源值本身不可编辑。

### 8.3 发布条件

- 所有阻断问题必须解决。
- 普通警告可以保留，但必须标记为已查看；日期不一致、确认保留重复项和人工解决阻断项必须填写备注。
- 发布前再次运行完整校验。字段、行、版本基础快照、解析设置或规则变化递增版本级 `data_revision`，并将 `ready_for_publish` 退回 `draft`，从而使旧校验结果失效。
- 警告确认、问题审核状态和发布备注只递增 `review_revision`，不改变数据，也不使同一数据修订的成功校验失效；这些审核事件必须明确关联到当前校验运行，数据修订变化后旧运行的确认自动失去发布资格。
- 发布服务锁定数据集和版本，并要求最新成功的 `validation_runs.data_revision` 与当前数据修订号完全一致、规则集版本仍有效且阻断项为零；同时要求该次校验产生的全部警告已确认且必填备注完整。
- 用户确认数据所属日、报表类型、行数以及第 9.4 节定义的合计。

### 8.4 结构错误的修复路径

字段编辑不能伪装修复解析器错误。系统按以下方式处理：

- 编码、分隔符、报表类型或已支持字段映射选择错误：以新设置创建新的 `parse_attempts`、源行快照和解析基线，旧尝试保持只读。新尝试成功后，界面先展示与当前草稿的差异；用户确认后以新解析基线生成不可变版本基础快照和新草稿，再废弃旧草稿。旧人工修改保留在历史中但不自动套用，避免把修改错误地映射到新行。
- 需要自定义字段映射：数据管理员提交映射建议，管理员保存为新的版本化规则后重新解析；不改写旧批次规则。
- 处理行被重复生成：审核人员可排除多余处理行并填写原因，写入 `row_changes`。
- 处理行被错误排除：审核人员可恢复该逻辑行并填写原因。
- 确认解析器遗漏但无法立即修复规则：数据管理员可新增一条仅存在于处理层的纠错行，必须关联来源批次、填写原因并通过全部字段校验；原始层保持不变。
- 原始文件本身损坏或缺少必要内容：拒绝该批次并要求重新上传正确源文件，不能通过编辑处理值绕过。

## 9. 自动校验与对账

校验分为两个相互独立的阶段：

1. 自动解析保真校验：比较成功解析尝试的源行与尚未人工修改的类型化基线，要求行数、可逆字段和数值合计完全一致。该阶段证明应用没有录错原表。
2. 人工调整可解释性校验：比较该版本不可变的基础快照与当前草稿，要求每个字段差异、行新增、排除和恢复都能由追加式 `field_changes`、`row_changes` 完整重放；合并取舍已经固化在基础快照及其成员清单中。该阶段允许合法纠错，但阻断任何没有审计依据的差异。

发布合计必须满足：`当前草稿合计 = 版本基础快照合计 + 字段修改净变化 + 行级增减净变化`。人工纠错不会降低自动解析保真要求，也不会要求纠错后的数据重新等于原始错误值。

### 9.1 阻断规则

- CSV 无法完整解析或编码不可识别。
- 必需字段缺失、字段错位或表头不属于已支持版本。
- 成功解析尝试的源行数与解析基线行数不一致。
- 经营报告的子 ASIN、SKU，或退货报告的 `return-date`、`order-id`、`sku`、`asin`、`quantity` 在解析基线中发生无法由转换规则解释的改变或丢失。
- 金额、百分比、数量或日期转换失败。
- CSV 引号、逗号或长留言解析后出现截断。
- 源行与解析基线的指定数值列合计不一致，或当前草稿与版本基础快照之间存在无法由修改事件解释的差异。

### 9.2 警告规则

- 用户选择日期与文件名识别日期不同。
- 单一来源文件内部出现潜在重复业务记录；跨批次合并造成的重复计数按第 7.3 节作为阻断冲突处理。
- 未知退货原因或状态。
- 数值违反第 9.4 节的首版业务合理性规则，但原始值与处理值仍准确一致。
- 可选字段缺失。

### 9.3 对账方式

- 比较成功解析尝试的源行与解析基线行数。
- 对源行和解析基线的关键文本字段计算标准化前后的相等性。
- 对源行和解析基线的金额、数量和订单商品数计算批次合计。
- 对百分比执行可逆格式校验，保证处理值重新格式化后与原始精度一致。
- 从版本基础快照开始，按顺序重放全部字段和行级修改事件，验证所得结果与当前草稿逐行一致，并核对修改前后数值净变化。
- 所有校验结果关联到具体解析尝试、批次、版本、行和字段。

### 9.4 首版规则矩阵

规则矩阵随 `ruleset_version` 保存。首版规则如下，后续亚马逊表头变化时新增版本，不回改历史规则。

经营报告：

- 结构必需字段为当前样本中的全部 22 个逻辑列：父 ASIN、子 ASIN、标题、SKU、会话数总计、会话数 B2B、转化率总计、会话百分比 B2B、页面浏览量总计、页面浏览量 B2B、页面浏览量百分比总计、页面浏览量百分比 B2B、推荐报价百分比、推荐报价百分比 B2B、已订购商品数量、已订购商品数量 B2B、商品会话百分比、商品会话百分比 B2B、已订购商品销售额、已订购商品销售额 B2B、订单商品总数、订单商品总数 B2B。表头首尾空格在映射时标准化，但原始表头保留。
- 行级必填字段为子 ASIN 和 SKU；父 ASIN 或标题为空时产生警告。
- 整数转换列为会话数、页面浏览量、已订购商品数量、订单商品总数及对应 B2B 列。
- 百分比转换列严格限定为 8 个源列：`转化率 - 总计` → `conversion_rate_total`、`会话百分比 - 总计 - B2B` → `session_percentage_b2b`、`页面浏览量百分比 - 总计` → `page_view_percentage_total`、`页面浏览量百分比 - 总计 - B2B` → `page_view_percentage_b2b`、`推荐报价（推荐报价展示位）百分比` → `featured_offer_percentage`、`推荐报价（推荐报价展示位）百分比 - B2B` → `featured_offer_percentage_b2b`、`商品会话百分比` → `unit_session_percentage`、`商品会话百分比 - B2B` → `unit_session_percentage_b2b`。
- 金额转换列为已订购商品销售额及其 B2B 列；首版识别 `US$` 并保存币种 `USD`。
- 源行与解析基线之间必须精确对账的合计为全部整数转换列和金额转换列；当前草稿与版本基础快照之间按人工修改净变化对账。百分比只做逐值可逆校验，不求和。
- 单文件潜在重复指纹为“子 ASIN + SKU”；仅提示人工确认，不用数据库唯一约束删除源记录。
- 原始数值为负数、百分比不在 0%–100%、B2B 值大于对应总计、页面浏览量小于会话数时产生业务合理性警告；只要原始与处理结果一致便不视为导入失真。

退货报告：

- 结构必需字段为当前样本中的全部 13 列：`return-date`、`order-id`、`sku`、`asin`、`fnsku`、`product-name`、`quantity`、`fulfillment-center-id`、`detailed-disposition`、`reason`、`status`、`license-plate-number`、`customer-comments`。
- 行级必填字段为 `return-date`、`order-id`、`sku`、`asin`、`quantity`、`detailed-disposition`、`reason` 和 `status`；其余字段允许空值。
- `quantity` 必须转换为正整数；源行与解析基线的数量合计必须一致，当前草稿按人工修改净变化对账。
- `return-date` 必须按原偏移转换为 UTC；无偏移且没有站点源时区配置时阻断发布。
- 潜在重复指纹为“return-date + order-id + sku + asin + fnsku + quantity + license-plate-number”。单文件内为警告，跨批次合并冲突为阻断项。
- 未知 `detailed-disposition`、`reason` 或 `status` 值产生警告，字典随规则集版本保存。
- 商品名称和买家留言按完整 Unicode 文本对账，不能因逗号、引号或换行被截断。

所有规则记录级别、是否允许豁免、是否要求备注和适用报表版本。首版只有警告可以豁免；阻断项必须通过重新解析、数据纠错或第 8.4 节的行级修复真正解决。

## 10. 修改、版本与回滚

### 10.1 待审核修改

人工可以修改任意处理字段，但不能修改原始文件或不可变解析尝试的源行快照。字段修改写入 `field_changes`，行级新增、排除和恢复写入 `row_changes`；两者都递增数据修订号并使旧校验结果失效。警告确认和不改变数据的审核说明只递增审核修订号。初次审核时允许备注可选；解决阻断项时必须填写处理说明。

### 10.2 已发布修改

修改已发布数据时，系统基于当前发布版本创建新草稿，不进行就地更新。数据管理员可编辑、审核并发布新版本，但必须填写修改原因。曾发布版本及其处理行永久只读。

### 10.3 回滚

回滚只允许管理员执行。发布指针只能指向同一每日数据集内曾成功发布的不可变版本；废弃草稿、未发布草稿和其他日期的版本不能作为回滚目标。回滚不删除新版，也不修改历史版本状态，而是在事务中写入发布事件、切换当前发布指针并写入 outbox。跨日期移动必须按第 7.4 节进行双数据集原子撤销。

### 10.4 并发修改

处理行和草稿版本包含修订号。阶段 5 草稿写命令先登记或恢复 operation token，再以共享锁固定操作者账号和角色关系组成的权限快照。物化或强制重建先锁本次直接输入的导入批次和当前解析基线，再通过更新同步表技术列锁数据集、活动草稿或发布指针和父版本；废弃操作按数据集锁、活动版本处理；跨日期改日先按数据集 ID 升序更新来源和目标锁行，再锁两侧实际版本。只有相关版本均已锁定后，事务才枚举这些版本继承的 `version_input_batches`，按批次 ID 升序显式锁定对应导入批次，最后按稳定行序读取或锁定处理行。每类命令必须遵守自己的上述顺序，同一资源集合不得倒序回锁。

阶段 6 的编辑与发布沿用“每日数据集 → 数据版本 → 处理行”的核心顺序。事务锁定数据集并确认 `dataset_drafts` 仍指向目标版本：数据编辑以当前 `data_revision` 和可编辑状态执行原子条件更新，成功后才能修改行并递增数据修订号；警告确认或备注以当前 `review_revision`、当前校验运行和可编辑状态执行条件更新，成功后递增审核修订号。若发布已先完成、版本状态不再可编辑或对应修订号已变化，事务不写入任何行或审核事件，显示最新值和当前用户的操作供重新确认。

`dataset_drafts.version_status` 由 `ON UPDATE RESTRICT` 复合外键绑定 `dataset_versions.status`。活动版本在 `draft` 与 `ready_for_publish` 间切换时，事务必须先持有对应数据集锁并锁定指针与版本，保存原 `pointed_at`，按预期 dataset、version 和旧状态条件删除草稿指针，再条件更新父版本状态和修订号，最后以同一 dataset、version、新状态及原 `pointed_at` 重建指针；任一步失败必须整体回滚。禁止分别直接更新父状态或子冗余状态。

创建草稿、分配版本号和发布时通过更新 `daily_dataset_locks.lock_revision` 锁定数据集。发布事务在锁内重新确认活动草稿指针、版本状态、当前数据修订号、当前审核修订号、最新成功校验、该校验运行的全部警告确认和必填备注；随后按预期版本和状态删除活动草稿指针、将版本封存为 `published`、切换发布指针并写入发布事件与 outbox。跨日期事务始终按数据集 ID 排序加锁。写请求携带幂等键，重复请求返回第一次操作结果。MySQL `1213` 死锁或 `1205` 锁等待超时必须回滚本次完整事务，并以同一 token、同一命令摘要和新的事务从边界重试；每次重放前先尝试恢复不可变终态结果，首次失败后最多重试 3 次，即总尝试最多 4 次，不能从保存点或事务中段继续。超过上限时不保留部分状态并提示用户重试。连接失效或提交确认丢失属于另一类结果不确定场景：只尝试从结果账本恢复，找不到终态结果时返回结果未知，不能盲目重放。

## 11. 数据日历与看板

数据中心首页使用日历作为每日隔离入口，状态按“红 → 黄 → 蓝 → 绿 → 灰”的优先级计算：

- 红色：任一报表存在阻断错误、导入失败或引用文件缺失；优先级最高。
- 黄色：不存在红色问题，但存在待审核草稿、未处理警告或正在导入的批次。
- 蓝色：不存在红黄问题，经营报告与退货报告中只有一类已发布，表示部分就绪。
- 绿色：两类报表均已发布且无待处理问题。
- 灰色：两类报表均无数据。

点击日期后分别展示经营报告和退货报告的状态、当前版本、草稿、历史版本和导入入口。

看板查询必须通过 `dataset_publications` 读取每天当前发布版本。草稿、失败批次和历史版本不能混入默认经营指标。

数据管理日历和经营报告趋势按 `report_date` 隔离。退货看板同时提供两种明确口径：按报告所属日统计，以及按 `return_date` 转换到该站点当前版本化报表统计时区后的事件日统计；界面必须标明当前口径和时区，不能混用。发布或回滚退货版本时，受影响范围包括旧版本与新版本涉及的全部报告日和事件日，而不仅是当前 `report_date`。报表统计时区配置变更时，写入 outbox 并重算该站点全部事件日范围。

首版不引入外部缓存，20 人规模直接使用带版本过滤和索引的 MySQL 查询。若后续增加汇总表或缓存，发布事务只写 `publication_outbox`；后台任务在提交后重算并可重复执行。报告日缓存键必须包含发布版本号；事件日汇总和缓存键必须同时包含发布版本号与 `site_config_version_id`，时区变更后的结果写入新配置版本命名空间。不能在持有发布锁时同步重建，也不能因失效任务失败而继续返回旧版本数据。

## 12. 权限模型

### 12.1 管理员

目前为系统所有者本人，拥有：

- 用户、角色和系统配置管理。
- 上传、纠错、备注、审核和发布。
- 跨日期移动、强制重建活动草稿、回滚和审计查看。
- 数据修复工具与备份恢复入口。

### 12.2 数据管理员

目前为 1 人，拥有：

- 选择日期并上传文件。
- 查看原始值、处理结果和校验问题。
- 修改草稿、添加备注、解决问题和发布。
- 基于已发布版本创建修订并重新发布。
- 创建普通合并或替换草稿；两者均不能绕过校验和审核。

不能管理用户、改变校验规则、删除原始文件、执行跨日期移动或批量回滚。

### 12.3 查看人员

其余约 18 人仅能：

- 查看已发布的汇总数据和经营看板。
- 查看标记为 `viewer_visible` 的版本说明。
- 使用未来的只读 Agent 分析能力。

查看人员不能访问草稿、原始文件、编辑界面或内部审计详情。首版默认向查看人员隐藏完整订单号、物流牌照号和原始买家留言；Agent 可以对已发布留言做聚合归因，但不能向查看人员复述可识别单笔订单的原文。管理员后续可通过独立权限扩大明细可见范围。

所有权限在 FastAPI 后端强制校验，前端隐藏按钮不能替代服务端授权。

## 13. Agent 接入边界

Agent 后续通过 FastAPI 提供的受控工具工作，不持有 MySQL 账号，不执行任意 SQL。

允许的能力包括：

- 查询指定日期范围的已发布经营指标。
- 查询 SKU、ASIN 和退货原因。
- 识别趋势和异常。
- 生成带日期范围和数据版本引用的分析。
- 为审核人员提出纠错建议。

限制如下：

- 默认只读取当前发布版本。
- 草稿仅可通过专门的审核辅助工具向管理员或数据管理员展示。
- Agent 不能直接编辑、发布、回滚或移动日期。
- Agent 提出的修改必须形成建议，由人工应用到草稿。
- 导出、发送报告或其他有外部影响的操作需要再次确认。

## 14. 错误处理与一致性

- 临时目录与正式内容目录必须位于同一文件系统。上传开始时先创建有过期时间的 `file_ingest_leases`，文件写入临时位置并计算 SHA-256 后，按 `sha256/<前两位>/<完整哈希>` 的相对键原子移动到正式目录，再提交引用该存储键并完成租约的数据库事务。若同哈希对象已经存在，先验证大小和哈希后复用，绝不覆盖。
- 文件系统与 MySQL 不能组成同一个事务，因此导入状态机必须幂等。进程若在文件落盘后、数据库提交前中断，只会留下带过期租约的未引用内容对象。定期对账仅处理超过 24 小时、没有有效租约且没有数据库引用的对象，并在移动到隔离区前再次检查租约和引用。数据库引用的文件若缺失，则产生系统级阻断告警并禁止相关版本发布。
- 批次数据库记录、解析尝试源行快照、处理行和活动草稿指针要么在一个事务中完整成功，要么回滚，不保留半份草稿。
- 解析失败保留失败批次信息和日志，但不创建可发布版本。
- `ConfirmAndParseCommand.operation_token` 与 `ChangeReportDateCommand.operation_token` 都是服务入口必填、由调用方在首次调用前生成并在重试时复用的稳定 UUID；服务拒绝缺失或非 UUID token，不得临时生成替代值。两个命令分别把影响结果的全部字段规范化为 SHA-256 摘要：确认解析覆盖批次、类型、日期、编码、站点配置版本和操作者，日期修改覆盖批次、目标日期和操作者。`parse_operation_tokens` 与 `report_date_operation_tokens` 分别作为不可变的全局归属账本；同 token、同批次、同摘要允许恢复，同 token 改变批次或任一命令字段必须拒绝。阶段 7 的 HTTP 写接口直接把客户端幂等键映射为对应的稳定 UUID。
- 确认解析的活动批次和成功或失败终态尝试通过复合外键绑定同一 `parse_operation_tokens` 记录。开始事务或终态事务提交确认丢失时，同 token、同摘要重试返回原 revision、attempt 和 baseline，不增加确认修订、尝试或基线。
- 独立 `ChangeReportDateCommand` 必须锁定导入批次；状态为 `processing` 或 `rejected`，或者已存在 `version_input_batches` 关系时返回冲突。允许执行时只更新 `report_date` 和批次更新时间，并写入唯一的 `import_report_date_change_applied` 审计；即使目标日期与原日期相同，也写入 `changed=false` 的已应用结果。它不递增解析 `confirmation_revision`，不写解析尝试或基线，也不修改当前成功解析指针和当前生效报表类型。日期事务提交确认丢失后，服务使用日期 token 账本和这条 `applied` 审计恢复原结果，不重复修改或写第二条审计。
- 阶段 5 的物化、强制重建、废弃和未发布草稿改日命令同样要求调用方提供稳定 UUID，并把完整命令和操作者规范化为摘要。`draft_operation_tokens`、`draft_operation_results` 与 `draft_disposition_events` 组成不可变账本：同 token、同摘要返回首次写入的终态结果，同 token 改变命令类型、操作者或任一摘要字段时拒绝。首次结果中的状态和修订号是命令完成时的快照，即使版本之后被编辑、替代或废弃，重试也不能返回后来状态。
- 当前解析租约没有心跳，超过 30 分钟会被下一次确认标记为放弃并回收；当前 62 份文件很小，此限制可接受，但在接入后台 worker 或支持大文件前必须增加心跳或主动任务恢复。解析读取虽然同时受存储对象声明大小和上传上限约束，当前实现仍把一份文件完整读入内存并解码；扩大文件上限前必须改为流式或分块方案并重新测量内存峰值。
- 发布在单个 MySQL 事务中完成：锁定数据集和版本、确认活动草稿指针、校验当前数据修订号与最新成功校验一致、确认当前审核修订号下所有警告和必填备注已完成、按预期版本和状态删除活动草稿指针、封存版本为 `published`、写发布事件与 outbox、切换发布指针并提交。
- 发布失败时旧版本继续生效。
- 后端使用结构化日志记录批次 ID、数据集 ID、版本 ID 和请求用户，不在日志中记录密码或完整敏感留言。
- 页面错误必须说明失败环节、受影响对象和可采取的下一步。

## 15. 备份与维护

- MySQL 每日执行一致性备份，并在同一备份清单中记录数据库备份 ID、时间点、所有已引用原始文件的相对存储键、大小和 SHA-256。
- 原始文件内容不可变，备份任务按照清单复制尚未备份的内容对象；只有数据库备份、文件对象和清单哈希全部验证成功后，该次备份才标记成功。
- 默认保留最近 30 份每日备份；保留周期可由管理员配置。
- 每月至少执行一次恢复演练，在干净环境中验证数据库、文件引用和哈希一致。
- 数据库结构使用迁移工具管理，应用版本记录对应的数据库迁移版本。
- `0007` 降级到 `0006` 前必须在任何 MySQL 自动提交 DDL 之前完成预检；若存在失败解析尝试，其尝试类型无法由 `0006` 的单一批次报表类型无损表达，则拒绝降级，不猜测类型或静默丢弃失败历史。
- `0007` 新增两张 operation token 账本后，已有本地运行账号的表级 `INSERT` 授权不会自动扩展到新表。数据库管理员必须按受版本控制的权限清单同步授权并核对：两表均有 `SELECT`、`INSERT`，且没有 `UPDATE`、`DELETE`。
- `0008` 新增 `draft_operation_tokens`、`draft_operation_results`、`draft_disposition_events` 和 `daily_dataset_locks` 后，同样必须按 `scripts/database-privileges.json` 同步运行账号授权；迁移本身不会替既有账号扩展表级权限。前三张不可变账本需要 `SELECT`、`INSERT`，不得授予 `UPDATE`、`DELETE`；锁表需要 `SELECT`、`INSERT` 和 `UPDATE(lock_revision)`，不得授予整表 `UPDATE` 或 `DELETE`。升级期间必须暂停应用写入；本地初始化脚本和后续部署迁移工作流必须在恢复服务前，以双向反连接和计数核对全部数据集锁行并在不一致时失败关闭。持续 readiness 检查在阶段 10B 接入部署健康门禁；在此之前，当前 `/api/health/ready` 不能被描述为已经验证数据库或锁行覆盖。
- 校验规则和字段映射使用版本化配置；亚马逊表头变化时新增适配版本，不改写历史批次。

普通删除采用软删除。原始文件不提供普通页面删除能力；若因合规必须删除，需要管理员执行独立流程并保留不可包含原文的删除审计记录。

当前草稿和终态写保护仍有一项明确的剩余风险：服务通过活动指针、状态和修订号条件阻止晚到写入，但持有迁移账号、数据库管理员账号，或任何能绕过服务直接执行相应写 SQL 的凭据，仍可能绕过这些服务层终态守卫。阶段 6 发布能力上线前，必须统一评估数据库级终态守卫，并把迁移、管理员、运行和人工运维凭据进一步隔离；在完成该决策前，不得把服务层校验描述为能防御高权限直接 SQL。

## 17. 测试与验收

目前 62 份 CSV 作为固定回归样本集。实施解析器前，先用独立参考脚本生成并由管理员确认一份只读 golden manifest；每个文件记录 SHA-256、报表类型、识别日期、表头顺序、原始行数、关键标识值集合、数值列合计、退货事件日集合和代表性长文本哈希。后续测试以该清单作为明确期望值，不能用待测解析器自行生成自己的期望结果。

验收至少覆盖：

1. 每份原始文件字节保持不变；每次解析尝试的行数、SKU、ASIN、订单号和长文本快照完整保留。
2. 解析基线中的金额、百分比、数量和日期转换准确且可对照对应解析尝试的源值。
3. 第 9.4 节列出的经营报告整数与金额列、退货数量列在源行与解析基线之间精确一致；人工修改后的合计等于版本基础快照合计加全部修改净变化。
4. 文件名日期能识别，用户也能在审核前选择或修改报告日期。
5. 修改任意一天的数据不会改变其他日期或其他报表类型。
6. 同一天同类型始终最多只有一个当前发布版本。
7. 草稿、失败批次和历史版本不出现在默认看板或查看人员查询中。
8. 发布、修订、跨日期移动和回滚后，当前版本指针与审计记录一致。
9. 管理员、数据管理员和查看人员的服务端权限符合本规格。
10. 两名用户同时创建活动草稿或修改同一草稿时，最多保留一个活动草稿且不会静默覆盖；晚到的编辑不能修改已经封存发布的版本。
11. 校验通过后再次编辑草稿会使校验失效，旧校验结果不能用于发布。
12. 对同一数据修订完成警告确认和必填备注后可以直接发布；确认动作不会使其校验循环失效，但任何后续数据编辑都会失效。
13. 来源日期存在其他活动草稿时跨日期移动被阻止；目标日期已有发布版本或活动草稿时必须执行明确的合并、替换或取消流程。
14. 跨日期事务在任意步骤注入失败时，来源和目标发布指针均保持原值；成功时两侧一次性生效。
15. 废弃草稿不能成为回滚目标，数据管理员不能执行强制重建他人草稿、跨日期移动或回滚。
16. 文件落盘后数据库提交失败会被租约保护并最终识别为未引用对象；孤儿对账不会移动仍在上传或提交中的对象；数据库引用文件缺失会阻断发布。
17. 带偏移和不带偏移的退货时间分别按版本化站点时区处理，结果不受宿主机或浏览器时区影响；修改报表统计时区会重算全部相关事件日。
18. Agent 不能直接访问 MySQL，也不能执行写入或发布。
19. MySQL、备份清单和原始文件能在干净环境中恢复，文件哈希一致。
20. 重新解析会创建新的不可变解析尝试，不覆盖旧源行快照；新尝试失败时当前成功尝试和草稿不受影响。
21. 普通应用账号更新或删除发布事件、审计事件、字段修改、行修改和问题审核事件时必须被数据库拒绝。
22. 两种命令缺少稳定 UUID `operation_token` 时都在服务入口被拒绝；token 在各自全局账本中只能归属一个批次和完整命令摘要。同 token 改变批次或任一摘要字段时拒绝，账本记录不可更新或删除。
23. 确认解析的开始事务或终态事务已经提交但响应丢失后，同一 token 和同一命令重试返回原 revision、attempt 与 baseline，且不会留下第二个确认修订、终态尝试或基线；活动批次和终态尝试的复合外键不能引用错配的 token、批次或摘要。
24. 允许执行的 `ChangeReportDateCommand` 只更新日期并新增一条结果为 `applied` 的审计；解析 `confirmation_revision`、解析尝试数、基线数、当前成功解析指针和当前生效报表类型均不变。日期事务提交确认丢失后，同 token 重试可从账本和审计恢复且不重复写入。
25. `processing`、`rejected` 或已被 `version_input_batches` 物化的批次不能直接修改日期；物化后的调整只能进入草稿日期迁移流程。
26. 普通运行账号对两张 operation token 账本只有 `SELECT` 和 `INSERT`；`UPDATE`、`DELETE` 被数据库拒绝。`0007` 降级遇到无法由 `0006` 表达的失败尝试类型时，在结构变更前拒绝。
27. 后继或跨日期草稿的基础快照保留前任当前值、`row_state` 和逻辑行身份，但不会复制前任追加式修改事件；前任修改仍可沿谱系查询。
28. 所有阶段 5 草稿写命令要求稳定 UUID；同 token、同命令返回首次冻结结果，改变命令或操作者时拒绝，token、result 和 disposition 账本不可更新或删除。
29. 阶段 5 草稿事务遇到 MySQL `1213` 或 `1205` 时只重试完整事务，首次失败后最多重试 3 次，即总尝试最多 4 次；达到上限或任一步骤失败时不留下部分草稿、指针或账本结果。

测试层次包括：

- 解析器和格式转换单元测试。
- 校验规则单元测试。
- 导入、编辑、发布和回滚集成测试。
- 权限与并发测试。
- 发布幂等、死锁重试、事务故障注入和 outbox 重试测试。
- 使用 62 份真实样本的端到端回归测试。
- 备份恢复演练。

## 18. 实施顺序建议

1. 使用独立参考脚本生成并人工确认 62 份样本的 golden manifest。
2. 建立 MySQL 数据模型、迁移和账号权限基础。
3. 实现原始文件存储、报表识别、不可变解析尝试和两类解析器。
4. 实现每日数据集、两阶段校验、草稿、修改记录和发布事务。
5. 实现数据日历与审核工作台。
6. 实现已发布数据查询和经营看板。
7. 实现服务器部署、备份和恢复流程。
8. 在稳定的数据接口上接入只读 Agent 工具。

该顺序确保 Agent 和看板只建立在经过人工确认、可版本化且可追溯的数据基础上。

## 19. P0 商品目录后继契约（2026-08-20）

本规格既有日报导入、审核和不可变发布语义保持不变。P0 在其旁建立不可变 `report_source_scopes`、`report_dataset_scope_assignments` 和 active Seller SKU match-key sidecar：每个历史及新增 dataset 必须在创建或回填事务中恰好绑定一个已确认 scope；不更新原始日报行，不允许客户端 `site_id`、Seller Account 或 Marketplace 覆盖服务端 `CurrentSiteContext`。未分配、多分配或规范化碰撞会阻断 P0 分析，但不篡改既有日报发布状态。

退货 publication 的 publish、rollback、跨日期 move 和 undo 必须统一采用“事务外构建 `return_event_fingerprint_v1` candidate-group checkpoint/delta → ready staging → 短事务双指针 CAS”。最终事务按站点退货同步行、dataset publication ID 升序、dedup pointer 的固定锁序，同时比较 proposed set digest、scope、publication revision、dedup revision、group revision 和 proposed version；成功时同时推进日报 current publication 与 ready dedup pointer，任一条件失败时二者都保持旧值。原始退货行、日报版本和历史 dedup snapshot 都不可更新；`building|failed|superseded` snapshot 不能进入正式 KPI。完整指纹字段、JCS、API/worker/retry/command recovery 和稳定错误码以 `2026-08-19-product-style-variant-analytics-foundation-design.md` 第 25 节为唯一 successor candidate。
