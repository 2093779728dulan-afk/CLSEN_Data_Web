# 商品主档商品卡与增量维护设计方案

> 状态：设计确认稿
>
> 日期：2026-09-02
>
> 面向对象：商品资料审核人员、运营人员、数据管理员、开发与运维人员

## 1. 背景

当前商品主档已经能够根据经营报告和退货报告生成款式、变体、Seller SKU
映射及来源证据候选，但仍存在以下问题：

- 审核界面以技术行和内部编号为中心，不符合业务人员按商品理解数据的方式。
- 同一个稳定 SKU 可能对应多个 Seller SKU，现有单行表达容易造成一对一误解。
- 新来源值、误报、草稿归属冲突和历史修正缺少完整治理规则。
- 候选生成曾因宽 JSON 行参与排序触发 MySQL 1038，并使前端长期停留在
  “正在生成目录候选”。
- 如果逐订单来源证据持续复制进导出 JSON，数据量增长后仍会造成数据库 I/O、
  Worker 内存和浏览器渲染压力。

本方案将商品主档改造成以“商品卡”为核心的长期身份管理模块，并明确数据来源、
增量更新、人工审核、历史修正和大数据量处理边界。

## 2. 目标与非目标

### 2.1 目标

- 一张商品卡代表一个稳定款式，卡内管理全部实际存在的稳定变体。
- 支持多个 Seller SKU 映射到同一个稳定 SKU。
- 所有候选都能追溯到经营报告、退货报告和不可变来源版本。
- 已完善字段不会被后续报告静默覆盖。
- 新值、冲突和误报进入明确、可收敛的审核流程。
- 历史映射修正具有明确生效日期、查询口径和影响预览。
- 候选生成、在线审核和来源证据浏览能够随数据量增长而稳定扩展。

### 2.2 非目标

- 不根据观察到的颜色和尺码生成颜色×尺码笛卡尔积。
- 不将经营报告或退货报告视为无需审核的商品真相。
- 不在本阶段建设图片资产管理、完整 PIM、ERP 或自动上架系统。
- 不在第一阶段引入重型前端组件框架或动画框架。
- 不修改已经批准的历史目录版本。

## 3. 核心概念与层级

```text
商品卡（稳定款式 style_id）
  ├─ 稳定变体（稳定 sku_id、颜色、尺码）
  │    ├─ Seller SKU 别名 1
  │    ├─ Seller SKU 别名 2
  │    └─ 来源证据摘要与明细
  ├─ 稳定变体
  └─ 待处理候选、冲突与排除项
```

### 3.1 商品卡

商品卡使用稳定 `style_id` 标识，对审核人员主要显示：

- 款号
- 标准商品名称
- 状态
- 稳定变体数
- Seller SKU 数
- 首次出现和最近出现日期
- 待处理项和高风险冲突数量
- 来源完整度

款号是业务识别字段，不代替内部稳定 ID。款号纠正不会导致历史身份丢失。

### 3.2 稳定变体

稳定变体使用稳定 `sku_id` 标识，包含：

- 内部展示 SKU
- 标准颜色
- 标准尺码
- 启用状态
- 关联 Seller SKU 数量
- 来源证据摘要

系统只创建实际观察且经审核确认的变体。

### 3.3 Seller SKU 别名

Seller SKU 是外部销售系统中的标识，不等同于内部稳定 SKU。同一个稳定 SKU
可以关联多个历史或渠道 Seller SKU，即允许 `N:1`：

```text
2301-Black-M-OLD ─┐
2301-Black-M-NEW ─┼─> 稳定 SKU #501（2301 / 黑色 / M）
US-2301-BLK-M ────┘
```

稳定变体在主列表中只显示一行。其下提供“关联 Seller SKU”折叠区，展示所有别名、
账号、站点、Marketplace、首次/最近出现时间和映射状态。

## 4. 身份作用域与全局归属

Seller SKU 的身份键必须是：

```text
site + Seller Account + Marketplace + normalized Seller SKU
```

不能只用 Seller SKU 文本全局判断，因为不同站点或账号可能合法复用同一字符串。

### 4.1 唯一归属声明

同一作用域 Seller SKU 在任何时间只能拥有一个有效归属声明：

- 正式映射到已启用商品卡；或
- 被一个草稿商品卡预占；或
- 被明确排除。

数据库必须通过唯一约束或等价的串行化写入机制保证该规则，不能只依赖前端检查。

### 4.2 草稿与已启用卡冲突

如果 Seller SKU 已被草稿卡 `2302` 预占，随后又在已启用卡 `2301` 的来源中出现：

- 生成一条统一的“Seller SKU 归属冲突”；
- 冲突记录同时引用两张卡和全部来源；
- 不在两张卡中分别创建两个普通候选；
- 冲突解决前不允许建立第二个归属；
- 草稿撤回、拒绝或过期后释放预占声明。

## 5. 商品卡界面

### 5.1 默认商品卡视图

商品主档默认使用卡片列表，支持：

- 搜索款号、标准名称、内部 SKU、Seller SKU、ASIN 或 FNSKU；
- 按状态、来源、账号、Marketplace、冲突风险和更新时间筛选；
- 仅看待处理；
- 商品卡展开/收起；
- 批量选择和批量审核入口；
- 在商品卡视图与批量表格视图之间切换。

卡片只展示决策所需摘要，不一次渲染全部变体和来源明细。

### 5.2 商品卡详情

详情由四个区域组成：

1. 基础信息：款号、名称、状态和版本。
2. 稳定变体：颜色、尺码、内部 SKU 和关联 Seller SKU 折叠列表。
3. 待处理项：新变体、新 Seller SKU、冲突和低置信度候选。
4. 来源证据：经营/退货来源摘要、代表样本和按需加载的完整明细。

空白标准字段提供带来源标记的下拉候选：

- 经营报告候选；
- 退货报告候选；
- 已有主档候选；
- 手动输入。

选择来源候选仍属于人工确认，界面必须记录选择者、时间和来源。

### 5.3 动画与视觉原则

当前继续使用 React、TypeScript 和项目自有 CSS。React 已覆盖现有路由、状态和测试，
更换前端框架会增加迁移成本，却不能解决身份治理和 Worker 数据问题。

本阶段只使用轻量、可关闭的交互动效：

- 商品卡展开和折叠；
- 状态变更过渡；
- 新候选进入时的短暂提示；
- 审核完成后的局部反馈；
- 尊重 `prefers-reduced-motion`。

当页面出现复杂编排、共享时间线或大量手势动画后，再评估引入 Motion 类动画库。
不为了动画预先更换 React，也不在数据结构稳定前引入大型 UI 组件框架。

## 6. 来源证据与可信度

### 6.1 来源类型

系统当前认可：

- 经营报告；
- 退货报告；
- 已批准商品主档；
- 获授权人员的手动修正。

来源报告用于提出候选和证明出现事实，不自动决定标准名称、标准颜色、标准尺码或最终
归属。

### 6.2 可追溯定位

每条来源观察使用以下不可变定位：

```text
report_source_scope_id
+ dataset_id
+ published_version_id
+ source_row_id
```

同时记录报告类型、报告日期、事件日期、Seller SKU、必要的 ASIN/FNSKU 引用和摘要值。
原始报告版本在其保留期内不可变。

### 6.3 摘要与样本

商品卡默认展示：

- 首次出现日期；
- 最近出现日期；
- 出现次数；
- 来源报告数量；
- 标题、ASIN、FNSKU 去重数量；
- 最近标题；
- 证据集合 digest；
- 3～10 条代表样本。

完整明细仅在用户展开时分页加载。

## 7. 增量更新规则

每次上传并发布新的经营报告或退货报告后，系统执行增量检测：

| 情况 | 系统行为 |
|---|---|
| 已知 Seller SKU 且映射一致 | 只更新来源统计和最近出现时间 |
| 已知商品卡出现新 Seller SKU | 创建待审核别名候选 |
| 已知商品卡出现新颜色或尺码组合 | 创建待审核稳定变体候选 |
| 出现新款号 | 创建草稿商品卡 |
| Seller SKU 已被其他卡预占或映射 | 创建一条统一高风险归属冲突 |
| 报告内容重复 | 按来源版本和行级 digest 去重 |
| 来源值与已完善标准字段不同 | 保留标准字段，记录差异证据 |

自动更新不得覆盖以下人工确认字段：

- 标准商品名称；
- 标准颜色；
- 标准尺码；
- 内部展示 SKU；
- 已批准 Seller SKU 归属；
- 人工排除决定。

## 8. 永久忽略与恢复审核

审核人员可以对误报候选执行“永久忽略该来源值”，并必须填写原因。

排除作用域为：

```text
site + Seller Account + Marketplace + normalized Seller SKU
```

排除后：

- 后续报告仍更新其出现次数和来源证据；
- 不再重复创建待更新提醒；
- 不阻塞商品卡完成状态；
- 只有“恢复审核”或管理员撤销排除才能重新进入候选队列；
- 置信度变化只能生成“建议复核”，不能静默撤销人工排除。

排除记录必须包含原因、操作者、时间、来源范围和版本。

## 9. 生命周期与状态

### 9.1 商品卡状态

- `draft`：新建草稿，尚未批准。
- `needs_update`：已启用卡存在待确认增量。
- `enabled`：当前有效且无阻塞项。
- `disabled`：停止用于新归集，但保留历史。
- `superseded`：由明确的新身份替代。

### 9.2 候选状态

- `pending`：待审核。
- `accepted`：已接受并进入新目录版本。
- `excluded`：永久忽略或业务排除。
- `conflicted`：存在唯一归属冲突。
- `superseded`：被更新候选替代。

状态转换必须有审计事件，前端不能通过隐藏行代替业务状态。

## 10. 版本、修正与历史查询

### 10.1 不可变版本

已批准目录版本不可原地修改。每次批准、归属转移、字段修正或排除撤销都创建向前版本。

### 10.2 修正生效时间

映射修正必须提供 `effective_date`，并选择：

- 仅向前生效：从指定日期起使用新映射；
- 追溯修正：从 Seller SKU 首次出现日或管理员指定日期重新归集。

追溯修正属于管理员高风险操作。提交前必须展示受影响的日期、订单/退货数量、报表范围、
商品卡和已结账期间。

### 10.3 查询口径

所有依赖商品主档的分析查询必须显式选择以下口径之一：

- 按当时版本重放：保持历史报表当时看到的结果；
- 按最新修正重述：使用当前有效映射重新计算历史；
- 已结账冻结口径：结账后的期间不受普通追溯修正影响。

报表导出必须显示所用目录版本、修正口径和数据截止时间。

## 11. 候选生成与大数据量架构

### 11.1 强制边界

任何单个 MySQL JSON 字段都不得随订单行数或来源观察行数无界增长。MySQL 负责状态、
关系、索引和摘要；大体积不可变明细留在来源事实表或压缩对象制品中。

### 11.2 当前兼容修复

当前代码采用以下修复：

- 队列发现只查询待处理 `export_id`，不让候选和证据 JSON 参与排序；
- 再按主键读取该导出的候选数据；
- 历史证据 JSON 只提取 `summaries`，不向 Worker 或 API 传输 `observations`；
- 新导出 JSON 只写 Seller SKU 证据摘要；
- 完整逐行证据继续保存在 `catalog_source_evidence`，通过不可变来源定位追溯。

因此，一个变体关联 1,000 个订单时，导出负载只增加聚合计数，不再复制 1,000 个
观察对象。

### 11.3 目标存储模型

当候选数量继续增长时，将候选 JSON 进一步拆分为：

- `catalog_export_styles`
- `catalog_export_variants`
- `catalog_export_mappings`
- `catalog_export_exclusions`
- `catalog_export_exceptions`
- `catalog_export_evidence_summaries`

每张表使用 `export_id + id` 游标分页，不使用大偏移量分页。

只有在法规或独立审计要求“快照脱离原始事实表仍可完整重放”时，才将全部证据写入
对象存储。建议格式为 Parquet + Zstandard；每块 8～32 MiB，MySQL 只保存块编号、
storage key、行数、压缩大小、首末游标和 SHA-256。

### 11.4 Worker 处理模型

目标 Worker 流程：

1. 原子领取一个轻量 `export_id`。
2. 写入领取时间、attempt 和租约。
3. 按游标分批读取候选和摘要。
4. 使用常量内存模式生成 XLSX。
5. 定期写入阶段、已处理行数和心跳。
6. 临时错误按指数退避重试。
7. 达到最大次数后进入 `failed`，保存安全错误码。
8. 管理员可以人工重试，重试创建新的 attempt，不篡改历史错误。

前端不得无限显示单一 spinner。状态至少区分排队、处理中、重试等待、失败、容量超限、
完成和被新任务替代，并显示最后心跳及可操作的恢复入口。

## 12. API 与分页

列表接口只返回商品卡摘要，并使用稳定游标。详情按层级加载：

```text
GET /catalog/cards
GET /catalog/cards/{style_id}
GET /catalog/cards/{style_id}/variants
GET /catalog/variants/{sku_id}/seller-skus
GET /catalog/variants/{sku_id}/evidence
```

来源明细默认每页 50 条，最大 200 条。排序必须使用已索引的稳定键，不允许为了展示
一次加载整份证据集合到应用内存或浏览器。

## 13. 权限与审计

### 13.1 建议角色

- 查看者：读取商品卡和安全来源摘要。
- 审核人员：接受候选、排除候选和完善标准字段。
- 目录管理员：解决归属冲突、转移 Seller SKU 和禁用商品卡。
- 系统管理员：执行追溯修正、撤销永久排除和人工重试失败任务。

### 13.2 必须审计的操作

- 商品卡创建、启用、禁用和替代；
- 变体创建与字段修改；
- Seller SKU 预占、映射、转移和释放；
- 候选接受、永久忽略和恢复审核；
- 有效日期修正和历史重述；
- Worker 人工重试和失败处置。

审计载荷只保存安全摘要和 digest，不将敏感原文写入普通日志。

## 14. 技术选型说明

### 14.1 保留当前框架

- 前端继续使用 React 19、TypeScript、Vite 和 React Router。
- 后端继续使用 FastAPI、Pydantic、SQLAlchemy 和 MySQL。
- 异步生成继续使用独立 Worker 与现有本地内容存储抽象。

原因是当前问题来自数据边界、身份治理和任务可靠性，而不是框架缺少页面或动画能力。
这些技术已经具备路由、组件状态、类型校验、数据库事务、后台任务和自动测试基础。

### 14.2 暂不选择的方案

| 方案 | 优点 | 当前不选择的原因 |
|---|---|---|
| 更换 Vue/Svelte 等前端框架 | 某些场景语法更轻 | 需要重写现有页面和测试，不能直接解决目录身份与数据膨胀 |
| 立即引入大型 UI 组件库 | 快速获得复杂表格组件 | 容易改变现有视觉语言并增加包体，商品卡交互尚未稳定 |
| 将所有证据放进 MySQL JSON | 实现简单、单行读取 | 无界放大、更新放大、I/O 和内存峰值明显 |
| 将全部证据都放对象存储 | 压缩率高、适合冷数据 | 小规模查询和关系过滤不便，应只用于必须独立冻结的大明细 |
| 只调大 MySQL sort buffer | 短期可能绕过 1038 | 会放大每连接内存，不能消除宽行排序与大 JSON 根因 |

`schema fail-fast`、Worker 监控和重试机制不是替代 React 或 FastAPI 的“新框架”，而是
围绕现有框架增加的可靠性边界。

## 15. 分阶段实施

### 阶段 A：恢复可用性与阻止继续膨胀

- 队列窄查询和按 ID 加载。
- 导出证据 JSON 只保留摘要。
- 历史大 JSON 读取时只提取摘要。
- Worker 错误不再导致前端无期限无信息等待。
- 对当前 7 月数据完成真实候选生成验证。

### 阶段 B：商品卡业务闭环

- 商品卡和稳定变体界面。
- 关联 Seller SKU 折叠列表。
- 全局归属声明和草稿预占。
- 永久忽略、恢复审核和统一冲突队列。
- 商品卡/表格双视图与来源候选下拉框。

### 阶段 C：版本修正与规模化

- `effective_date` 和三种历史查询口径。
- 追溯影响预览与结账冻结。
- 候选子表化、游标分页和流式 XLSX。
- Worker 租约、心跳、退避、最大重试和人工恢复。
- 必要时增加压缩证据块对象存储。

## 16. 验收标准

### 16.1 业务验收

- 一张款号卡可以显示全部实际变体。
- 一个稳定变体可以折叠查看多个 Seller SKU。
- 同一作用域 Seller SKU 不会同时归属于两张卡。
- 永久忽略后相同来源值不会反复制造待更新提醒。
- 已完善字段不会被后续报告自动覆盖。
- 每个候选都能查看来源摘要并追溯到原始发布版本和行。
- 历史修正必须明确生效日期和查询口径。

### 16.2 性能验收

- 队列发现 SQL 不选择候选或证据 JSON。
- 导出证据 JSON 大小与订单/观察行数不再线性增长。
- 商品卡、变体、Seller SKU 和证据明细均支持分页或按需加载。
- Worker 峰值内存由单批大小决定，不由全部数据量决定。
- MySQL 1038 不再使任务无限停留在 `building`。
- 失败任务具备错误码、最后心跳、重试次数和人工恢复路径。

### 16.3 安全与一致性验收

- 所有归属唯一性由数据库事务保障。
- 已批准版本不可修改。
- 追溯修正有管理员权限、影响预览和审计事件。
- 普通 JSON、日志和页面不泄露订单号、客户留言或其他非必要敏感字段。

## 17. 仍需在实施计划中拆分的工作

本文件定义目标设计和约束，不把所有目标误标为已完成。后续实施计划需要分别拆分：

- Worker 状态、租约和重试数据模型；
- 商品卡、稳定变体、别名和归属声明迁移；
- 永久排除与冲突工作流；
- `effective_date` 与历史重述查询；
- 候选子表化和流式工作簿；
- 商品卡 UI、动效、无障碍和大数据量性能测试。

每一阶段都必须具备迁移、回滚策略、自动化测试、Docker 真实链路验证和业务验收样例。
