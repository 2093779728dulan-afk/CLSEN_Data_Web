## 1. 执行摘要

当前项目不需要更换 React、Vite、FastAPI、SQLAlchemy、MySQL、Alembic 或 Python Worker。它们已经承载了日报导入、审核发布、商品目录、版本审计和后台任务等核心能力，也与约 20 名内部用户、单体部署和数据库事务密集型业务相匹配。现在最需要解决的不是“框架落后”，而是运行安全、后台任务可见性、UI 工程化和模块边界没有随着功能增长同步增强。

schema fail-fast 与 Worker 监控不是替代 React 或 FastAPI 的新框架：

- schema fail-fast 是所有真实 API、Worker 入口共享的启动安全策略。代码期望的 Alembic head 与数据库实际版本不一致时，进程必须在提供服务或领取任务前退出，且绝不自动迁移。
- Worker 监控是建立在现有数据库队列、进程心跳、结构化日志和管理员状态页之上的可观测能力。它不要求 Redis、RabbitMQ、Prometheus 或 Grafana。
- UI 优化是在现有 React/Vite 应用上增加设计 Token、无障碍基础组件、局部样式、组件文档、视觉回归、功能性动画和标准图表，不做全站一次性重写。

路线图分为六个严格有序的阶段：

| 阶段 | 主题 | 阶段结果 |
| --- | --- | --- |
| 0 | 基线、指标和变更边界 | 冻结可复现的安全、性能、页面和队列基线 |
| 1 | 全环境 schema fail-fast | API 与 Worker 在不兼容 schema 上均拒绝启动 |
| 2 | Worker 可观测性 | 数据库心跳、四类队列指标、结构化日志和管理员状态页形成闭环 |
| 3 | UI 工程基础 | Token、基础组件、Radix UI、Lucide、CSS Modules、Storybook 和视觉回归可用 |
| 4 | 全页面渐进迁移 | 全部页面逐批迁移，并规范使用 Motion 与 ECharts |
| 5 | 模块边界和性能 | 按真实证据拆分大型组件与 Repository，并消除已确认的性能瓶颈 |

阶段 0～2 优先降低“代码与数据库不兼容仍然运行”和“后台任务失败但无人看见”的运行风险；阶段 3～4 提升界面质量、可扩展性、无障碍和动画表达；阶段 5 最后根据前四阶段获得的测试与性能证据重构内部边界，避免先拆文件、后发现拆错职责。

3～6 个月只是管理视野，不是工期承诺。每个阶段只有在验证门禁通过并附上完成证据后，才能进入 complete。阶段持续时间由范围和验收结果决定，不以日历日期强行推进。

## 2. 当前基线

### 2.1 产品和运行基线

本项目是面向小规模内部用户的数据审核与可视化系统。当前核心能力包括：

- 日报文件导入、解析、人工审核、发布、版本修订与回滚；
- 批量审核的服务端权威状态、幂等操作和浏览器限流执行；
- 已发布数据看板、日期工作台、版本历史和明细账；
- 商品目录导入、导出、版本、未匹配处理和退货去重；
- 本地备份、隔离恢复验证、数据库维护写屏障；
- 基于 MySQL 行锁、租约和重试状态的本地 Python Worker。

当前正式技术栈为：

| 层级 | 当前选择 | 保留原因 |
| --- | --- | --- |
| 前端 | React 19、TypeScript、Vite、React Router | 已形成大量业务组件和测试；客户端交互密集，公开 SEO 和服务端渲染不是当前需求 |
| API | FastAPI、Pydantic | 类型化 API、统一错误响应和 OpenAPI 客户端生成已经落地 |
| 数据访问 | 同步 SQLAlchemy 2 | 业务以短事务、锁顺序和一致性为核心；当前没有异步连接吞吐瓶颈证据 |
| 数据库 | MySQL 8.0/8.4 | 迁移、事务、备份、授权和兼容矩阵已经围绕 MySQL 建立 |
| 迁移 | Alembic | 当前唯一 head 为 0022，迁移历史和契约测试已存在 |
| 后台任务 | Python Worker + MySQL 持久状态 | 四类工作均以 MySQL 为权威来源，但领取、租约和重试能力各不相同；当前规模不需要额外消息中间件 |

### 2.2 已有优势

- 核心写操作普遍采用服务端权威状态、事务、幂等键和并发冲突检测。
- API 已有 JSON 结构化请求日志、请求 ID 和统一错误模型。
- 后端已有 Ruff、mypy、pytest、MySQL 集成测试和迁移契约；前端已有 ESLint、TypeScript、Vitest、Playwright 和生成式 OpenAPI 客户端。
- MySQL 8.0/8.4 兼容矩阵、备份恢复和本地运维脚本已经形成较强的安全基础。
- 商品主档已有固定 400 万行夹具、预热、采样和 p95 预算；阶段 0 复用这项窄范围证据，不重写它，也不把它外推为全系统性能结论。
- 蓝白视觉系统已有初步 Token 和基础样式，不需要从零建立品牌方向。
- 最近的批量审核与发布恢复修复已经补强事务边界，可作为后续回归基线，而不是在本路线图中重写业务状态机。

### 2.3 当前缺口

截至基线提交，主要缺口为：

1. schema 版本来源已经集中在 backend/app/maintenance/schema_revision.py，备份写入和部分管理命令也会检查当前 head；但直接启动 FastAPI、开发服务器或 Worker 时，没有一个所有真实入口共同执行的 fail-fast 门。FastAPI readiness 在尚未创建数据库 Engine 时还可能只报告应用进程就绪。旧代码可能连接新 schema，新代码也可能连接旧 schema。
2. 当前 Docker Compose 的 backend 和 worker 依赖一次性 migrate 服务，该服务会执行 Alembic upgrade head。也就是说，一次普通的组合启动可能隐式迁移数据库，与本路线图已经批准的“迁移必须是独立、显式运维动作”不一致。
3. WorkerRunner 实际轮询四类工作：return_dedup、publication_outbox、catalog_export 和 catalog_import。管理员接口 GET /api/admin/maintenance 目前只汇总 publication outbox，没有其他三类队列，也没有 Worker 进程心跳。
4. 四类队列的状态协议不同。publication_outbox 有 pending/processing/completed/failed 和重试时间；return_dedup 有 building/ready/failed/superseded 及租约；catalog_import 有 uploaded/parsing 和解析租约，但过期 parsing 目前不能由普通轮询直接恢复；catalog_export 只有 building/ready/failed，尚无 claim/lease，不能可靠区分等待与正在执行。
5. Worker 的队列异常能够写普通日志并继续下一类队列，但 Worker 入口没有配置 API 已有的 JSON 日志基础，日志也缺少统一的事件名、Worker 实例、队列、耗时、结果和错误码字段。管理员无法从 UI 判断进程离线、维护暂停、队列暂时为空还是队列已经停滞。
6. 批量审核第一版仍由打开任务页的浏览器领取 queued 项目。该模型有自己的持久状态和恢复契约，但不是当前四类 Worker 队列；阶段 2 不会把它静默改造成后台 Worker。
7. frontend/src/styles.css 约 3474 行，而 frontend/src/design-system/tokens.css 约 54 行、primitives.css 约 265 行。全局样式承担了过多页面职责，组件隔离和视觉回归不足。Radix UI、Lucide、Motion、ECharts 与 Storybook 当前未安装；源码尚未采用 CSS Modules；axe 和截图基线尚未形成门禁。
8. VersionHistory.tsx 约 1301 行，DraftReviewGate.tsx 约 1015 行；大型组件混合了数据加载、命令、状态编排和展示，但目前不能只凭行数决定如何拆分。
9. 后端 publications/repository.py、datasets/repository.py、review/repository.py 和 catalog/return_dedup_repository.py 分别约 3915、3226、2609 和 2322 行。它们同时承载查询、命令、锁和映射逻辑，维护成本已经上升，但事务边界不能被机械拆散。
10. 除商品主档的专用性能 harness 外，当前缺少统一的页面清单、交互性能基线、队列等待基线和项目级固定环境对照。因此不能诚实声明全系统的绝对 p95 目标，也不能证明一次重构没有重复性退化。

以上数字只描述当前复杂度，不是重构验收阈值。文件变短不等于职责更清晰，文件较长也不自动构成缺陷。

### 2.5 为什么保留当前核心框架

#### React + Vite

React 适合当前大量状态化表格、审核工作台、路由内交互和可组合组件。Vite 提供快速本地构建，当前系统不依赖服务端渲染、公开搜索收录或边缘渲染。

保留 React 的代价是仍需治理复杂状态、重渲染、bundle 和大型组件；Vite 也不提供 Next.js 那类服务端渲染和全栈约定。Next.js 的优势是 SSR、服务端组件、文件路由和公开内容交付，但当前会新增 Node 服务运行时、缓存与数据获取语义，却不能直接解决数据库兼容、Worker 可见性或全局 CSS。Vue 和 Svelte 的模板/响应式模型更简洁、Svelte 还能减少部分运行时代码；Angular 提供完整强约束框架，但三者都要求重写现有页面、测试和路由。只有公开 SEO/SSR 或团队组织发生实质变化时才重评，当前迁移风险远大于收益。

#### FastAPI + Pydantic

FastAPI 已经提供依赖注入、类型模型、统一 API 契约和 OpenAPI 生成，适合当前 Python 数据处理能力。保留它能直接复用现有认证、权限、错误响应和测试。

FastAPI/Python 的代价是 CPU 密集吞吐和多进程资源效率不如 Go/Rust，框架也不会替项目解决事务与部署治理。Django 的优势是 ORM、管理后台和 batteries-included 约定，但项目已经拥有 SQLAlchemy、Alembic 和自定义事务模型，引入它会产生双重基础设施或大规模重写。Flask 更轻、更自由，但需要重新组装当前已有的类型、验证和 OpenAPI 能力。NestJS 适合统一 TypeScript 全栈团队；Go/Rust 适合经证实的高吞吐或低延迟服务。当前没有这类瓶颈证据，跨语言重写会把主要风险转成业务回归。

#### 同步 SQLAlchemy + MySQL + Alembic

当前业务首先要求事务正确、锁顺序稳定、迁移可审计和备份可恢复。同步 SQLAlchemy 更容易保持现有事务语义，也与约 20 名内部用户的并发规模相符。

同步 SQLAlchemy 的代价是每个阻塞数据库调用占用执行线程，在高并发 I/O 下扩展性不如完整异步链路；MySQL 也没有 PostgreSQL 的部分高级类型与扩展生态。异步 SQLAlchemy 的优势是大量并发等待场景的连接利用率，但只有完整调用链异步化且测量证实瓶颈时才有收益。PostgreSQL 的优势包括更丰富的数据类型、扩展和查询特性，但当前 MySQL 8.0/8.4 的 schema、权限、备份、恢复和集成测试成本已经投入，也没有 MySQL 无法满足的已批准需求。

#### 数据库队列 + Python Worker

现有四类工作均以 MySQL 持久状态为权威；publication_outbox、return_dedup 和 catalog_import 分别拥有不同程度的锁、租约或恢复语义，catalog_export 当前只有 building/ready/failed，不能泛化为统一队列协议。对于当前单机或少量进程规模，数据库仍是足够可靠的任务协调点。

数据库轮询的代价是共享业务数据库负载、状态协议不统一、路由和高吞吐能力有限。Celery/RQ 配合 Redis 或 RabbitMQ 的优势是成熟调度、独立扩缩容、路由和重试生态，但会增加新的持久化语义、部署组件、消息确认、死信处理和恢复手册。只有阶段 0/2 证据持续显示数据库工作源无法达到冻结等待预算，或出现跨主机高吞吐和事件广播需求时，才重新评估消息中间件。

### 2.6 UI 工程选型及替代方案

UI 改进采用“保留 React，增加薄而可替换的工程层”：

| 选择 | 优点 | 采用代价 | 替代方案的优势与暂不采用原因 |
| --- | --- | --- | --- |
| 现有设计 Token | 延续已批准的蓝白语义，能渐进统一颜色、排版、间距、动效和图表 | 需要治理流程、静态检查和例外清单，不能只靠变量文件自动统一页面 | 新建主题可摆脱历史命名，但会形成双重语义和迁移歧义，因此不采用 |
| CSS Modules | Vite 原生支持、无额外运行时、类名局部化，能与旧 CSS 渐进共存 | 迁移仍要修改 import/className，动态变体和 Token 纪律需要自行设计 | Tailwind 可渐进采用且工具生态成熟；CSS-in-JS 擅长动态主题，部分实现无运行时。但两者都会引入第二种样式范式，当前先收敛现有 CSS |
| Radix UI | 无样式、复合控件焦点和键盘基础较好，不强迫改变视觉语言 | 需要自行组合、样式化和测试；按原语拆包也增加依赖治理 | Ant Design/Material UI 的完整表单、表格和主题能更快铺页面，但默认视觉、覆盖成本和 bundle 约束较重 |
| Lucide React | 描边风格统一、按图标导入、容易与 Token 对齐 | 仍需逐个审查语义、可访问名称和 bundle，图标不能替代文字 | 成熟综合图标库覆盖更广，自制 SVG 控制更强；当前更看重一致性和维护成本 |
| Storybook | 隔离展示组件状态、交互和评审，适合长中文和权限矩阵 | 配置、故事和生产组件可能漂移，需要 CI 和所有权维护 | 应用内组件画廊更轻，但隔离、插件和视觉评审能力弱；当前共享组件规模值得使用 Storybook |
| Playwright 视觉回归 | 复用现有浏览器测试，基线留在仓库并绑定提交 | 对 OS、字体和浏览器敏感，基线评审需要纪律 | Chromatic 等托管平台有更好的评审 UI 和跨环境能力，但增加外部服务、费用和数据边界，当前不需要 |
| Motion | 适合复杂进入/退出、布局连续性和统一 reduced-motion | 增加 bundle 与运行时成本，滥用会影响性能和可访问性 | 简单过渡优先原生 CSS；只有 CSS 难以表达的状态/布局关系才使用 Motion |
| ECharts | 运营趋势、比较、多系列和交互能力完整，已有总体设计方向 | bundle 较大，canvas/SVG 无障碍和 Number 精度需额外设计 | D3 自由度更高但实现成本高；现有自制 SVG 对简单、精确和可访问图表更合适，ECharts 未通过门禁时保留 SVG |

Motion 只用于状态反馈、展开收起、列表变更和页面区域之间的空间关系，不改变蓝白视觉系统的克制原则。ECharts 是规范并扩大使用范围，不是推翻已有展示方式的全站重写。

如果未来出现公开页面 SEO、独立前端服务端渲染、多团队独立部署、数据库队列持续突破容量预算或 Python API 经优化后仍被确认是瓶颈，应另开架构决策记录重新比较框架。路线图不提前为这些尚未发生的情形付出迁移成本。

## 3. 指导原则与非目标

### 3.1 指导原则

1. 安全门先于体验升级。schema 不兼容和后台进程不可见会影响数据正确性，必须先于大规模 UI 迁移解决。
2. 数据库是运行状态的权威来源。管理员页面不从浏览器缓存或某个 API 进程内存推断 Worker 和队列状态。
3. 失败必须可见且默认关闭。schema 无法读取、缺失、过旧、过新或存在多个 head 都视为不兼容；监控查询无法得到可靠结果时显示 unknown，不显示健康。
4. 迁移必须显式。API 和 Worker 永远不得在启动时运行 Alembic upgrade、downgrade 或创建表。
5. 逐页迁移且始终可用。旧样式兼容层在对应页面验收前保留，每个页面批次都能独立回退。
6. 无障碍与 reduced-motion 是完成条件，不是最后补丁。状态不能只靠颜色或动画表达。
7. 先测量再优化。绝对性能预算由阶段 0 在固定环境中测量并冻结，后续不得用主观“更快”代替证据。
8. 保持业务契约。优化不改变日报、审核、发布、权限、幂等、版本或商品目录的权威语义。
9. 以边界和可验证性评价重构。不得以文件行数、组件数量或 Repository 数量作为成功指标。
10. 每个阶段形成小范围、可审查、可回退的提交和证据，不把六个阶段合成一次大改。

### 3.2 非目标

本路线图明确不做：

- 不更换 React、Vite、FastAPI、SQLAlchemy、MySQL 或 Alembic；
- 不把单体拆成微服务，不引入 Kubernetes；
- 不引入 Redis、RabbitMQ、Celery、RQ 或新的分布式调度系统；
- 不把同步 SQLAlchemy 全面改为异步；
- 不自动迁移任何真实运行数据库；
- 不允许 schema 不兼容时提供只读降级 API 或继续领取 Worker 任务；
- 不在阶段 2 把批量审核浏览器执行器迁移成 Worker；
- 不在阶段 2 引入 Prometheus、Grafana、外部告警平台或值班系统；
- 不用 Ant Design、Material UI 或 Tailwind 一次性替换现有视觉系统；
- 不一次性重写全部页面，不在 UI 迁移中改变业务流程；
- 不为了减少行数机械拆分组件或 Repository；
- 不把 3～6 个月解释为未经评估的交付日期。

数据丢失、安全漏洞或生产阻断类紧急修复可以独立于路线图阶段处理，但仍必须保留最小回归测试、影响说明和回退证据。

### 4.2 schema fail-fast

#### 统一版本来源

backend/app/maintenance/schema_revision.py 中的 CURRENT_SCHEMA_REVISION 继续是代码期望 schema head 的唯一运行时来源。Alembic heads 契约必须证明仓库只有一个 head，且它与该常量一致。备份读取历史版本的兼容集合是独立政策，不得被误用为 API 或 Worker 的运行兼容窗口。

本阶段检查的是“代码声明的 revision policy 与 alembic_version 是否精确匹配”，不是完整结构指纹、权限审计或迁移后数据 canary。当前单 head 运行集合只有 CURRENT_SCHEMA_REVISION；未来若引入发布 manifest 或结构指纹，必须通过独立批准的设计扩展检查器，不能用字符串大小比较 revision，也不能夸大本门禁能够发现所有手工结构漂移。

#### 真实入口定义

任何会连接实际应用数据库并提供业务响应、管理响应或领取后台任务的进程，都是“真实运行入口”，包括：

- 本地开发和演示脚本启动的 FastAPI；
- 直接运行的 Uvicorn FastAPI 应用；
- 容器 api 角色；
- scripts/run-worker.ps1 启动的 Worker；
- 直接运行的 app.worker.cli；
- 容器 worker 角色；
- 后续新增的任何 API 或 Worker 启动包装器。

离线生成 OpenAPI、纯单元测试和显式注入假 Session/Engine 的应用工厂不是实际运行进程。它们使用不接触真实数据库的专用构造路径，不能依赖一个可在真实环境中随意关闭 fail-fast 的通用开关。

当前 Docker Compose 的隐式 migrate 依赖也在阶段 1 范围内移除。migrate 必须进入非默认 operations profile 或独立 Compose 文件；backend/worker 改为直接等待 mysql healthy 和 storage-init 完成，不能靠 migrate 间接提供启动顺序。普通 docker compose up、本地 API 启动和 Worker 启动都不得创建 migrate 容器或触发 upgrade head。专用 migrate 操作除 Alembic 外还要显式完成当前所需的凭据/最小授权同步，并只能由管理员按 runbook 独立调用。未来发布控制器只有在另行批准并获得一次明确发布操作授权后，才能把它作为独立、可审计步骤执行。

#### 检查语义

共享检查器提供进程前 preflight 和进程内防御两种接线。受支持的本地脚本与容器 entrypoint 在启动 Uvicorn 或 Worker 主循环前先运行 preflight；FastAPI lifespan 继续保护直接 Uvicorn 等绕过包装器的入口，Worker CLI 在任何 ready 文案、心跳或领取前再次检查。这样多 Worker Uvicorn 的父进程不会在受支持入口先绑定端口，直接 Uvicorn 即使由宿主短暂创建 socket 也永远不能完成 startup、返回成功响应或保持运行。检查器只读取数据库身份和 alembic_version：

- 实际版本精确等于 CURRENT_SCHEMA_REVISION 时通过；
- alembic_version 缺失、无行、多行、无法读取、版本较旧、版本较新或值未知时失败；
- 数据库连接或权限不足导致无法证明兼容时失败；
- 失败退出码非零，API 不进入 ready，Worker 不写业务状态也不领取任务；
- 失败日志包含稳定事件名、期望版本、实际版本或封闭错误码和不含凭据的数据库环境标识；
- 检查器不得执行 DDL、DML、Alembic 命令或自动重试迁移。

迁移顺序始终是：停止会访问数据库的旧进程，完成备份和显式 Alembic 迁移，验证 head，再启动与新 head 匹配的 API 和 Worker。启动失败时由运维人员修复代码/数据库配对，不能通过跳过门禁、手工修改 alembic_version 或让应用进程补跑迁移恢复服务。

### 4.3 Worker 心跳和四类队列指标

#### Worker 进程心跳

新增数据库持久化的 Worker 进程状态。每次进程启动生成不可复用的实例 ID，并记录：

- Worker 实例 ID、角色和支持的四类队列；
- 代码版本或构建标识；
- 启动时间、最后心跳时间和单调递增心跳序号；
- 每类消费者最近一次轮询开始、结束、成功和失败时间；
- 每类消费者连续失败次数和最后一个封闭 failure_code；
- 当前生命周期状态及最后一个内容无关的结果码；
- 不含主机用户名、数据库 URL、文件内容、订单号或客户数据的有限诊断字段。

心跳时间、状态计算时间和队列 observed_at 均使用 MySQL UTC_TIMESTAMP，不用 Worker 或浏览器主机时钟决定健康。阶段 0 冻结四个生效值：心跳间隔 H、stale 阈值 S、offline 阈值 O 和页面刷新上限 R；必须满足 S 不少于 3H、O 大于 S，崩溃在 O+R 内对页面可见。初始测量候选为 H=10 秒、S=30 秒、O=60 秒、R=15 秒，它不是未经验证的产品 SLO。阶段 0 必须根据数据库开销、备份写屏障和实际轮询波动批准或替换候选，并保存最终数值。API 返回实际生效值，测试只按已冻结值验收。

心跳调度独立于可能长时间运行的单个队列工作，使用独立短事务和连接，长任务不能阻塞正常心跳。Worker 只有在最近一个心跳周期内成功写入后才能领取新任务；连续心跳失败时停止领取并写入封闭错误日志，已经持有的任务仍按原有 lease、fencing 和事务契约安全完成或恢复，不能为了监控强行改写 processing 状态。恢复心跳后才能继续领取。

维护写屏障会阻止所有应用 DML，心跳也可能在受控备份期间无法写入。API 分开返回按年龄计算的 heartbeat_status 与当前 maintenance_active，绝不把两者合成一个看似确定的 online 或 suspended 状态。屏障活跃且心跳已 stale/offline 时，页面保留最后心跳年龄并说明“维护期间无法确认进程存活”；维护前已经离线的进程不会被改写为健康。屏障释放后必须等到真实新心跳才恢复 online。无法读取数据库时为 unknown。online 只表示该进程最近能够向数据库写入心跳，不表示四类消费者都在推进。

实例记录保留 30 天，清理由有界、可测试的维护操作执行，不能在一次请求中无上限删除。

#### 四类队列

监控范围精确对应当前 WorkerRunner：

| 队列标识 | 当前职责 |
| --- | --- |
| return_dedup | 退货去重暂存任务 |
| publication_outbox | 发布后续失效或重算事件 |
| catalog_export | 商品目录导出物化 |
| catalog_import | 商品目录导入处理 |

统一响应外壳包含 queue_name、health、observed_at、原生状态计数、最老相关时间和 capability 标记，但指标按各队列真实协议映射：

| 队列 | 可领取或未解决工作 | 可证明的处理中 | 重试/陈旧 | 失败 |
| --- | --- | --- | --- | --- |
| publication_outbox | pending 且 available_at 已到期 | processing 且锁未过期 | pending 且 available_at 在未来；另列过期 processing | failed |
| return_dedup | building 且无租约或租约已过期 | building 且租约有效 | 无独立计划重试；过期租约单列 stale | failed；ready/superseded 只作终态统计 |
| catalog_import | uploaded | parsing 且解析租约有效 | 过期 parsing 单列 stuck；当前普通轮询不能把它伪装成可领取 | parse_failed，并区分 recoverable |
| catalog_export | building 统一记为 unresolved_building | 当前无 claim/lease，字段为 null 且 capability=false | 当前无计划重试和陈旧判定，字段为 null | failed；ready 作终态统计 |

每类至少返回可可靠计算的工作数、失败数和最老工作时间。actionable、in_flight、retry_wait、stale、next_retry_at、last_succeeded_at 等不适用或当前无法证明的字段返回 null，并在 capabilities 中解释，绝不能用 0 冒充。阶段 2 不为了填满统一表而静默改变 catalog_export 的 claim/lease，或改变 catalog_import 的恢复状态机；若要补齐这些队列协议，必须作为单独设计的行为改造。

聚合查询在同一数据库观测窗口内产生 observed_at。某类队列无法可靠查询时，该类 health 为 unknown，并带封闭 failure_code；其他队列仍可展示。聚合 API 不读取 Worker 进程内存，不缓存一个可能掩盖离线的“最后健康”结果。

每类队列同时区分两种健康：

- query_health：管理员 API 此次是否成功读取并解释数据库权威状态；
- consumer_health：在线 Worker 是否持续成功执行该类消费者。

WorkerRunner 捕获单类异常并继续其他类的既有隔离行为保持不变，但每次调用前后必须持久记录 queue_name、last_poll_started_at、last_poll_completed_at、last_poll_succeeded_at、last_poll_failed_at、consecutive_failures 和封闭 failure_code。一个总体 heartbeat 为 online、某类连续失败的情况必须显示为“进程在线、该消费者失败”，不能显示为空闲健康。长任务保持 started 状态并由独立进程心跳证明进程可达；消费者记录不保存任务载荷或异常原文。

#### 结构化日志

扩展 API 已有的日志基础，使 Worker 每一行日志都是可解析 JSON。固定字段至少包含 timestamp、level、event、worker_instance_id、queue_name、outcome、duration_ms、attempt 和 failure_code。允许记录内部任务主键以便关联，但不得记录原始文件内容、来源标识原文、客户数据、凭据或完整异常输入。异常堆栈只进入受控服务端日志，不直接返回管理员页面。

#### 管理员状态页

现有“备份与任务”区域扩展为运行状态视图，至少显示：

- Worker 总体状态、最后心跳、构建标识和生效阈值，并说明 online 只代表数据库心跳；
- 四张队列卡片及该队列可证明的积压、处理中、重试、陈旧、失败和最老等待时间；不适用项显示“不适用”，不显示 0；
- 每类 query_health、consumer_health、最近成功/失败轮询、连续失败数和安全 failure_code；
- 数据库产生的 observed_at、页面最后刷新时间、自动刷新状态、heartbeat_status、maintenance_active 和 unknown/stale/offline 的明确说明；
- 备份、恢复、维护写屏障和现有 publication outbox 信息的兼容展示。

状态必须同时用文字、图标和颜色表达。管理响应继续只允许 admin，并发送 Cache-Control: private, no-store。阶段 2 先沿用现有蓝白样式完成能力，阶段 3～4 再把该页面迁移到共享组件。

### 4.4 UI 工程层

#### Token 层

扩展现有 Token，而不是创建第二套主题。Token 覆盖：

- 语义颜色：背景、表面、边框、正文、弱文本、主操作、成功、警告、错误、信息、焦点；
- 排版：字号、行高、字重、数字和表格对齐；
- 间距、圆角、阴影、层级和响应式断点；
- 动效时长、缓动和 reduced-motion；
- 图表系列、网格、轴线、阈值和选择状态。

业务组件不得直接创建未登记的品牌色或任意 z-index。确有新语义时先更新 Token 及其 Storybook 说明。

#### 基础组件和模式层

共享组件至少覆盖 Button、IconButton、Link、Input、Select、Checkbox、Radio、Dialog、Drawer、Popover、Tooltip、Tabs、Menu、Toast、Badge、Status、Skeleton、EmptyState、ErrorState、Table 基础结构、Pagination 和 FormField。Radix UI 只承担需要复杂焦点、键盘和弹层行为的交互原语；原生 HTML 能正确完成的控件继续优先使用原生语义。

高层模式覆盖页面标题、筛选工具栏、批量操作栏、指标卡、状态时间线、确认流程、错误恢复和数据表空/载入/失败状态。组件暴露稳定 props 和可访问名称，样式放入 CSS Modules，共享全局文件只保留 reset、根 Token、排版基础和迁移期兼容规则。

#### 页面视觉合同

“好看”不能只由实现者主观判断。每个路由迁移前必须形成一页视觉任务说明并随截图评审：

- 指明该角色进入页面的首要任务、最重要信息和完成反馈；
- 页面按“标题与上下文 → 关键状态/指标 → 主要工作区 → 次要历史/帮助”建立清晰层级；
- 每个视觉区域只设置一个主操作，次要操作降级，不让危险操作与主操作竞争；
- 数据密度由任务决定：审核/明细表保持高密度和稳定列对齐，概览页保留呼吸空间，不能用大面积卡片稀释关键数据；
- 分别定义 1280、768、390 像素宽下的网格、堆叠、表格滚动、工具栏和关键操作位置，不隐藏完成任务所需信息；
- 每个动画和图表写明它解释的状态/关系；没有明确理由时使用静态界面或表格；
- 正常、载入、空、错误、权限、长中文和高数据量状态使用同一信息层级，错误恢复操作保持可见；
- 前后截图由项目负责人按蓝白视觉原则、信息层级、密度、一致性和任务完成性批准。

#### Storybook 与视觉回归

每个共享组件必须有正常、hover/focus、禁用、载入、空、错误、长中文文本和窄屏等适用状态。Storybook 静态构建是 CI 门禁。Playwright 在固定浏览器、视口、字体和数据夹具上生成关键组件与页面截图；基线更新必须与设计变更同一评审，不允许用批量重录掩盖意外差异。

#### Motion

动画必须解释状态或空间变化：

- 微交互通常为 120～180 毫秒；
- 面板进入、退出或展开通常为 180～240 毫秒；
- 不设置超过 300 毫秒且阻止用户继续操作的过渡；
- 加载、成功、错误和队列状态不能只用动画表达；
- prefers-reduced-motion 下移除位移、缩放和非必要补间，仅保留立即切换或必要的短淡入；
- 不对大数据表逐行播放入场动画，不让动画改变审核命令的实际时序。

#### ECharts

ECharts 用于确实需要趋势、比较、分布或多维筛选的数据展示。每个图表必须：

- 使用图表 Token 和一致的数值、日期、货币格式；
- 原始 decimal 先保持为精确字符串/BigInt，只能在证明范围有界后归一化为 ECharts Number 坐标；tooltip、摘要和表格从原始精确值格式化，不能从浮点坐标反推业务值；
- null 数据保持断线，不能插值成 0 或跨缺口连线；
- 在图旁提供可读摘要，关键数据能够以表格或明细方式访问；
- 保留 role=img、可访问名称、title/desc，并用线型、点标记或文字提供非颜色识别；每日点矩阵或等价数据表仍可供键盘和屏幕阅读器访问；
- 有空、载入、错误、权限不足和窄屏状态；
- 按页面懒加载，避免让不使用图表的审核页面承担完整图表包；
- 键盘可访问的筛选控件位于图表外，不能把 canvas 交互作为唯一操作路径；
- 不用 3D、无意义渐变或连续动画装饰运营数据。

若某个图表不能同时通过精度、null-gap、无障碍和 bundle 门禁，保留或改进现有可访问 SVG，不为了统一库而降低正确性。

### 4.5 模块边界

阶段 5 的拆分遵循“一个单元一个清晰职责”：

- React 页面容器负责路由和用例编排，数据 Hook 负责请求生命周期，领域组件负责展示和交互，命令模块负责幂等写请求；
- Repository 查询、命令、映射和事务协调可以分离，但跨表原子操作仍由一个明确的事务协调器拥有；
- 对外 API、服务接口和事务不变量先由测试固定，再通过兼容 facade 或导出路径逐步切换；
- 只有能降低认知负担、隔离变化、改善测试或消除测得瓶颈的拆分才进入实施；
- 不规定“文件必须少于多少行”，也不以新增文件数量作为完成证据。

### 4.6 失败处理和回退原则

- schema 检查失败：进程退出，保持数据库不变，记录封闭原因；回退只能恢复匹配的代码和 schema 组合。
- 心跳失败：停止领取新工作；已持有工作只按原 lease/fencing 和事务契约完成或恢复，不由监控逻辑改写；连接恢复且心跳成功后继续领取。
- 单类队列指标失败：该类显示 unknown，其他类继续展示；不得把 0 当作 unknown。
- UI 组件失败：通过页面批次回退到已保留的兼容实现，不回退同一阶段已经验证的后端安全能力。
- 图表或动画加载失败：核心数据表、摘要和操作仍可使用。
- Repository 拆分回归：切回兼容 facade 的旧实现；任何迁移或业务状态写入均按原事务边界处理。

## 5. 六阶段路线图

### 5.1 阶段 0：基线、指标和变更边界

#### 目标

建立后续阶段共同使用的可复现基线，明确真实入口、页面、队列、性能场景、测试范围和证据格式。在基线冻结前，不宣称任何绝对性能目标。

#### 当前问题

### 5.2 阶段 1：全环境 schema fail-fast

#### 目标

保证每个真实 API 和 Worker 进程只在数据库 schema 精确等于当前代码 head 时启动，消除版本错配继续提供服务或领取任务的窗口。

#### 当前问题

CURRENT_SCHEMA_REVISION 和部分运维检查已经存在，但 FastAPI 生命周期与 Worker CLI 没有共享启动门。直接 Uvicorn、开发脚本和容器入口的行为不能由一个契约证明一致。

#### 纳入范围

- 建立一个无写入的共享 schema compatibility guard；
- 在本地/容器 API 包装器启动 Uvicorn 前运行 preflight，并在 FastAPI startup/lifespan 再次防御；
- 在 Worker 包装器输出 ready、创建心跳、构造业务循环或领取四类任务前运行同一 preflight；
- 覆盖本地脚本、直接模块入口和容器 api/worker 角色；
- 把 migrate 放入非默认 operations profile 或独立 Compose，backend/worker 直接依赖 mysql healthy 与 storage-init；
- 保留专用 migrate 操作需要的 Alembic、凭据和最小授权同步，但只允许显式调用；
- 为缺表、零行、多行、较旧、较新、未知、权限不足、连接失败和当前 head 建立测试矩阵；
- 输出不含凭据的结构化启动成功/失败事件和非零退出码；
- 保持离线 OpenAPI 生成和纯单元测试不连接真实数据库；
- 把新增的启动进程和 schema 集成测试登记到 ci-suite-manifest 的 MySQL 8.0/8.4 套件及对应 node baseline，不能停留在默认排除集合；
- 更新运行手册中的停止、备份、显式迁移、验证、启动顺序。

#### 明确不做

- 不自动执行 Alembic upgrade 或 downgrade；
- 不提供忽略版本检查的真实运行开关；
- 不允许普通 docker compose up 通过依赖链隐式迁移；
- 不把备份历史读取兼容范围当成运行兼容范围；
- 不在不兼容 schema 上提供只读业务 API、健康假成功或 Worker 排空模式；
- 不顺带修改业务表或业务状态机。

#### 依赖

阶段 0 的真实入口清单、当前 head 单一来源和 MySQL 8.0/8.4 可丢弃测试环境。

#### 交付物

- 共享 schema compatibility guard 及稳定错误分类；
- 所有真实 API/Worker 入口接线；
- 显式 migrate 入口、非默认 operations profile、直接基础依赖和不再隐式迁移的 Compose 启动契约；
- 启动进程级和 MySQL 集成测试；
- 更新后的 ci-suite-manifest 与 node baseline；
- OpenAPI 离线生成不触库契约；
- 更新后的本地和容器运行说明。

#### 风险与回退

门禁可能暴露原本被隐藏的部署顺序错误并导致服务拒绝启动，这是预期的安全失败。先在可丢弃数据库演练旧代码/新 schema、新代码/旧 schema 和匹配组合。回退不等于绕过检查：任何回退制品必须声明并验证与数据库完全相同的 revision；数据库已迁移到旧制品不支持的版本时默认向前修复，确需恢复数据只能按演练过的备份恢复 runbook 在隔离数据库验证后受控切换。禁止增加 bypass、自动迁移、删除检查或手工修改 alembic_version。

#### 验证门禁

- 阶段 0 列出的真实入口覆盖率为 100%；
- 受支持的本地/容器 API 包装器在所有不兼容情况中于启动 Uvicorn 前退出，端口未监听；直接 Uvicorn 在 lifespan 失败后退出、未进入 ready 且从未返回成功业务响应；仅返回 readiness 503 不算完成；
- Worker 在所有不兼容情况中于限定启动时间内退出非零，四类队列领取次数和业务写入均为 0；
- 当前 head 在 MySQL 8.0/8.4 上启动成功；
- 检查过程只有读取，测试证明不会迁移或改变 alembic_version；
- 日志不暴露数据库 URL、密码或业务数据；
- 直接 Uvicorn、app.worker.cli、本地脚本和容器角色均不能绕过检查；
- scripts/run-worker.ps1 的 ready 文案只在 preflight 通过后出现；
- docker compose effective config 证明默认 profile 不包含 migrate，backend/worker 直接等待 mysql/storage-init；旧 schema 上普通 up 保持 revision 不变且 API/Worker 拒绝，显式 operations migrate 完成 revision 与授权同步后才能启动；
- 新测试确实由 ci-suite-manifest 的 MySQL 8.0/8.4 profile 收集，无未解释 skip；
- 同一候选 SHA 的统一质量门及 OpenAPI client check 全部通过。

#### 完成证据

必须附上入口覆盖矩阵、每种错配的进程退出结果、当前 head 成功结果、零副作用断言、MySQL 8.0/8.4 结果、日志脱敏样本、运维文档和回退演练记录。

### 5.3 阶段 2：Worker 心跳、队列指标和管理员状态页

#### 目标

让管理员能够从数据库权威事实判断 Worker 是否在线、四类队列是否积压或失败，并用结构化日志定位问题。

#### 当前问题

现有管理员维护页只显示 publication outbox；其他三类队列和 Worker 进程状态不可见。普通异常日志能说明某次调用失败，却不能回答“现在有没有 Worker”“哪类队列最老”“是否正在重试”。

#### 纳入范围

- 通过显式 Alembic 迁移增加 Worker 心跳持久化结构和必要索引；
- 同步数据库最小权限清单、迁移契约、备份/恢复结构契约和 MySQL 8.0/8.4 测试；
- Worker 启动、轮询、心跳失败、正常停止和崩溃超时语义；
- 每个 Worker 实例、每类消费者的 last poll、连续失败和安全 failure_code 持久状态；
- 使用数据库时间的独立心跳调度、长任务心跳，以及正交的 heartbeat_status/maintenance_active 语义；
- return_dedup、publication_outbox、catalog_export、catalog_import 四类原生状态指标、capabilities 和 observed_at；
- 扩展 GET /api/admin/maintenance，同时保持现有字段兼容；
- 管理员页面显示 online、stale、offline、stopped、unknown、maintenance_active 及实际冻结阈值；
- Worker JSON 日志事件和敏感字段白名单；
- 30 天有界保留与清理；
- 运行手册中的启动、检查、积压、失败和离线排查；
- API/Worker 多进程、假时钟、崩溃和部分队列查询失败测试。
- 把新增心跳、队列和管理 API 集成测试登记到 ci-suite-manifest 的 MySQL 8.0/8.4 套件。

#### 明确不做

- 不把批量审核 queued 项改由 Worker 领取；
- 不增加任务取消、强制重试、删除失败记录或修改队列的管理按钮；
- 不引入 Prometheus、Grafana、外部告警、Redis 或消息代理；
- 不在心跳或日志中保存业务载荷、原始文件名、订单号或客户字段；
- 不以 Worker 在线代替队列正确性检查，也不以队列为空推断 Worker 在线。
- 不把 catalog_export 的 building 伪装成“正在处理”，也不把 catalog_import 的过期 parsing 伪装成可自动恢复。

#### 依赖

阶段 1 的 schema fail-fast 必须完成。迁移、API 和 Worker 使用同一个新 head，部署演练遵循停止旧进程、备份、迁移、验证、启动新进程的顺序。

#### 交付物

- Worker 心跳迁移、Repository 和生命周期逻辑；
- 数据库最小权限、迁移、备份恢复和索引契约；
- 四类队列的原生映射、统一响应外壳、capabilities、query_health 与 consumer_health 查询；
- 向后兼容的管理员维护 API；
- 管理员运行状态 UI；
- Worker 结构化日志规范和实现；
- 监控、保留、故障排查和恢复说明。

#### 风险与回退

心跳频率和聚合查询可能增加数据库负载。阶段 0 先记录维护 API 与空闲 Worker 基线，查询必须使用受控索引、有界时间范围和 EXPLAIN 证据。UI 可独立回退到旧维护视图；API 新字段保持追加兼容。Worker 回退时先停止新 Worker，确认现有 lease/claim 的安全恢复条件，再部署与当前 schema 匹配的旧制品，不得批量手改 processing 状态。新增监控表暂时不用时保持为无消费者的 additive schema；删除表是另一项经批准的迁移，不能与紧急应用回退同时执行。

#### 验证门禁

- 正常 Worker 按阶段 0 冻结的 H 使用数据库时间更新且状态为 online，长任务期间仍按时更新；
- 假时钟证明按 S/O 转为 stale/offline，页面刷新契约证明崩溃最迟在 O+R 内可见；
- 正常停止显示 stopped，崩溃不需要手工改行即可转为 offline；
- 心跳写入失败后不领取新任务，已有任务仍遵循原 lease/fencing；维护写屏障期间同时展示事实性的 heartbeat_status 与 maintenance_active，不把维护前离线改写为健康，释放后等待真实新心跳；
- 四类队列在空、未解决、可领取、处理中、等待重试、失败、过期租约和不适用夹具下逐字段与同一 observed_at 的数据库事实一致；
- catalog_export 无 claim/lease 的处理中、重试和陈旧字段为 null 且 capability=false，catalog_import 过期 parsing 明确显示 stuck；
- 模拟单类消费者连续异常时总体 Worker 仍 online，但该类 consumer_health 显示失败、连续次数递增，其他三类保持自身结果；
- 单类指标失败只把该类标为 unknown，不伪造 0 或污染其他类；
- 非管理员不能访问运行状态，响应为 private/no-store，API 和日志不泄露敏感信息；
- 管理 API p95 和 Worker 空闲数据库开销不突破阶段 0 冻结预算；
- 心跳表权限、备份恢复和所有队列查询在 MySQL 8.0/8.4 通过，新增测试进入 canonical suite 且无未解释 skip；
- 同一候选 SHA 的 Ruff、mypy、pytest、OpenAPI 无漂移、ESLint、TypeScript、Vitest 和 Playwright 全部通过。

#### 完成证据

必须附上迁移与回退演练、最小权限和备份恢复结果、假时钟结果、真实进程停止/崩溃/维护屏障演示、实际识别耗时、observed_at、四类队列逐字段数据库对账、单类消费者持续失败演示、权限负向测试、结构化日志脱敏样本、管理员页面截图与 Playwright 结果、性能对照、canonical suite 收集证据和更新后的运维手册。

- 键盘可完成打开、移动焦点、选择、提交和关闭，焦点可见且返回正确位置；
- test:a11y 自动检查无 serious 或 critical 问题，人工检查覆盖核心复合控件；
- Token 和组件在桌面、窄屏、长中文和 200% 缩放下可用；
- prefers-reduced-motion 契约在组件层生效；
- test:visual 固定截图无未批准差异，基线更新附人工审核人和原因，禁止自动接受；
- 新组件通过 Token 可执行检查或在有原因、有审核人的 allowlist 中；
- 前端生产 bundle 增量不突破阶段 0 冻结预算；
- 新依赖进入锁文件，并通过现有两种 source 配置的生产构建；
- 全部前后端统一质量门通过。

#### 完成证据

必须附上 Token 说明、组件清单、Storybook 构建产物、键盘与无障碍结果、视觉差异评审、bundle 对照、管理员状态页前后截图、测试结果和组件使用文档。

### 5.5 阶段 4：全页面渐进迁移、Motion 和 ECharts

#### 目标

在系统持续可用的前提下，让阶段 0 登记的全部页面和页面状态采用共享 Token、组件和局部样式，并增加克制、可关闭的动画与一致的数据图表。

#### 当前问题

页面视觉和交互细节分散，部分页面依赖大型全局选择器；图表、状态反馈和加载体验不够统一。一次性重写会同时触碰审核、发布、目录和管理员高风险流程。

#### 纳入范围

按以下批次迁移，每个批次独立验收后再继续：

1. 应用外壳、登录、导航、全局错误和权限状态；
2. 管理员控制台、运行状态和版本列表；
3. 商品目录首页、款式详情、导入、未匹配和目录版本；
4. 看板、商品分析、已发布日期与明细账；
5. 日期工作台、单项审核、批量审核和高级发布流程。

每个批次都覆盖正常、载入、空、错误、离线、权限、窄屏和长中文状态。阶段还包括：

- 每个页面先批准视觉任务说明，再实施和评审前后截图；
- 页面样式迁移到 CSS Modules 和共享模式；
- 对确有空间或状态关系的交互引入 Motion；
- 规范并扩大 ECharts 在趋势和对比场景中的使用；
- 图表摘要、表格后备、键盘筛选和懒加载，并保留现有图表的小数精度、BigInt 缩放和 null 数据断线语义；
- 页面级视觉回归、核心 E2E、无障碍和性能对照；
- 盘点 frontend/src 下所有普通 CSS，不只检查 styles.css；把 feature/component 样式迁入 module.css；
- 删除已无调用者的页面级兼容 CSS，只保留 tokens、primitives、reset 和带所有者/删除条件的临时 allowlist。

#### 明确不做

- 不冻结整个系统等待一次性上线；
- 不在同一页面迁移中重写后端业务状态机；
- 不以动画替代文本、焦点或状态图标；
- 不对大表逐行播放动画，不使用 3D 图、装饰性粒子或自动轮播；
- 不强迫所有数据使用图表，表格更清楚时保留表格；
- 不删除仍被下一批页面依赖的兼容样式。

#### 依赖

阶段 3 的 Token、共享组件、Storybook 和视觉回归必须稳定；阶段 0 的页面登记表是“全部页面”的唯一清单。

#### 交付物

- 五个页面迁移批次及每批证据；
- Motion 使用规范、共享过渡和 reduced-motion 测试；
- ECharts 包装层、图表 Token、摘要和可访问后备模式；
- 更新后的页面 Storybook、视觉基线和 E2E；
- 全部非 module CSS 清单、自动扫描、兼容 allowlist 和清理记录；
- 每页视觉任务说明及信息层级/密度/响应式/动效图表理由的批准记录；
- 页面迁移登记表的 100% 完成记录。

#### 风险与回退

视觉迁移可能改变可点击范围、焦点顺序、表格密度或业务信息层级。每批先固定行为测试，再迁移展示；每迁移一个页面都必须保持为可发布候选，发现回归时只回退该页、该组件或该批，不撤销已验证批次。Motion 和 ECharts 必须可独立移除，核心表单、表格和命令不能依赖它们完成。视觉快照不能作为“修复”直接重录；只有行为正确且差异获人工批准后才能更新。

#### 验证门禁

- 每批所有登记页面、admin/data_manager/viewer 适用角色和状态在 1280/768/390 像素宽视口均有截图或明确的不适用说明；
- 每页首要任务、信息层级、区域唯一主操作、数据密度和响应式结构通过视觉评审；动画/图表都有可验证理由；
- 核心操作在鼠标、键盘、200% 缩放和 reduced-motion 下完成；
- 自动无障碍检查无 serious 或 critical 问题，目标符合 WCAG 2.2 AA；
- 关键审核、发布、回滚、目录和批量流程的 Playwright 行为保持不变；
- 图表数据与同一 API 响应或表格数据对账一致；
- 图表保留 decimal/BigInt 原始精度、null-gap、role/title/desc、非颜色识别和每日点矩阵/等价表格；任一门失败时保留 SVG；
- 页面懒加载、交互时延和 bundle 不突破阶段 0 冻结预算；
- 连续三轮固定环境对照不存在可重复的 API p95、核心交互或队列等待退化；
- 自动扫描 frontend/src 的全部 CSS：除 tokens、primitives、reset 和有所有者/删除条件的兼容 allowlist 外，feature/component 样式均为 CSS Modules；所有路由不再依赖未登记的页面级全局选择器。

#### 完成证据

必须附上五批迁移记录、页面登记表、视觉差异、E2E、键盘与无障碍结果、reduced-motion 演示、图表数据对账、bundle 和性能对照、删除兼容 CSS 的调用者证明，以及项目负责人对全部页面完成的确认。

### 5.6 阶段 5：拆分大型组件与 Repository，并按指标优化性能

#### 目标

在外部行为和 UI 契约稳定后，按职责、事务和真实性能证据改进内部边界，降低修改风险并消除已确认瓶颈。

#### 当前问题

若干 React 组件和后端 Repository 同时承担多个职责。直接按行数拆分容易把状态机、锁顺序和事务切断；在 UI 迁移前拆分又会让同一代码经历两轮高冲突修改。

#### 纳入范围

- 使用提交历史、测试归属、依赖关系、性能剖析和故障记录识别真实拆分点；
- 把页面路由/用例编排、请求 Hook、命令、领域展示和通用 UI 分离；
- 把 Repository 的读取、命令、行映射和跨表事务协调分离；
- 为跨模块接口建立类型、契约测试和兼容 facade；
- 记录并保持发布、回滚、日期移动、批量审核和目录操作的事务/锁不变量；
- 对阶段 0/2/4 证明确认的慢查询、重复请求、过大 bundle 或重渲染进行针对性优化；
- 用 EXPLAIN、查询计数、渲染剖析、bundle 分析和固定性能对照验证收益。

#### 明确不做

- 不设文件行数上限，不以拆成更多文件作为目标；
- 不顺带拆微服务、改数据库、改 ORM 或全面异步化；
- 不在无测量证据时增加缓存、索引或预计算；
- 不把数据库结构变化与纯代码边界拆分放进同一个工作项；确需 additive migration 时单独设计、迁移和回退；
- 不改变 API 字段、权限、幂等、状态机或事务结果；
- 不把性能优化建立在减少校验、审计或一致性保护之上。

#### 依赖

阶段 4 的页面和组件契约稳定；阶段 0 的基线、阶段 2 的队列指标和阶段 4 的前端性能数据能够指出优先级。

#### 交付物

- 候选模块的职责与依赖图；
- 经批准的组件和 Repository 边界；
- 兼容 facade、契约测试和迁移顺序；
- 针对确认瓶颈的性能修改；
- 事务、锁、SQL、渲染和 bundle 对照报告；
- 旧入口和临时适配层的安全移除记录。

#### 风险与回退

最大风险是破坏隐含事务、导入环或并发顺序。每个拆分先增加 characterization/contract tests，再移动一个边界；旧 facade 保留到新实现通过 MySQL 并发测试和调用者迁移。性能修改单独提交，若收益不能复现或出现业务回归则独立回退，不与结构重构捆绑。

#### 验证门禁

- 每个新模块能说明职责、公开接口和依赖，不存在新循环依赖；
- 外部 API、OpenAPI 客户端和页面行为无未批准漂移；
- 发布、回滚、跨日期、批量审核和目录事务在 MySQL 8.0/8.4 上通过并发与失败恢复测试；
- SQL 计划、查询次数、API p95、核心交互、bundle 和队列等待不突破冻结预算；
- 被优化场景的收益在至少三轮固定环境中复现；
- 删除旧实现前，调用者为 0 且兼容测试仍通过；
- 全部统一质量门通过。

#### 完成证据

必须附上职责图、边界决策、characterization 与契约测试、并发/失败恢复结果、调用者清单、SQL 或前端剖析、三轮性能对照、回退验证和旧适配层移除证明。文件行数变化只能作为背景信息，不能作为完成结论。

## 6. 跨阶段工作流

### 6.1 状态模型

所有阶段和工作项使用同一状态：

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| planned | 已登记，尚未形成阶段级设计 | 有明确问题、范围和负责人角色 |
| designed | 设计和边界已批准 | 目标、非目标、风险、回退和验证门禁明确 |
| implementing | 正在修改 | 详细实施计划、基线和回退点已确认 |
| verifying | 实现完成，正在收集证据 | 代码审查通过，所有要求的测试已开始执行 |
| complete | 已完成 | 同一候选 SHA 的强制门禁、文档、回退和批准证据齐全 |
| blocked | 无法安全继续 | 阻断事实、影响、责任角色和解除条件已记录 |

正常流转为 planned → designed → implementing → verifying → complete。发现设计缺口时可从 implementing 或 verifying 返回 designed；测试失败返回 implementing。blocked 不是“稍后再做”的同义词，解除后回到与实际工作相符的状态。

没有测试结果和文档链接的工作项不得标记 complete。单纯合并代码、截图好看或文件变短都不构成完成。

### 6.2 阶段进入和退出

- 前一阶段必须 complete，后一阶段才能进入 implementing；
- 后一阶段可以在前一阶段 verifying 时进行只读调研，但不得提交依赖尚未稳定的实现；
- 每个阶段进入 implementing 前，基于当时仓库 HEAD 编写独立详细实施计划；
- 每个阶段结束时更新基线、运维文档和受影响的权威设计；
- 紧急修复可以独立处理，但不得把未完成阶段标记完成。

### 6.3 数据库变更流程

任何阶段需要 schema 变更时：

1. 在可丢弃 MySQL 8.0/8.4 上验证 upgrade、head 和适用的 downgrade/恢复路径；
2. 停止会访问目标数据库的 API 和 Worker；
3. 创建并验证备份；
4. 用独立迁移账号通过专用命令显式运行 Alembic；普通 docker compose up 不得代为触发；
5. 验证唯一 head、结构契约和运行账号权限；
6. 启动匹配 head 的 API 和 Worker；
7. 验证 schema fail-fast、健康、心跳和核心 canary。

任何应用进程不得替代上述流程自动迁移。未来受控发布器只有在单独设计已经批准、操作者明确发起发布操作且迁移作为独立审计步骤时才能执行第 4 步。

### 6.4 API 和客户端契约

- API 模型变化先更新后端契约测试，再重新生成 TypeScript 客户端；
- 生成结果必须由无数据库副作用的离线路径产生；
- CI 通过 scripts/generate-api-client.ps1 -Check 对生成前后差异执行 OpenAPI 无漂移检查；
- 阶段 2 的维护响应只追加字段，不删除现有字段；
- UI 不绕过生成客户端重新手写相同响应类型。

### 6.5 UI 页面迁移登记

每个路由登记以下事实：

- 页面所有者和主要用户角色；
- 首要任务、信息层级、每个区域主操作和数据密度；
- 1280/768/390 像素宽的响应式结构；
- 正常、载入、空、错误、离线、权限和窄屏状态；
- 使用的共享组件、全局兼容 CSS 和图表；
- 每个动画/图表的功能理由或明确不采用理由；
- 键盘路径、焦点规则和 reduced-motion 行为；
- Vitest、Storybook、视觉截图和 Playwright 覆盖；
- 迁移批次、当前状态、回退提交和完成证据。

阶段 4 只能以登记表 100% 完成声明“全页面迁移”，不能用抽样截图代替。

### 6.6 统一验证证据

每个阶段在同一候选 SHA 上按影响范围运行并记录：

- Ruff lint 与 format check；
- mypy strict；
- pytest 单元、契约、集成、并发和恢复测试；
- ESLint、TypeScript typecheck、Vitest 与生产 build；
- OpenAPI 生成无漂移；
- Playwright 行为与视觉回归；
- MySQL 8.0/8.4 兼容测试；
- 键盘、焦点、对比度、200% 缩放和 reduced-motion；
- 固定环境的 API、交互、bundle 和队列性能对照；
- git diff check、敏感数据检查和工作区状态。

现有 canonical profile 名称为 ubuntu-full、windows-smoke、frontend-full 和 MySQL compatibility。MySQL 8.4 当前只在 master push 的完整门禁中执行，因此阶段完成证据必须来自同一 SHA 的手工 8.4 profile 或该 SHA 成功的 master-required，不能引用另一提交。新增阶段测试必须进入 ci-suite-manifest 和相应 node baseline，不能停留在排除清单。

测试命令、开始/结束时间、退出码、通过/失败/skip 数、提交 SHA、环境指纹和产物链接必须一起保存。任何未解释的 skip、xfail 或重试成功都使状态保持 verifying。只写“测试通过”不是充分证据。

## 7. 指标与成功标准

### 7.1 安全和兼容性

| 指标 | 成功标准 |
| --- | --- |
| 真实入口 schema 覆盖率 | 阶段 0 登记的 API/Worker 入口 100% 接入共享门 |
| 不兼容拒绝率 | 缺失、零/多行、旧、新、未知、无权限和连接失败场景 100% 在服务/领取前拒绝 |
| 自动迁移次数 | API、Worker 和普通 docker compose up 启动路径恒为 0；只有独立显式迁移操作可执行 |
| 错配副作用 | 业务写入、队列领取、心跳写入均为 0 |
| OpenAPI 漂移 | 生成客户端与当前 API 不存在未提交差异 |

### 7.2 Worker 可观测性

| 指标 | 成功标准 |
| --- | --- |
| 心跳在线判定 | 使用阶段 0 冻结的 H/S/O，满足 S≥3H、O>S，并由 API 返回生效值 |
| UI 离线可见时间 | 无维护屏障干扰时，崩溃最迟在阶段 0 批准的 O+R 内显示 offline |
| 队列覆盖 | return_dedup、publication_outbox、catalog_export、catalog_import 全部展示 |
| 在线语义 | online 只代表最近成功写数据库心跳，不得被描述为队列正在推进 |
| 消费者隔离 | 每类独立返回 query_health 与 consumer_health；单类持续失败不被总体 online 掩盖 |
| 维护语义 | heartbeat_status 与 maintenance_active 正交展示；维护前离线不会被改写为健康，维护中不虚构进程存活 |
| 权威一致性 | 固定种子和同一数据库 observed_at 下，管理员 API 与直接数据库事实逐字段 100% 一致 |
| 不适用语义 | 无法证明或原生不支持的指标返回 null 与 capability=false，不用 0 替代 |
| 部分失败语义 | 查询失败显示 unknown，绝不显示伪造的 0 或 healthy |
| 敏感信息 | 心跳、API 和结构化日志中禁止字段出现次数为 0 |

### 7.3 UI、无障碍和可维护性

| 指标 | 成功标准 |
| --- | --- |
| 页面迁移覆盖 | 阶段 0 登记的全部路由和状态 100% 完成 |
| 共享视觉语义 | 页面颜色、间距、状态、图表和动效来自登记 Token |
| 页面视觉合同 | 每页首要任务、信息层级、区域唯一主操作、数据密度、响应式结构和动效/图表理由均有批准证据 |
| CSS 收敛 | 全部 feature/component 样式为 CSS Modules；全局例外只有受控基础文件和带删除条件的 allowlist |
| 组件证据 | 每个共享组件具备适用的 Storybook 状态和测试 |
| 视觉漂移 | 固定截图只有经评审并与设计变更绑定的差异 |
| 键盘操作 | 核心审核、发布、目录、管理员和筛选流程无需鼠标即可完成 |
| 无障碍 | 以 WCAG 2.2 AA 为目标；自动检查无 serious/critical，人工门禁全部通过 |
| reduced-motion | 所有新增位移、缩放和图表动画都有关闭或等价静态路径 |
| 模块边界 | 被拆单元职责、接口和依赖可说明，新循环依赖为 0 |

WCAG 2.2 AA 是产品验收目标，不表示仅靠自动扫描即可宣称完整合规；自动与人工证据必须同时保留。

### 7.4 性能

阶段 0 负责在固定环境中测得并冻结每个核心场景的绝对预算。该过程是一个必须完成的交付物，不在本文凭空填写毫秒数。

后续统一判定方法为：

- 使用相同提交构建方式、数据库版本、合成数据、硬件档位、浏览器和预热步骤；
- 阶段 0 对每个场景保存 baseline p50/p95、观测方差和允许的绝对 p95 上限；上限在任何候选实现运行前由项目负责人批准并版本化；
- 新旧候选按配对顺序运行，每个场景至少三轮独立重复；
- 保存原始样本和 p50/p95/最大值，不只保存汇总截图；
- 三轮中持续突破阶段 0 冻结预算即为可重复退化，阶段不得 complete；
- API p95、核心交互、页面 bundle、Worker 空闲开销和队列等待分别判断，不能用一项改善抵消另一项退化；
- 如果环境、数据量或业务场景改变，建立带新版本号的基线并保留旧基线，不能悄悄覆盖；
- 放宽预算必须有证据、原因和项目负责人批准，不能由实现者自行修改门禁。

### 7.5 总体完成定义

路线图只有在以下条件全部满足时才完成：

- 所有真实 API/Worker 入口在 schema 不兼容时拒绝运行；
- Worker 离线在约定阈值内被识别，管理员状态与数据库权威事实一致；
- 四类队列均有积压、处理中、重试、失败和时间指标或明确不适用映射；
- 全部页面渐进采用共享 Token、组件、CSS Modules 和视觉回归；
- Motion 与 ECharts 遵循 reduced-motion、可访问后备和性能预算；
- 核心操作达到既定键盘和 WCAG 2.2 AA 目标；
- 没有可重复的 API p95、交互、bundle 或队列等待退化；
- 大型组件与 Repository 的拆分由职责和证据驱动，业务/API/事务契约保持不变；
- 每个阶段均有测试结果、文档、回退和批准证据。

## 8. 风险登记表

| 风险 | 早期信号 | 预防与控制 | 回退 |
| --- | --- | --- | --- |
| schema 门阻断正常启动 | 匹配环境也报告未知版本 | 单一版本来源、MySQL 双版本进程测试、迁移前演练 | 恢复经验证且与数据库 head 匹配的代码；不得绕过门 |
| 部署顺序导致旧/新版本错配 | 迁移后旧进程仍存活 | 停止、备份、迁移、验证、启动的固定 runbook | 停止全部访问者，按批准恢复路径恢复匹配组合 |
| 心跳写入增加数据库负载 | 空闲 Worker 写 IOPS 或锁等待超预算 | 阶段 0 冻结 H、单行有界更新、索引和性能基线 | 停止新 Worker，回退心跳实现并保持 schema 匹配 |
| 维护写屏障造成心跳误解 | 备份期间 heartbeat_status 变 stale/offline | 正交展示 factual heartbeat_status、last_seen_at 与 maintenance_active | 屏障释放后等待真实新心跳；查询失败显示 unknown |
| 队列聚合查询变慢 | 管理 API p95 或扫描行数上升 | 队列专用查询、EXPLAIN、索引和有界时间范围 | 回退单类聚合或 UI 字段，保留原始队列行为 |
| 统一指标虚构队列能力 | catalog_export 被显示为处理中或 catalog_import 被显示为可恢复 | 原生状态映射、nullable 字段和 capabilities 契约 | 回退错误映射，显示 unknown/不适用，不改任务状态 |
| 管理页把 unknown 显示为健康 | 数据源异常时出现 0 积压 | 封闭状态模型、部分失败测试、明显 unknown 文案 | 回退展示层并保留 API 原因码 |
| 新 UI 依赖扩大 bundle 或供应链面 | build 体积和依赖树突增 | 按需 Radix 包、Lucide 组件导入、锁版本和许可审查 | 移除单个适配组件或依赖，不影响旧页面 |
| CSS 新旧规则冲突 | 页面局部回归、选择器优先级上升 | CSS Modules、兼容层登记、逐路由截图 | 回退当前页面批次，保留已验收页面 |
| 动画造成眩晕或阻断 | reduced-motion 仍有位移、焦点延迟 | 统一 Motion wrapper、时长上限和人工检查 | 禁用该过渡，保留立即状态切换 |
| 图表与数据表不一致 | 同筛选下数值或日期不同 | 同响应建模、数据对账测试、可读摘要 | 回退图表，保留权威表格和 API |
| Repository 拆分破坏事务 | 锁顺序、并发或回滚测试失败 | characterization、事务协调器、MySQL 双版本并发测试 | 切回兼容 facade 的旧实现 |
| 性能基线受环境噪声污染 | 独立轮次差异大于冻结预算 | 固定环境、预热、多轮原始样本 | 废弃该批证据并重新建立版本化基线 |
| 路线图范围膨胀 | 阶段中出现框架替换或新业务需求 | 每阶段明确不做、变更审查和独立设计门 | 把新增需求移出当前阶段，恢复已批准范围 |
| 证据形式化但不可复现 | 只有截图或“已通过”文字 | 保存命令、退出码、SHA、环境和机器可读产物 | 状态退回 verifying，重新运行门禁 |

风险责任按领域分配：数据库兼容和事务由后端/运维共同负责；Worker 指标由后端负责、管理员展示由前端负责；UI Token、组件、动画和无障碍由前端负责；阶段状态和预算变更由项目负责人批准。具体人员在阶段实施计划中绑定。

## 9. 状态与证据模板

### 9.1 工作项记录字段

每个阶段工作项必须使用以下字段；这是记录契约，不代表本文存在未决内容。

| 字段 | 填写规则 |
| --- | --- |
| 标题 | 唯一、可验证的结果，不写宽泛的“优化代码” |
| 阶段 | 0～5 中唯一一个所属阶段 |
| 状态 | planned、designed、implementing、verifying、complete 或 blocked |
| 基线 | 开始实施时的完整提交 SHA |
| 候选 | 收集完成证据的唯一完整提交 SHA |
| 负责人角色 | 项目负责人、后端、前端或运维；实施计划再绑定具体人员 |
| 目标与范围 | 说明改变什么、明确不改变什么 |
| 依赖 | 前置工作项、迁移 head、API/组件契约 |
| 风险与回退 | 可观测信号、停止条件和精确回退边界 |
| 验证门禁 | 测试、环境、预期结果和性能预算 |
| 证据链接 | 测试结果、日志、截图、报告、文档和提交 |
| 决策记录 | 范围、预算或设计变更的批准链接 |
| 更新时间 | 带时区的时间和更新者 |

blocked 还必须记录阻断事实、影响范围、已尝试措施、解除条件和有权解除的角色。没有这些字段时只能保持原状态，不能使用 blocked 隐藏未完成工作。

### 9.2 complete 的最低证据

任何工作项进入 complete 前必须同时具备：

1. 实现提交和审查链接；
2. 同一候选 SHA 上与影响范围相符的完整命令、开始/结束时间、退出码、通过/失败/skip 数和机器可读结果；
3. OS、Python、Node、pnpm、浏览器、MySQL 的精确版本、schema revision 和运行环境指纹；
4. 合成数据/fixture 名称与摘要，不保存敏感原始数据；
5. CI workflow、run、job 和产物链接，以及未解释 skip/xfail/重试数为 0 的证明；
6. API/OpenAPI、UI、队列或事务中适用的对账证据；
7. 性能 fixture、预热/样本数、原始摘要、baseline/candidate p95、差值和判定，或说明为什么该工作项不影响性能；
8. 回退触发条件、目标制品 SHA、步骤、数据影响和至少一次适用层级的演练结果；
9. 更新后的设计、实施或运维文档链接；
10. 阶段验证责任人的批准人和批准时间。
