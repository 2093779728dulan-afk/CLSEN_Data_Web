# 批量审核工作流设计

日期：2026-08-17
状态：已批准；第一版明确排除 Worker、消息队列、任务监控和部署运维工作

## 1. 背景

现有多文件导入会把每份文件保存为独立不可变原始批次，并逐份识别日期、报表类型和编码。用户随后需要逐份确认识别、解析、生成草稿、运行校验并进入待发布状态。这个模型保留了可靠的来源证据和日期隔离，但大量文件需要重复执行相同操作，审核效率不足。

本功能在不削弱原始文件、解析基线、草稿、完整校验和发布门禁的前提下，增加跨日期批量审核。用户只需核对一次清单，系统即可并行推进全部安全项目；任何不确定、冲突或带警告的项目继续由人工单独处理。

## 2. 目标与非目标

### 2.1 目标

- 多文件上传后提供一次性批量预检和统一确认。
- 对严格满足安全条件的项目自动执行：确认识别、解析、生成草稿、完整校验、标记待发布。
- 前端最多同时推进三份文件，提高吞吐量但限制数据库和解析服务压力。
- 每份文件独立提交、独立恢复和独立重试；单项失败不阻断其他项目。
- 服务端持久化批量任务和每项状态，刷新、重新登录或短暂断网后可以恢复。
- 清楚区分已进入待发布、需要人工处理和处理失败。
- 保留现有逐份审核入口，异常项目可以直接进入对应日期和报表类型的工作区。

### 2.2 非目标

- 不自动发布任何版本。
- 不自动合并、替换或覆盖已有草稿或发布版本。
- 不自动确认校验警告。
- 不允许批量回滚、批量跨日期移动或批量删除原始文件。
- 第一版不引入独立任务队列、Worker 或新增运维系统。
- 不改变已发布版本和不可变原始证据的现有约束。

## 3. 已确认的产品决策

1. 批量流程终点是 `ready_for_publish`，不是 `published`。
2. 目标日期已有活动草稿或当前发布版本时，项目直接转人工处理。
3. 校验出现任何警告或阻断时，项目直接转人工处理。
4. 执行前必须展示文件名、日期、类型、编码和预计动作，并由用户勾选统一确认声明。
5. 单项失败不整批回滚；其他项目继续执行。
6. 前端并发上限固定为三项。
7. 采用“服务端权威预检和持久状态 + 前端限流执行”，为以后升级后台 Worker 保留任务接口。

## 4. 用户流程

### 4.1 创建预检

多文件保存和识别完成后，导入队列提供“批量审核”操作。客户端提交本次队列内的服务端批次 ID；文件名、检测结果、日期、类型、编码和目标数据状态均由服务端重新读取，客户端不能把显示值变成权威值。

服务端创建一个 `preview` 批量任务，为每份文件计算资格和预计动作。页面随后导航到独立的跨日期任务路由：

`/review/batch/:runId`

批量任务不继续挂在某个 `/review/:reportDate` 页面下，避免跨日期文件被误认为属于当前页面日期。

### 4.2 确认清单

确认表格至少显示：

- 文件名；
- 原始批次号；
- 识别日期；
- 报表类型；
- 文件编码；
- 识别状态；
- 目标日期当前状态；
- 预计动作或不能执行的原因。

合格项目默认选中，用户可以取消选择。不合格项目不可选。开始按钮附近显示选中数量，并要求用户勾选：

> 我已核对所选文件的报告日期和报表类型。

确认请求记录操作人、确认时间、确认时看到的任务修订号和选中项目。服务端在确认事务中重新检查全部选中项目；状态已经变化的项目转人工处理，不能沿用过期预检结果。

### 4.3 并行执行

确认成功后，任务进入 `running`。前端执行器只从服务端返回的 `queued` 项目中取任务，最多同时调用三个单项推进命令。

每个单项命令按顺序执行：

1. 再次校验原始文件和批次状态；
2. 使用预检中经用户确认的日期、类型和编码确认解析；
3. 生成新的不可变解析基线；
4. 在空目标位置生成活动草稿；
5. 运行当前数据修订对应的完整校验；
6. 仅在校验通过、没有警告且状态未变化时标记为 `ready_for_publish`。

一个单项命令可以跨越多个现有领域操作，但不能把不同文件放入同一数据库事务。每个现有领域操作继续使用自己的事务、锁和不可变结果。若后续阶段失败，已提交的原始批次、解析基线或草稿不会被删除；系统从服务端事实恢复到可解释的人工处理状态。

### 4.4 暂停、恢复和完成

“暂停批量处理”把任务改为 `paused`，停止领取新项目。已经发出的单项命令允许安全完成。恢复后继续领取剩余 `queued` 项目。

关闭页面不会启动新的项目，但已经到达服务端的命令仍按幂等契约完成。重新打开任务页面时，客户端先读取服务端任务状态，再恢复最多三项并发执行，不依赖旧 React 状态或浏览器队列推断完成结果。

没有 `queued` 或 `running` 项目后，任务进入：

- `completed`：全部选中项目进入待发布；
- `completed_with_exceptions`：至少一个项目需要人工处理或失败。

## 5. 严格资格规则

项目只有同时满足以下条件才能为 `eligible`：

- 原始文件完整性状态为可用；
- 导入批次属于当前站点且尚未被物化到其他版本；
- 检测得到唯一且受支持的报表类型；
- 检测得到合法报告日期；
- 编码受当前解析器支持；
- 批次没有处理中租约、不可确定提交结果或拒绝状态；
- 目标“站点 + 日期 + 报表类型”没有活动草稿；
- 目标没有当前发布版本；
- 同一批量任务中没有另一项目指向相同目标；
- 当前用户具备 `admin` 或 `data_manager` 角色。

不满足资格规则时必须返回稳定的机器原因码和中文说明。至少覆盖：

- `recognition_uncertain`；
- `source_unavailable`；
- `batch_state_conflict`；
- `duplicate_target_in_run`；
- `active_draft_exists`；
- `publication_exists`；
- `already_materialized`；
- `permission_denied`。

批量流程不得提供自动合并或覆盖选项。用户可以从异常项进入现有单项冲突决策流程。

## 6. 服务端状态模型

### 6.1 批量任务

新增持久化实体 `batch_review_runs`，核心字段包括：

- `id`；
- `site_id`；
- `created_by_user_id`；
- `status`：`preview | confirmed | running | paused | completed | completed_with_exceptions`；
- `revision`；
- `confirmed_at`；
- `confirmed_by_user_id`；
- `confirmation_statement_version`；
- 创建和更新时间。

状态更新必须携带预期 `revision`，避免两个页面同时确认、暂停或恢复时互相覆盖。

### 6.2 批量项目

新增持久化实体 `batch_review_items`，每项绑定一个任务和一个原始批次，核心字段包括：

- `run_id`、`batch_id`；
- 服务端快照的文件名、检测日期、检测类型和编码；
- 目标日期和报表类型；
- `selected`；
- `status`；
- `reason_code` 和安全中文说明；
- 当前解析尝试、解析基线、数据集和版本 ID；
- 单项操作 UUID、命令摘要和尝试次数；
- 创建和更新时间。

项目状态为：

`eligible | skipped | queued | parsing | materializing | validating | ready_for_publish | manual_review | failed`

数据库约束保证同一任务内批次不重复，并为任务内目标键建立查询索引。服务端资格检查仍是最终约束，数据库唯一索引不能代替跨现有草稿和发布指针的事务检查。

## 7. API 契约

### 7.1 创建预检

`POST /api/imports/batch-reviews/preflight`

请求只包含去重后的正整数 `batch_ids`。响应返回任务 ID、修订号、汇总计数和全部项目。空数组、重复 ID、跨站点批次或无权限访问必须失败；不能静默忽略。

### 7.2 读取和恢复

`GET /api/imports/batch-reviews/:runId`

返回任务、项目、汇总和允许的下一步操作。响应是页面恢复的唯一任务状态来源。

### 7.3 确认

`POST /api/imports/batch-reviews/:runId/confirm`

请求包含：

- `expected_revision`；
- 选中的项目 ID；
- `confirmation_accepted: true`；
- 版本化确认声明标识。

确认操作使用 UUID v4 幂等键。服务端重新预检选中项目，记录确认审计，把仍合格项目转为 `queued`，把变化项目转为 `manual_review`。

### 7.4 推进单项

`POST /api/imports/batch-reviews/:runId/items/:itemId/advance`

每个项目只允许一个活动推进操作。首次推进时冻结单项操作 UUID 和命令摘要；网络重试必须使用相同语义和同一 UUID。响应返回服务端最终或当前阶段。结果不确定时返回明确的 `outcome_unknown`，客户端先重新读取任务，不能直接换 UUID 重放。

### 7.5 暂停、恢复和重试

- `POST /api/imports/batch-reviews/:runId/pause`；
- `POST /api/imports/batch-reviews/:runId/resume`；
- `POST /api/imports/batch-reviews/:runId/items/:itemId/retry`。

暂停和恢复携带预期修订号及幂等键。只有机器标记为可重试的 `failed` 项目可以重试；业务冲突和校验异常只能进入人工处理。

## 8. 校验与待发布门禁

批量确认清单承担本次文件级日期和类型人工确认，但不能跳过版本级完整校验。

自动标记待发布必须同时满足：

- 最新完整校验属于当前数据修订；
- 校验运行成功且结果通过；
- 解析保真和草稿可解释性阶段都没有阻断；
- 警告数量为零；
- 草稿、数据修订、审核修订和活动指针仍与校验开始时一致；
- 目标位置仍无发布指针；
- 批量确认审计仍绑定本项目日期、类型和来源批次。

出现警告时不允许批量流程自动确认或生成替代备注。草稿保留为 `draft`，项目转为 `manual_review`，用户在现有审核页面中查看警告、添加依据并继续。

## 9. 前端组件

### 9.1 导入队列入口

`ImportReviewFlow` 保留现有单项流程。队列中存在至少两个可预检服务器批次时显示“批量审核”主操作。重复文件指向的已有未完成批次可以参加预检，但同一批次 ID 只能出现一次。

批量职责从当前体量较大的 `ImportReviewFlow.tsx` 中拆分，避免继续把任务执行和单项审核混在一个组件内。

### 9.2 独立任务页

新增 `BatchReviewPage`，内部至少拆分为：

- `BatchReviewSummary`：统计和总体状态；
- `BatchReviewPreflightTable`：清单、选择和确认；
- `BatchReviewExecutor`：最多三项并发调度，不保存权威业务状态；
- `BatchReviewProgressTable`：逐项阶段和原因；
- `BatchReviewCompletionActions`：待发布、异常和失败入口。

桌面保持紧凑表格；窄屏使用内部横向滚动，不把大量状态挤成卡片墙。所有控件保持至少 44px 触控高度，支持键盘操作和可读状态文本。

### 9.3 结果入口

- “查看全部待发布草稿”进入按本任务项目过滤的版本列表，不执行发布；
- “处理异常”进入对应 `/review/:reportDate` 并选中报表类型或版本；
- “重试”仅对服务端返回 `retry_allowed` 的项目显示。

## 10. 并发、锁与恢复

- 前端并发上限为三，服务端不能信任客户端并发限制；同一项目必须通过行锁或等价租约禁止并发推进。
- 不同项目如果在确认后变为相同目标，服务端锁定目标数据集键并让后到项目转人工处理。
- 单项内部沿用现有导入、解析、物化、校验和标记待发布的锁顺序，不能建立另一套绕过领域服务的直接 SQL 快捷路径。
- 数据库死锁和锁等待超时沿用现有有限重试规范；超过上限保留可恢复状态。
- 连接失效或提交确认丢失只读取幂等结果账本和当前服务端状态，不盲目重放。
- 页面关闭时不新增任务；本版本没有常驻 Worker，因此不会承诺浏览器关闭后继续领取尚未开始的项目。

## 11. 审计与权限

只有 `admin` 和 `data_manager` 可以创建、确认、执行、暂停、恢复或重试批量审核任务。`viewer` 不可访问任务内容，因为任务包含未发布数据和内部异常。

审计至少记录：

- 任务创建及批次清单；
- 预检资格结果和原因码；
- 用户确认声明、日期、类型和任务修订；
- 暂停、恢复、重试；
- 每项解析基线、草稿版本、校验运行和待发布结果；
- 任务最终统计。

审计事件不得包含原始文件正文、敏感单元格值或未清理的异常堆栈。

## 12. 失败语义

### 12.1 人工处理

以下属于确定的业务结果，不显示为系统失败：

- 识别不确定；
- 日期或类型缺失；
- 同任务目标重复；
- 已有草稿或发布版本；
- 校验警告或阻断；
- 状态在预检后变化；
- 已被其他流程物化。

### 12.2 可重试失败

短暂网络错误、数据库有限重试耗尽、解析服务暂时不可用等可以标记为可重试，但必须保存已经确认的服务器阶段。重试从领域服务允许的边界恢复，不删除已生成的不可变结果。

### 12.3 结果不确定

提交确认丢失时项目状态显示“正在确认服务器结果”，不归入成功或普通失败。客户端轮询服务端任务；恢复到终态后再继续调度。

## 13. 测试与验收

### 13.1 单元测试

- 资格规则及所有稳定原因码；
- 批量任务和项目状态转移；
- 并发调度最多三项；
- 暂停时不领取新项目；
- 恢复时只以服务端状态建立队列；
- 人工处理、失败和结果不确定的显示与允许操作。

### 13.2 后端集成测试

- 创建预检、跨站点拒绝、重复 ID 拒绝和权限拒绝；
- 确认时状态重检；
- 同任务目标重复、已有草稿、已有发布和并发目标变化；
- 单项从解析到待发布的完整成功路径；
- 校验警告或阻断保留草稿并转人工；
- 同一 UUID 重试恢复相同结果，改变命令摘要冲突；
- 三个以上并发请求不能并发推进同一项目；
- 暂停、恢复、刷新读取和可重试失败；
- 全流程不存在自动发布事件或发布指针切换。

### 13.3 前端和端到端测试

- 预检清单字段、默认选择、禁用原因和确认声明；
- 未勾选声明不能开始；
- 进度状态和汇总与服务端一致；
- 单项失败后其他项目继续；
- 页面刷新和重新登录恢复；
- 暂停后活动项完成但不启动新项；
- 待发布、异常和重试入口正确；
- 桌面、768px 和 390px 无整页横向溢出；
- 30 份和 100 份文件的并发验收。

### 13.4 效率标准

- 无论 5 份还是 100 份文件，合格批次的必要人工操作固定为核对清单、接受确认声明和开始任务。
- 并发执行数量始终不超过三。
- 在相同受控测试环境和相同 30 份合格 fixture 下，批量总耗时至少比现有逐份串行操作缩短 50%。
- 效率测试同时要求零重复草稿、零重复解析结果、零自动发布和零连接池耗尽。

## 14. 兼容与回退

- 现有单文件和逐份审核流程继续可用；批量入口不可用时不影响单项处理。
- 新 API 不改变现有导入、解析、物化、校验和发布接口语义。
- 任务页面只组合现有领域服务，不直接修改不可变源行或发布数据。
- 后续若引入 Worker，只替换“领取 queued 项目”的执行者，任务、项目、幂等和 API 状态模型保持不变。
- 回退前端入口后，已经创建的草稿和待发布版本仍能在现有日期审核页继续处理。

## 15. 完成定义

本功能完成需要同时满足：

1. 用户可以从多文件导入队列创建、确认、暂停、恢复并完成批量审核任务；
2. 合格文件不需要逐份点击即可到达待发布；
3. 冲突、警告、阻断和状态变化全部转人工，且原因明确；
4. 刷新和网络异常不会伪造完成或创建重复结果；
5. 不存在批量自动发布或自动覆盖路径；
6. 全部单元、集成、端到端、响应式和效率验收通过。
