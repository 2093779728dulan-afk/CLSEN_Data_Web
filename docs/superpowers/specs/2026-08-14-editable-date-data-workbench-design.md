# 可编辑日期数据工作台设计

日期：2026-08-14

## 1. 目标

把“上传 CSV 后查看和修改表格”变成产品的主流程，而不是隐藏在导入、解析、草稿和发布术语之后。

用户应当能够：

1. 上传一份或多份 CSV；
2. 在识别成功后立即看到完整原表；
3. 直接修改单元格，自动保存并撤销；
4. 从首页点击任意历史日期，重新打开对应表格；
5. 修改已发布历史数据时自动生成修订草稿，确认发布后再替换当前版本；
6. 始终保留原始文件、旧发布版本和完整修改记录。

本设计保留现有不可变原文件、解析基线、草稿、校验和发布模型，但重新组织页面和接口，使表格成为用户看到的第一层。

## 2. 已确认的产品规则

- 采用“日期数据工作台”方案，不直接覆盖已发布数据。
- 上传后自动识别日期、报表类型和编码；识别确定时自动解析并打开表格，只有不确定时才要求人工确认。
- 预览表格显示 CSV 全部原始列，并保持原始列顺序。
- 系统统计字段在表头中标识；未参与统计的原始列也保留并允许修改。
- 单元格修改自动保存，提供撤销。
- 同一日期的经营报告和退货报告使用两个标签切换，不混成一张表。
- 点击历史已发布日期时先读取当前发布版本；第一次修改自动创建修订草稿。
- 新修订只有在人工确认发布后才成为首页和统计接口读取的当前版本。
- 管理员和数据管理员可编辑；查看人员只读。
- 整体 UI 简洁，采用蓝白配色和高密度表格，不使用渐变、大型 Hero 或卡片堆砌。
- 实现后使用项目内去标识化样表完成真实本地导入、编辑和撤销，保留页面供用户体验。

## 3. 当前问题

现有系统已有逐单元格修改和审计能力，但存在四个可用性断层：

1. 上传后还要理解“识别、解析基线、生成草稿”等步骤，表格出现得太晚；
2. 首页能进入日期页，但已发布日期默认只读，不能从相同页面开始修订；
3. 原始 CSV 预览与可编辑标准字段表分离，用户无法在一张表中看到并修改全部原始列；
4. 重复上传显示为失败，且待确认批次的临时日期会污染首页状态。

这不是简单的换色问题。页面入口、数据工作副本、动态列和状态归属需要作为一个完整功能调整。

## 4. 设计契约

### 4.1 页面真正的工作

日期页只做一件核心事情：让用户查看并维护某个报告日的经营或退货明细表。

### 4.2 主要用户

- 管理员：编辑、校验、发布和处理冲突；
- 数据管理员：编辑、校验和普通发布；
- 查看人员：读取当前发布表格。

### 4.3 主要操作

有数据时，主要操作是编辑表格；无数据时，主要操作是上传 CSV。发布是完成编辑后的确认动作，不与编辑争夺首屏层级。

### 4.4 允许的界面组件

- 日期切换器；
- 经营报告/退货报告标签；
- 文件上传区；
- 高密度数据表；
- 搜索、筛选、排序和分页控件；
- 紧凑保存状态；
- 底部固定操作栏；
- 只在需要时出现的识别确认栏、错误提示和发布确认框。

### 4.5 明确拒绝的模式

- 大标题 Hero、装饰性指标卡、渐变和玻璃效果；
- 用多张卡片代替数据表；
- 把表格藏在折叠区、向导末尾或独立“高级审核”入口；
- 重复文件只有错误文本而没有可执行去向；
- 保存失败后仍显示成功值；
- 已发布数据被静默原地覆盖。

## 5. 信息架构与路由

### 5.1 首页 `/`

首页保留每日总表和产品总表。

- 管理员或数据管理员点击日期行进入 `/review/:reportDate`；
- 查看人员点击日期行进入 `/published/:reportDate`；
- 日期行状态只由已确认归属该日期的报告或活动草稿决定；
- 尚未确认日期的上传显示为独立“待归档上传”数量，不再计入某个日期的经营/退货状态。

### 5.2 日期数据工作台 `/review/:reportDate`

页面从上到下分为：

1. 紧凑工具栏：返回总表、日期、上一日/下一日、当前版本状态和保存状态；
2. 报告标签：经营报告、退货报告；
3. 条件栏：搜索、筛选、排序、差异筛选和列显示；
4. 可编辑数据表；
5. 底部固定操作栏：撤销、修改记录、运行检查、确认发布。

无数据时，第 3–5 项替换为上传区。上传成功后上传区立即收起并显示表格。

### 5.3 已发布日期 `/published/:reportDate`

查看人员获得只读版本。可写角色从首页统一进入 `/review/:reportDate`，不需要先打开只读页再寻找编辑入口。

## 6. 上传到表格的数据流

### 6.1 自动路径

1. 客户端上传原文件，后端保存不可变文件并计算内容摘要；
2. 后端检查重复内容；
3. 后端执行识别；
4. 当识别响应给出日期、报表类型和编码，且规则集没有返回需要人工确认的提示时，后端自动确认并解析；
5. 后端基于解析基线自动创建活动草稿；
6. 客户端读取草稿表格架构与第一页数据并显示编辑器。

自动路径必须由一个幂等的编排命令驱动，不能依赖浏览器按顺序发送多个不可恢复的写请求。刷新或网络重试不得创建重复草稿。

### 6.2 需要确认的路径

识别不确定时仍显示原始表格预览，但顶部出现紧凑确认栏，包含：

- 识别日期；
- 报表类型；
- 编码；
- 识别提示。

用户确认后继续自动解析并生成草稿。确认前允许查看，不允许编辑或发布。

### 6.3 批量上传

每份文件独立执行识别。识别确定的文件按其确认日期进入对应日期工作台；识别不确定的文件进入“待归档上传”。客户端批量队列只反映服务器状态，不作为唯一恢复来源。

## 7. 完整原始列模型

现有解析源行的 `decoded_fields` 已保存完整原始键值，但现有版本表主要保存标准化业务字段。为了让全部原始列可编辑，需要增加版本化表格架构和扩展字段存储，而不是修改不可变源行。

### 7.1 表格架构

每个版本保存有序列定义：

- 稳定列 ID；
- 原始表头；
- 显示顺序；
- 推断数据类型；
- 对应的标准统计字段，可为空；
- 是否为关键固定列；
- 是否参与校验与统计。

若一个版本合并了不同表头的多个来源，架构按首次出现顺序取并集；某来源缺少的列显示为空值。CSV 中的重复表头继续作为结构错误阻断解析，避免两个同名列在编辑和统计时产生歧义。

### 7.2 单元格值

- 映射到标准业务字段的列继续使用现有强类型字段和校验逻辑；
- 未映射的原始列使用版本化扩展单元格存储；
- 表格 API 把两类字段组合成同一个有序行；
- 原始值始终来自解析证据，当前值来自草稿的修改视图；
- 发布快照同时冻结标准字段和扩展字段，保证历史版本可重现。

### 7.3 统计边界

只有映射到标准业务字段的列影响首页、产品表和经营统计。扩展列的修改被保存和发布，但不会意外进入统计。表头用简洁标记区分“统计字段”和“原始字段”。

## 8. 编辑、自动保存与撤销

### 8.1 编辑交互

- 单击单元格进入编辑；
- Enter 保存并下移，Tab 保存并右移，Escape 放弃未保存输入；
- 失焦触发自动保存；
- 单元格保存时显示细小进度标记，不阻塞其他非冲突单元格；
- 页面右上角汇总显示“保存中、已保存、保存失败”。

### 8.2 并发控制

每次保存携带版本头、行版本和上次已知字段修订。服务器使用乐观并发：

- 预期版本一致时写入修改记录并返回新版本头；
- 同一单元格已被他人修改时返回冲突和服务器当前值；
- 客户端保留用户输入，要求选择采用服务器值或重新提交当前输入；
- 不允许最后写入者静默覆盖。

### 8.3 撤销

“撤销上次修改”恢复当前用户最近一次仍可撤销的字段修改，并创建新的恢复记录，不删除历史。单元格详情也可针对该字段恢复到原始值或指定历史值。

页面刷新后撤销能力从服务器修改历史恢复，不依赖浏览器内存。

### 8.4 保存失败

失败单元格保留未提交输入并标红，提供重试。存在未成功保存的单元格时禁止确认发布。

## 9. 历史日期修订

进入已有发布版本且没有活动草稿的日期时，页面先显示当前发布数据。

第一次尝试修改时，客户端调用幂等的“从当前发布创建修订草稿”命令。命令验证当前发布指针没有变化，然后创建以该版本为父版本的活动草稿。第一次单元格修改只在草稿创建成功后提交。

若已有活动草稿，直接恢复该草稿。若当前发布已被他人替换，页面刷新到新版本并提示用户，不基于过时版本创建草稿。

确认发布后：

- 当前发布指针原子切换到新版本；
- 旧版本保持不可变并可查看；
- 首页与产品统计只读取新当前版本；
- 草稿的修改历史、验证结果和发布说明继续保留。

## 10. 重复文件与待确认上传

### 10.1 重复文件

服务器返回结构化重复结果，而不是普通失败：

- 已有批次 ID；
- 实际报告日期；
- 报表类型；
- 当前阶段；
- 可进入的工作台 URL。

客户端显示“该文件已存在”，并提供“打开已有表格”。重复文件不进入失败队列，也不沿用本次选择的临时日期。

### 10.2 待确认上传

上传命令不再用页面当前日期永久污染批次归属。识别日期在人工确认前属于候选日期；首页日期状态只统计确认后的归属。

现有错误归属的未确认批次通过一次受控迁移或修复命令转入“待归档上传”，保留文件、批次 ID 和审计历史。

## 11. 视觉规范

### 11.1 色彩

- 页面背景：白色或极浅蓝灰；
- 主色：清晰的中深蓝；
- 表头：浅蓝背景；
- 边框：低对比灰蓝；
- 成功、警告和错误色只用于真实状态。

不使用渐变、发光、玻璃、装饰性阴影或大面积深色块。

### 11.2 密度与层级

- 桌面端以一屏尽量显示更多数据行为目标；
- 表头和关键身份列固定；
- 行高保持紧凑但满足点击与键盘操作；
- 工具栏使用明确中文标签，不使用含糊的“概览”“洞察”等词；
- 发布、删除行等高影响操作与普通编辑在视觉上分开。

### 11.3 响应式

桌面端是主要编辑环境。窄屏不把所有列挤压成不可读卡片，而是保留关键列并允许横向滚动；底部操作栏保持可见。移动端查看可用，但不以复杂批量编辑为首要目标。

## 12. 权限

- `admin`：上传、编辑、撤销、校验、普通发布及管理员冲突操作；
- `data_manager`：上传、编辑、撤销、校验和普通发布；
- `viewer`：读取当前发布表格，不能创建修订草稿或写入修改。

服务端仍是权限最终裁决者。隐藏按钮不能替代接口授权。

## 13. 状态与错误处理

必须实现并可测试以下状态：

- 首次加载；
- 无数据待上传；
- 上传中；
- 自动识别与解析中；
- 等待识别确认；
- 草稿可编辑；
- 当前发布只读、首改建草稿中；
- 单元格保存中、已保存、失败和冲突；
- 校验未运行、通过、警告和阻断；
- 发布中与发布成功；
- 重复文件并可打开已有表格；
- 离线；
- 无编辑权限；
- 空表与超宽表。

## 14. 接口边界

接口应围绕用户任务组合，避免客户端重新拼装内部状态机：

- 上传并启动识别；
- 查询上传编排状态；
- 确认识别并创建工作副本；
- 读取日期报告工作台；
- 从当前发布幂等创建修订草稿；
- 更新一个标准或扩展单元格；
- 撤销最近一次修改；
- 读取修改历史；
- 校验和发布。

工作台读取响应一次返回页面需要的报告标签状态、版本头、列架构、分页行、保存权限和可用操作。原始文件下载与不可变证据接口继续独立存在。

## 15. 测试与验收

### 15.1 后端

- 自动编排幂等性和失败恢复；
- 完整原始列与顺序持久化；
- 标准字段与扩展字段编辑；
- 乐观并发冲突；
- 撤销审计；
- 已发布首改自动建修订草稿；
- 发布指针原子切换；
- 重复文件结构化恢复；
- 未确认日期不污染每日总表；
- 角色权限。

### 15.2 前端

- 上传成功后直接显示表格；
- 识别不确定时显示确认栏；
- 全部原始列、原顺序和统计字段标记；
- 键盘编辑、自动保存、失败重试和撤销；
- 页面刷新恢复草稿和服务器撤销历史；
- 经营/退货标签切换；
- 历史发布首改建草稿；
- 重复文件打开已有表格；
- 加载、空、错误、离线和只读状态；
- 蓝白高密度布局与窄屏横向滚动。

### 15.3 真实本地体验

实现通过自动化门禁后，使用仓库内去标识化经营报告和退货报告样表：

1. 导入到一个明确的本地体验日期；
2. 确认上传后直接进入可编辑表格；
3. 修改一个不含敏感信息的单元格并确认自动保存；
4. 执行一次撤销并确认值恢复；
5. 刷新页面并确认工作副本仍可恢复；
6. 保留该日期工作台页面供用户体验。

不使用正式数据，不删除现有批次，不为了演示绕过权限、校验或版本规则。

## 16. 实施范围边界

本轮包含日期工作台、完整原始列编辑、自动保存、撤销、历史修订、重复恢复、日期状态修复和蓝白 UI 收敛。

本轮不包含公式、跨单元格粘贴、拖拽填充、任意工作表、多级透视表或 Excel 文件格式支持。CSV 仍是导入格式；这些高级电子表格能力只有在实际需要时再独立设计。

## 17. 完成标准

只有同时满足以下条件才算完成：

- 用户上传后无需理解内部证据链即可看到表格；
- 日期页的首要视觉对象是可编辑数据表；
- 全部原始列可见、可编辑、可自动保存和撤销；
- 历史已发布数据不会被原地覆盖；
- 重复文件和待确认日期不再制造误导状态；
- 所有角色、错误和并发状态有明确结果；
- UI 符合简洁蓝白、高密度且产品专用的设计契约；
- 自动化测试通过，并完成一次真实本地样表体验。
