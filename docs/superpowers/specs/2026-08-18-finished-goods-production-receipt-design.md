# 成品生产订单与完工入库设计（第一期）

日期：2026-08-18

最近优化：2026-08-19

状态：原业务范围已批准，但实施继续暂停；2026-08-20 起稳定商品身份完全由 P0 商品目录拥有，本规格须在 P0 Milestone A 后生成 successor 并再次批准才可执行

范围：内部广州工厂的成品数量与完工入库第一期；完整供应链见 `docs/superpowers/plans/2026-08-18-end-to-end-sku-supply-chain-roadmap.md`

## 1. 背景

当前业务从运营下单开始，内部广州工厂通常在 7～30 天后分批完成成品，随后还要连接工厂出货、30～40 天海运在途、Amazon FBA 入库、销售日报和退货日报。本文只定义第一期的两件事：记录运营下达的成品生产数量，以及把工厂实际完工数量经过审核后计入广州工厂成品仓。出货、在途、FBA 和 Amazon 日报仍是总体项目的必需阶段，不能因第一期验收而视为已经完成。

目前没有既定 Excel 表格。系统因此提供标准模板，运营和工厂继续使用 Excel 工作，并把文件上传到当前 Web 应用。设计借鉴 ERPNext 的商品变体、业务单据、仓库和库存流水思想，但不复制或嵌入 ERPNext 源码，也不在第一期部署另一套 ERP。

现有批量审核工作流继续负责通用的上传体验、持久状态、幂等、审计和审核交互模式。生产订单与库存属于新的业务领域，不能硬塞进面向日报解析和发布的数据表；新模块复用现有基础能力和组件，拥有独立的生产及库存领域数据。

## 2. 目标与非目标

### 2.1 目标

- 运营使用标准 Excel 批量创建成品生产订单。
- 一张生产订单包含多个具体到款号、颜色和尺码的 SKU。
- 系统为每张正式订单生成稳定且唯一的内部订单号，并保留可选外部单号。
- 系统按订单日派生 D+7～D+30 自然日生产窗口，并显示窗口前、窗口内和逾期三态。
- 工厂使用标准 Excel 按天批量上报多个订单、多个 SKU 的完工数量。
- 完工数据经过校验和人工审核后才增加广州工厂成品仓库存。
- 自动计算累计完工、待审核、未完工、超额数量和完工状态。
- 未知 SKU 进入人工匹配流程，不自动污染 P0 商品目录；生产端只能选择已批准身份或等待目录后继版本批准。
- 订单变更、审核、库存入账和冲销均可追溯且不可静默覆盖历史。
- 保持稳定的 `sku_id`、单据号和库存流水边界，为后续出货、在途、FBA、销售和退货模块提供接口。

### 2.2 非目标

- 不管理原材料、辅料、BOM、工艺路线、裁剪、车缝、包装或质检工序。
- 不做产能排程、工价、成本核算、采购、应收应付或财务总账。
- D+7～D+30 只作为按自然日派生的进度观察窗口；第一期不维护人工预计完工日，不因超窗阻断真实完工或入库。
- 本文第一期不做工厂出货、海运在途、FBA 入库、销售和退货数据串联；这些能力仍属于总体项目要求，按全链路路线图的 E0/C/D/E 阶段交付。
- 不支持箱、套、公斤等多单位换算；库存统一按“件”记录。
- 不在第一期引入 ERPNext 或 Odoo 运行时，也不建立双系统同步。
- 不新增用户角色或另一套权限模型。

### 2.3 总体业务追溯边界

| 总体阶段 | 本文是否交付 | 验收边界 |
| --- | --- | --- |
| 运营订单与工厂订单表 | 是 | 正式订单、内部订单号、D+7～D+30 派生窗口、固定工厂 XLSX 导出 |
| 7～30 天分批完工与广州入库 | 是 | 三态窗口观察、实际完工日期、审核、入库、流水、余额 |
| 出货要求、出货表与广州库存扣减 | 否 | 全链路路线图 C 阶段 |
| 30～40 天海运在途 | 否 | 全链路路线图 C 阶段 |
| FBA 分批实收与短溢收对账 | 否 | 全链路路线图 D 阶段 |
| 销售/退货 CSV 按稳定 SKU 串联 | 否 | 全链路路线图 E 阶段；现有日报功能只做回归保护 |

第一期完成定义只能称为“订单到广州成品仓闭环”，不能称为完整供应链闭环。

## 3. 第一期产品决策

第 1～12 项继承原批准规格；第 13 项及以后是 2026-08-19 可行性评审加入的安全性、可恢复性和验收细化，已纳入同一正式批准规格且不扩大第一期业务边界。

1. 采用当前应用内的“精简 ERP 模型”，复用现有上传、审核、权限和审计能力。
2. 生产订单使用系统内部订单号；外部单号为可选辅助字段，不能作为内部关联主键。
3. 一份生产订单文件只创建一张订单；订单内每行代表一个 SKU。
4. 一份完工入库文件可以同时包含多个生产订单和多个 SKU，并适合按天汇总上传。
5. 完工上传后先校验和人工审核，审核通过后才正式入库。
6. 允许超额完工，但必须显示警告并由审核人员明确确认。
7. 下单和完工数量统一为“件”，只能使用正整数。
8. 未知 SKU 不自动创建；必须由授权用户匹配当前批准 P0 目录中的 SKU，或先在商品目录流程批准后继版本再返回生产流程。
9. 生产订单由上传者完成预览确认后生效，第一期不强制另一人复核订单。
10. 生效订单通过订单变更记录调整数量，不直接覆盖历史。
11. 完工记录保存实际完工日期；系统另存上传时间、审核时间和入账时间。
12. 权限沿用当前用户、站点范围、菜单权限和批量审核授权规则。
13. `sku_id` 表示具体款号、颜色和尺码的实物变体。同一站点不能存在两个正式 `sku_id` 表示同一规范化款色码；停用不释放该身份，冲突必须阻断并人工处理。
14. SKU 纠错通过同一 `sku_id` 下的新不可变 revision 完成；历史事实继续绑定原 revision，旧展示编码保留为别名。第一期不合并两个 `sku_id`，也不迁移它们之间的历史事实。
15. 订单确认时固化工厂导出使用的 SKU 编码，并建立“工厂完工 Excel”来源别名，保证 7～30 天后即使展示编码改变仍能回匹配。
16. 撤回的完工批次释放活动文件去重占位；同一原文件允许重新创建新批次，但历史撤回批次继续保留。
17. 警告确认必须绑定锁内事实快照，而不只是警告代码。事实变化后即使代码相同，也必须重新确认。
18. 生产窗口固定为订单日 D 的 D+7～D+30 自然日，窗口状态按站点当前业务日期派生，不作为入账阻断条件。
19. 校验成功与提交审核是两个状态边界；正式审核必须绑定无副作用审核预检返回的整组投影摘要。
20. `outcome_unknown` 不是终态；带 fencing token 的租约 reconciler 必须把它收敛为 `completed` 或 `retryable`。
21. 完工回传必须携带工厂声明其依据的导出版本和订单修订号；订单后来调量时保留该回传证据，并按当前订单事实重新判断超额。

## 4. 领域边界与总体流程

新模块命名为“生产与成品入库”，包含五项职责：

- P0 商品目录只读选择与 production 来源别名；
- 成品生产订单及订单变更；
- 完工文件上传、匹配、校验和审核；
- 成品入库单与冲销；
- 广州工厂成品仓的库存流水和余额。

总体流程为：

`运营订单 Excel → 文件校验与 SKU 匹配 → 上传者确认 → 正式生产订单 → 工厂完工 Excel → 订单/SKU/数量校验 → 人工审核 → 成品入库单 → 广州工厂成品仓库存流水`

订单确认后，系统在订单页面显示派生生产窗口，并可导出固定契约的工厂生产订单 XLSX。完工模板必须填写导出中的内部订单号，从而避免用文件名、外部单号或可修改备注建立业务关联。

## 5. 商品身份消费边界（由 P0 拥有）

生产领域不再创建、修订、合并或删除 `product_styles`、`product_skus`、`product_style_revisions`、`product_sku_revisions`、identity reservation 或 Seller SKU mapping；这些表、算法、权限和审核流程完全由《商品款式主档与变体趋势基础设计（P0）》拥有。生产订单只能消费当前已批准目录中的稳定 `style_id/sku_id/style_revision_id/sku_revision_id`，并在订单确认、完工匹配、入库明细和库存来源中冻结当时四元组及展示快照。目录后续向前纠错不能改写历史生产事实。

生产来源编码只允许作为独立的工厂/运营匹配 evidence 与 alias sidecar，必须包含站点、source kind、规范字节、目标 `sku_id`、采用的目录版本和审核来源；它不能复用 P0 带 Amazon scope 的 Seller SKU mapping 唯一键，也不能因未知字符串自动创建身份。运营订单无法唯一命中已批准 SKU 时进入待匹配：用户可以选择 P0 已有 SKU，或离开生产流程进入 P0 商品目录创建并批准后继版本，再回来重新解析；生产页面不得内嵌第二套“创建 SKU”命令。

只有具体变体可以进入订单和库存。款号、颜色、尺码、展示编码、Seller SKU、FNSKU、ASIN 或标题都不能代替稳定 ID；生产领域第一期仍不提供 SKU merge、事实重绑或跨 `sku_id` 迁移接口。

## 6. 核心数据模型

所有业务实体均按当前站点隔离。实现命名可遵循项目约定，但必须表达以下实体和约束。

### 6.1 仓库

第一期只有一个可入账仓库“广州工厂成品仓”，内部代码固定为 `guangzhou_finished_goods`，数据库以 `(site_id, warehouse_code)` 唯一。数据模型仍使用稳定 `warehouse_id`，避免以后增加出货仓和海运在途仓时修改库存流水结构。第一期界面不提供通用仓库配置系统；并发首次使用只能幂等得到同一仓库。

### 6.2 生产订单

生产订单头保存内部订单号、可选外部单号、订单日期、单据状态、创建人、确认时间、关闭或取消原因及乐观并发修订号。内部订单号格式固定为 `PO-YYYY-NNNNNN`，其中 `YYYY` 取订单日期年份；同一站点内 `(site_id, internal_order_number)` 唯一。

年度序列表以 `(site_id, calendar_year)` 为唯一键，在订单确认事务内锁行并分配六位正整数序号。同一导入或命令重试返回原订单号，不再次取号；已经成功分配给正式订单的号码永不复用。系统不承诺无间隙序列，超过 `999999` 时固定返回 `409 production_order_sequence_exhausted`，不创建订单或消耗不合法号码。数据库同时约束年度序列唯一键、站点订单号唯一键和一份订单导入最多确认一张订单。

生产窗口不是可编辑字段：`expected_completion_from = order_date + 7 个自然日`，`expected_completion_to = order_date + 30 个自然日`，首尾均包含。查询 API 和导出按订单日期派生并返回这两个 `DATE`，不使用工作日、小时差或服务器本地时区。

生产订单明细保存订单、`sku_id`、确认时的 `sku_revision_id`、`factory_sku_code_snapshot`、下单数量和可选备注。同一订单中一个 SKU 只能存在一条明细；导入文件出现重复 SKU 时必须让用户合并或修正，不能静默生成两条相同明细。

订单导入批次与完工导入批次都必须保存本次上传自己的安全原文件名和声明 `media_type` 快照。内容寻址的 `raw_files` 可以被相同字节的多次上传复用，因此后续解析或 resume 不能把 `raw_files` 上第一次上传者的元数据误当成本批次元数据；必须用“批次元数据 + raw file 内容”重建同一 `WorkbookUpload` 校验输入。

订单变更记录保存明细、调整前数量、调整后数量、原因、操作人和时间。调整后的数量不能小于该明细已审核且未冲销的累计完工数量。

### 6.3 完工上传批次与明细

上传批次保存原始文件引用、本次上传的安全原文件名和声明 `media_type` 快照、SHA-256 摘要、上传人、上传时间、解析状态、业务状态、修订号和各类行数统计。解析状态至少区分 `uploaded | parsing | parsed | parse_failed`；解析失败保存安全原因及明确的 `recoverable` 标记，只有可恢复失败才能对同一批次重新解析。原始文件沿用当前不可变文件存储及站点隔离规则。

上传明细保存原始行号、内部订单号、工厂回传的导出版本、工厂声明其依据的订单修订号、原始 SKU 编码、匹配后的订单明细、`sku_id` 和 `sku_revision_id`、本次完工数量、实际完工日期、原始辅助字段、校验结果、警告、审核决定、原因及时间。

明细进入 `validated` 时必须保存版本化 `validation_digest`。摘要对规范 JSON 计算 SHA-256，至少绑定摘要 schema 版本、站点、批次和行 ID、规范化原始业务值、订单/订单明细 ID 与 revision、`sku_id`/`sku_revision_id`、匹配来源、校验原因码和警告。提交审核前服务端重新读取事实并复算；摘要变化的行不得转换为 `ready_for_review`，而应固定返回 `409 stale_completion_validation` 并重新校验。

原始单元格值保留在受控的导入证据中；正式订单、SKU 和库存查询不得依赖未经规范化的原始字符串。

### 6.4 入库单与库存

每次成功的审核入账命令生成一张成品入库单及其明细。入库明细绑定来源上传行、生产订单明细、`sku_id` 和交易时点 `sku_revision_id`，并复制工厂回传的导出版本和订单修订号证据。一个上传批次可以因分次审核产生多张入库单，但同一上传行最多成功入账一次。

库存流水至少保存仓库、`sku_id`、有符号数量变化、业务日期、入账时间、来源单据、来源明细和可选的被冲销流水。正式流水不可更新或删除。

入库单详情是只读追溯资源，必须返回入库单头、每条入库明细、来源完工批次及原始行、生产订单及明细、`sku_id`/`sku_revision_id`、仓库、正向流水和可选冲销流水的稳定定位符。库存流水查询必须返回该入库单定位符，不能只返回无法解析的文本来源类型或展示 SKU。

库存余额按“站点 + 仓库 + SKU”保存或计算。若使用余额表加速查询，库存流水仍是业务事实来源；余额更新、流水写入和来源行状态更新必须在同一数据库事务内完成。

数量字段使用整数类型。订单和完工输入必须大于零；库存流水允许负数以表达冲销以及未来出库。

所有同时保存 `site_id` 和业务实体 ID 的关系都使用复合外键校验站点一致性，例如 SKU revision 到 SKU、订单明细到订单/SKU/具体 SKU revision、完工行到订单明细/SKU/具体 SKU revision、入库明细到来源行、库存流水到仓库/SKU。`product_skus.current_revision` 只是数值版本，不建立到 revision 表的反向外键。仅在应用层添加 `site_id` 过滤不足以满足站点隔离。

第一期余额保持非负。进入出货阶段前必须采用全链路路线图的补偿策略：若原入库对应库存已经流向下游，先原子冲销或调整下游调拨，再冲销原入库，不能直接更新旧流水。

## 7. 状态模型

### 7.1 生产订单状态

单据状态为：

- `active`：已确认并可接收完工；
- `closed`：人工关闭，不再接受普通完工；
- `cancelled`：取消且从未产生已审核入库。

完工状态由有效入库数量计算，不作为可人工随意修改的事实：

- `not_started`：累计完工为零；
- `partially_completed`：累计完工大于零且小于下单数量；
- `completed`：累计完工等于下单数量；
- `over_completed`：累计完工大于下单数量。

关闭和完工状态独立显示。例如，允许带原因关闭一个仍未全部完工的订单，但不能把它伪装为已完工。

生产窗口状态同样是独立派生维度。以站点配置时区的当前业务日期 `today` 与订单日期 D 比较：

- `not_due`：`today < D+7`；
- `in_window`：`D+7 <= today <= D+30`；
- `overdue`：`today > D+30`。

窗口状态不落成可人工修改的业务事实。只有仍有未完工数量且单据不是 `cancelled` 的订单返回窗口三态；已完成或已取消订单返回 `null`。页面同时显示单据状态、完工状态和窗口状态，单据为 `active` 的 `overdue` 订单显示醒目的逾期徽标；第一期不建立独立提醒队列、通知任务或审批阻断。仍未完工但已关闭的订单保留窗口位置用于追溯，不产生活动提醒。订单日期只能在导入预览阶段修正，正式订单确认后不可修改，因此窗口边界也随正式订单固定。

### 7.2 完工批次和明细状态

批次状态固定为：

- `uploaded`：文件已保存，正在或等待校验；
- `needs_attention`：存在匹配或校验问题；
- `validated`：全部可处理行已经校验，等待上传者提交审核；
- `pending_review`：全部可处理行已经提交审核；
- `partially_reviewed`：一部分行已有决定，仍有待审核行；
- `completed`：全部可处理行已有最终决定；
- `withdrawn`：在首次批准前由上传者撤回。

明细状态固定为：

- `needs_match`：SKU 尚未唯一匹配；
- `invalid`：存在阻断错误；
- `validated`：校验通过但尚未提交审核；
- `ready_for_review`：校验完成并已提交审核；
- `approved`：已生成有效入库；
- `rejected`：已填写原因并拒绝；
- `reversed`：原批准入库已经冲销。

提交命令先复算每行 `validation_digest`，再把摘要未变化的 `validated` 明细原子转换为 `ready_for_review`；任何摘要变化固定返回 `409 stale_completion_validation` 且整批零状态变化。只有 `ready_for_review` 明细可以进入 `review-preview` 并被批准或拒绝。状态转移由服务端校验，客户端显示状态但不是权威来源。

## 8. Excel 契约

工作簿解析边界显式接收三项输入：不可变 `content` 字节或只读二进制流、未经信任的 `original_filename` 和请求 `media_type`。服务端只把原文件名的安全 basename 用于扩展名校验、显示和审计，不把它当作路径或业务主键；扩展名、media type 与实际 ZIP/OOXML 内容必须分别校验。允许的 media type 固定为官方 XLSX 类型 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`，以及在内容和 `.xlsx` 扩展名均通过严格校验时兼容 `application/octet-stream`；缺少扩展名、其他 media type 或内容签名不符均返回稳定错误。

模板和工厂导出统一返回可测试的 XLSX artifact，至少包含 `content`、安全 `filename` 和 `media_type`；`media_type` 固定为官方 XLSX 类型，HTTP 下载名从 artifact 的 `filename` 生成安全 `Content-Disposition`，不能由请求原文件名覆盖。解析测试必须分别覆盖内容、原文件名、media type，导出测试必须同时断言三个 artifact 字段，而不能只断言工作簿字节。

### 8.1 成品生产订单模板

系统提供 `.xlsx` 模板，唯一可见工作表固定为 `成品生产订单`。一份文件代表一张生产订单，同一文件内订单日期和外部单号必须一致。第一期字段为：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 外部订单号 | 否 | 仅作检索和辅助核对，不作为关联主键 |
| 订单日期 | 是 | 每行一致且能解析为日期 |
| SKU编码 | 是 | 按“运营订单 Excel”来源匹配 |
| 款号 | 是 | 用于核对已批准 P0 SKU 或生成待匹配建议 |
| 颜色 | 是 | 用于核对已批准 P0 SKU 或生成待匹配建议 |
| 尺码 | 是 | 用于核对已批准 P0 SKU 或生成待匹配建议 |
| 下单数量 | 是 | 正整数，单位为件 |
| 备注 | 否 | 不参与身份匹配 |

模板只允许指定的工作表和表头结构；两份导入模板及工厂导出的精确表头一律使用无空格的 `SKU编码`。系统不依赖文件名识别订单，不把合并单元格或颜色格式当作业务数据。

第一期只接受 `.xlsx`，拒绝 `.xls`、`.xlsm`、公式、外部链接、隐藏数据表和非标准表头。工作簿最多包含 10,000 条数据行、16 列、128 个 ZIP 条目和 200 MiB 解压后内容，并继续受全局 `APP_STORAGE_MAX_UPLOAD_BYTES` 限制。解析使用只读模式和安全 XML 解析器。模板把编码及备注列预设为文本；导出把所有用户文本显式写成 OOXML 字符串单元格而不是公式单元格，逻辑值保持逐字符不变，因此以 `= + - @` 开头的合法 SKU 可以安全导出并原样回传。

上传后先生成预览。未知 SKU 必须处理，重复 SKU 必须修正，所有阻断消除后由上传者确认。相同外部单号或高度相似的“订单日 + SKU + 数量”已有正式订单时返回 `possible_duplicate_order` 警告；其 SHA-256 指纹必须绑定候选订单 ID/revision、规范化当前行集合和导入 revision。确认请求提交精确 `{code, fingerprint}`，事务锁内重算，候选或输入变化后旧确认失效。确认事务重新校验并生成内部订单号、订单和明细。重复确认使用同一幂等结果，不能创建第二张订单。

### 8.2 工厂生产订单导出

工厂导出版本固定为 `production_factory_order_v1`，格式为 `.xlsx`，只包含一个可见工作表 `工厂生产订单`。首行必须按以下顺序精确使用这些表头，不能因页面语言、可选值为空或后续模块上线而增删、改名或重排：

| 顺序 | 字段 | 规则 |
| --- | --- | --- |
| 1 | 导出版本 | 每行固定为 `production_factory_order_v1` |
| 2 | 系统生产订单号 | 每行相同，使用正式内部订单号 |
| 3 | 订单修订号 | 每行相同，使用本次导出的订单 revision |
| 4 | 外部订单号 | 可空，仅供工厂核对 |
| 5 | 订单日期 | `yyyy-mm-dd` |
| 6 | 生产窗口开始日 | 订单日期 D+7 自然日，`yyyy-mm-dd` |
| 7 | 生产窗口结束日 | 订单日期 D+30 自然日，`yyyy-mm-dd` |
| 8 | SKU编码 | 使用订单明细的 `factory_sku_code_snapshot`，不能改用当前展示编码 |
| 9 | 款号 | 使用订单明细绑定的 SKU revision |
| 10 | 颜色 | 使用订单明细绑定的 SKU revision |
| 11 | 尺码 | 使用订单明细绑定的 SKU revision |
| 12 | 下单数量 | 当前订单 revision 的有效正整数数量，单位为件 |
| 13 | 备注 | 可空，不参与身份匹配 |

一份导出只对应一张正式订单，每条订单明细一行，并按稳定订单明细 ID 升序排列。下载文件名固定为 `production-order-{internal_order_number}-r{revision}.xlsx`；HTTP 使用安全的 `Content-Disposition`。同一订单 revision 的重复导出必须得到相同业务单元格值，订单调量后以新 revision 和新文件名导出；已经下发的旧文件可通过其中的订单号、revision、固定 SKU 编码和订单变更历史核对，不能被新 revision 解释成当前数量。

导出不得包含公式、宏、外部链接、隐藏工作表或隐藏数据；所有用户文本使用第 8.1 节的公式安全字符串单元格编码，不添加会改变 SKU 逻辑值的前缀。该导出是工厂填写完工模板的来源，不能以页面临时列、CSV 或任意列顺序替代。

### 8.3 完工入库模板

系统提供唯一可见工作表固定为 `完工入库` 的 `.xlsx` 模板。一份文件允许包含多个订单和 SKU，每行是一条本次完工记录：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 系统生产订单号 | 是 | 必须属于当前站点 |
| 工厂订单导出版本 | 是 | 第一版固定为 `production_factory_order_v1` |
| 工厂订单修订号 | 是 | 必须是该订单真实存在且不晚于当前 revision |
| SKU编码 | 是 | 按“工厂完工 Excel”来源匹配 |
| 本次完工数量 | 是 | 正整数，单位为件 |
| 实际完工日期 | 是 | 保存业务日期，不以上传时间代替 |
| 款号 | 否 | 辅助核对；与正式 SKU 冲突时警告 |
| 颜色 | 否 | 辅助核对；与正式 SKU 冲突时警告 |
| 尺码 | 否 | 辅助核对；与正式 SKU 冲突时警告 |
| 工厂备注 | 否 | 不参与身份匹配 |

“工厂订单修订号”是工厂回传的生产依据证据。第一期工厂导出保持无副作用的 GET，不建立浏览器下载/下发台账，因此系统只证明该 revision 在订单历史中真实存在且不晚于当前 revision，不声称证明工厂确实下载或收到过该文件。若未来业务要求下发签收证据，应另增有幂等命令的不可变下发单，而不能把 GET 下载日志冒充签收事实。

系统分别记录实际完工日期、文件上传时间、审核决定时间和正式入账时间。工厂订单修订号小于当前订单 revision 时保留原值并产生 `stale_factory_order_revision` 警告；审核仍以当前有效下单量计算超额，不能用旧 revision 绕过调量。不存在或大于当前 revision 的修订号，以及不支持的导出版本，均为阻断错误。

## 9. 校验、重复检测与审核

### 9.1 阻断错误

以下情况不能提交审核或入账：

- `missing_required_field`：必填字段缺失；
- `invalid_date`：日期格式无效；
- `invalid_quantity`：数量不是正整数；
- `unsupported_factory_order_export_version`：工厂回传的导出版本不是当前支持版本；
- `factory_order_revision_not_found`：回传 revision 不属于该订单或尚不存在；
- `order_not_found`：订单不存在或不属于当前站点；
- `order_cancelled`：订单已经取消；
- `sku_unmatched`：SKU 无法匹配；
- `sku_ambiguous`：SKU 匹配到多个候选；
- `sku_not_on_order`：SKU 不属于指定生产订单；
- `line_already_posted`：同一来源行已经成功入账；
- `permission_denied`：当前用户没有现有权限体系授予的操作权限。

### 9.2 必须确认的警告

以下情况允许进入审核，但批准前必须显示并单独确认：

- `completion_overage`：本次入账会使累计完工超过下单数量；
- `possible_duplicate`：与历史记录存在疑似重复；
- `order_closed`：订单已经关闭；
- `sku_attribute_mismatch`：文件中的款号、颜色或尺码与匹配到的正式 SKU 不一致。
- `stale_factory_order_revision`：工厂依据的订单 revision 早于当前 revision，需核对后续调量记录。

每条警告除了稳定代码，还包含基于当前事实生成的 `warning_fingerprint`。指纹使用排序键、稳定数组顺序和明确整数/日期表示的规范 JSON，再计算 SHA-256；至少覆盖订单和订单明细 revision、`sku_id`/`sku_revision_id`、当前有效累计入库量、相关疑似重复行 ID、订单状态以及产生警告的字段值。批准请求提交逐条 `{code, fingerprint}` 确认，服务端在锁内重新计算并精确比较。预览后新增入库、订单变更、SKU revision 变化或状态变化时，即使警告代码没有变化，也不能沿用过期确认。

审核多行时，警告必须按“当前有效累计量 + 本命令选中批准行的投影总量”计算，不能逐行孤立计算。同一订单明细在一个命令中选中多行时，投影按稳定行 ID 顺序累计；使总量首次超过订单数量的行及后续相关行都返回超额警告。

审核人必须先携带 `expected_revision`，用与正式审核完全相同的 1～500 条不重复决定数组调用 `review-preview`。服务端规范化决定数组，拒绝决定包含规范化原因，批准决定包含行 ID；随后返回无副作用的逐行警告、`warning_fingerprint`、批次当前 revision 和 `projection_digest`。`projection_digest` 是带 schema 版本的规范 JSON SHA-256，至少绑定站点、批次 ID/revision、排序后的完整决定集合、各行 `validation_digest`、订单/明细/SKU revision、当前有效累计量、重复候选稳定 ID 集合以及最终警告代码和指纹。

正式审核请求必须原样提交决定数组、`expected_revision`、`projection_digest` 和逐警告确认。服务端在事务锁内重放同一投影算法；任何决定、原因、revision、累计量、候选集合、警告或摘要 schema 变化都返回 `409 stale_review_projection`，且入库单、流水、余额、状态和审计均零副作用。客户端必须重新预检，不能自行计算或拼接投影摘要。

### 9.3 重复检测

同一站点、同一导入领域中，完全相同的文件摘要若已有未撤回批次，系统返回该活动批次并阻止再建。撤回批次不占用活动去重键，因此同一原文件可以创建新批次；旧批次、原文件引用和撤回审计保持不变。该规则必须由并发安全的活动去重键或 claim 表实现，不能使用永久 `(site_id, raw_file_id)` 唯一约束。内容不同但“订单 + SKU + 实际完工日期 + 数量”相同的历史行标记为疑似重复；它是需人工确认的警告，因为工厂可能在同一天确实分两次完成相同数量。

最终幂等边界是上传行的稳定 ID 和审核命令 UUID。同一行无论页面重复点击、网络重试或两个窗口并发批准，都最多产生一次有效入库。

### 9.4 审核结果

一个批次可以部分批准、部分拒绝。拒绝必须填写原因，不产生入库或库存变化。正式审核只接受已经 `ready_for_review` 且 `validation_digest` 仍有效的行；批准命令可以包含多行，任何一行在投影复核、最终校验或入账中失败时，该次命令整体不产生部分库存，用户重新预检后重试。

## 10. 入账、进度和纠错

审核入账在一个数据库事务中完成：

1. 锁定并重新读取待批准上传行、生产订单明细和相关库存余额；
2. 复核权限、状态、幂等键、订单/SKU 关系、超额和重复警告确认；
3. 创建成品入库单及明细；
4. 创建广州工厂成品仓库存流水；
5. 更新库存余额和上传行审核状态；
6. 提交事务后返回新的订单进度与库存结果。

累计完工只统计已批准且未被冲销的入库明细。页面同时显示待审核数量，但待审核、已拒绝和校验失败数量不进入正式完工或库存。

订单头同时展示订单日期、D+7/D+30 窗口边界、窗口三态、单据状态和完工状态。订单明细展示：下单数量、待审核数量、累计完工数量、未完工数量和超额数量。计算规则为：

- `未完工数量 = max(下单数量 - 累计完工数量, 0)`；
- `超额数量 = max(累计完工数量 - 下单数量, 0)`。

未审核批次可以由上传者撤回；`admin` 是否可以代为撤回必须作为显式管理动作并填写原因，普通 `data_manager` 不能撤回他人批次。已审核入库不能编辑或删除；纠错由授权用户填写原因并冲销。冲销创建与原流水方向相反、数量相等的新流水，标记原入库明细的冲销关系，并重新计算库存和订单进度。冲销本身必须幂等且保留完整审计。

入库单详情和库存流水形成双向只读追溯：从流水可以打开来源入库单，从入库明细可以打开来源完工上传行和生产订单明细；冲销详情同时显示原正向流水与反向流水。追溯始终使用稳定内部 ID，不使用展示 SKU、文件名或备注重新查找关系。

曾经产生过已批准入库的订单不能取消，即使该入库后来已经冲销；此类订单只能填写原因后关闭。关闭后的新完工属于需明确确认的警告。订单数量调整不能低于当前有效累计完工数量。

## 11. 页面与用户流程

新模块提供五个入口：

1. **商品目录选择**：只读搜索 P0 款号、颜色、尺码、展示编码并维护 production alias；处理待匹配项，缺少身份时跳转 P0 目录后继版本流程。
2. **生产订单**：上传、预览并确认订单；查看 D+7/D+30 窗口三态和订单进度；导出固定契约的工厂生产订单 XLSX；提交数量变更、关闭或取消。
3. **完工上传**：下载模板、上传文件、查看逐行校验、处理 SKU 匹配并提交审核。
4. **完工审核**：从服务端分页待办队列筛选待审核批次和明细，批量批准或拒绝；超额和疑似重复必须逐项确认。
5. **广州成品仓**：按 SKU 查看当前库存、累计入库和库存流水，并从流水打开来源入库单。

入库单详情是从库存流水进入的次级只读页面，不增加第六个主导航入口。其路由为 `/production/receipts/:receiptId`，并提供到完工上传行和生产订单明细的稳定链接；刷新后必须仅凭路由参数从服务端恢复。

完工上传使用四步流程：

`选择文件 → 自动校验 → 处理错误和警告 → 提交审核`

桌面端使用适合批量数据的紧凑表格；窄屏允许表格内部横向滚动，不能把大量字段压缩成难以核对的卡片。所有服务端错误必须返回稳定原因码和安全中文说明，页面保留用户已经完成的匹配和选择，避免因一次失败清空整个批次。

## 12. 权限与审计

第一期不新增角色。模块复用当前用户、站点隔离、菜单权限和批量审核授权规则，不建立平行的角色映射表。现有角色按当前语义映射：

- `admin`：可以访问全部生产与成品入库功能，并负责入库冲销；
- `data_manager`：可以从已批准 P0 目录选择 SKU、维护 production alias、创建和变更订单、上传及审核完工数据、查看订单和库存；不能在 production 创建、修订、合并或重绑 P0 身份，也不能执行仅限管理员的入库冲销；
- `viewer`：不能访问内部生产订单、待审核完工数据和未发布库存模块。

是否允许审核本人上传的数据，遵循当前批量审核工作流的既有规则。

审计至少记录：

- 文件上传、摘要和来源批次；
- SKU 匹配、别名绑定、明确建档、revision 纠错及其原因；
- 订单确认、数量变更、关闭和取消；
- 完工提交、批准、拒绝及警告确认；
- 入库、库存流水和冲销；
- 操作人、站点、时间、命令 UUID、变更前后 revision、投影摘要和原因。

审计事件不得包含整份文件正文、密码、数据库凭据或未清理异常堆栈。

## 13. API 与组件边界

每个 production 请求都从服务端认证依赖取得不可由客户端构造的共享 `CurrentSiteContext`，其稳定字段至少为当前 `site_id`、`site_config_version_id` 和 `reporting_timezone`。Cookie 会话、CSRF 与 RBAC 校验完成后，API、领域服务和仓储都显式传递该上下文；请求体、查询参数和自定义请求头均不接受或信任客户端提供的 `site_id`。资源 ID 先按 `CurrentSiteContext.site_id` 限定再查询，跨站 ID 不得通过“管理员参数”绕过。生产窗口的当前业务日期、日期筛选和页面日期展示复用现有 `data-calendar` 的 `reporting_timezone` 与 `site_config_version_id`，不另建一套时区或客户端日期口径。

接口路径遵循现有 FastAPI 项目约定，后端路径参数统一使用 snake_case。第一期提供以下资源边界：

- `GET /api/production/skus`：只读查询当前批准 P0 目录中的 SKU revision 和 production 来源别名；
- `GET /api/production/skus/{sku_id}/revisions`：只读分页查询 P0 不可变 SKU revision 历史；
- production API 不提供 SKU create、PATCH、merge 或 repoint；商品身份纠错只通过 P0 `/catalog` 的向前版本流程完成；
- `POST /api/production/sku-aliases`：现有写权限用户建立或修正 production 来源别名，目标必须是当前批准 P0 成员；
- `GET /api/production/templates/production-order`：下载生产订单模板；
- `POST /api/production/order-imports`：上传并创建订单预览；
- `GET /api/production/order-imports/{import_id}`：只读返回订单预览、解析状态和匹配状态，不推进解析；
- `POST /api/production/order-imports/{import_id}/resume`：从批次已保存的不可变 `raw_file` 恢复订单解析；
- `POST /api/production/order-imports/{import_id}/matches`：提交待匹配项决策；
- `POST /api/production/order-imports/{import_id}/confirm`：确认并创建正式订单；
- `GET /api/production/orders`、`GET /api/production/orders/{order_id}`：查询订单及进度；
- `GET /api/production/orders/{order_id}/factory-export`：导出含系统订单号的工厂用明细；
- `POST /api/production/orders/{order_id}/adjustments`：提交有原因的数量变更；
- `POST /api/production/orders/{order_id}/close`、`POST /api/production/orders/{order_id}/cancel`：关闭或取消订单；
- `GET /api/production/templates/completion-receipt`：下载完工入库模板；
- `GET /api/production/completion-imports`：按状态、上传人和日期分页查询批次；
- `POST /api/production/completion-imports`：上传并校验完工文件；
- `GET /api/production/completion-imports/{import_id}`：只读返回批次、解析状态、行和审核状态，不推进解析；
- `POST /api/production/completion-imports/{import_id}/resume`：从批次已保存的不可变 `raw_file` 恢复完工解析；
- `POST /api/production/completion-imports/{import_id}/matches`：提交待匹配项决策；
- `POST /api/production/completion-imports/{import_id}/submit`：提交可处理行进入审核；
- `POST /api/production/completion-imports/{import_id}/withdraw`：在首次批准前撤回批次；
- `POST /api/production/completion-imports/{import_id}/review-preview`：按本次决定集合计算无副作用的投影警告和指纹；
- `POST /api/production/completion-imports/{import_id}/review`：批量批准或拒绝并提交警告确认；
- `GET /api/production/completion-review-lines`：分页查询当前用户可审核的待办行；
- `GET /api/production/receipts/{receipt_id}`：查询入库单、明细、来源上传行、订单、SKU revision 及正反向流水定位符；
- `POST /api/production/receipt-lines/{receipt_line_id}/reverse`：管理员按行冲销错误入库；
- `GET /api/production/inventory`、`GET /api/production/inventory/ledger`：查询库存余额和流水。
- `GET /api/production/commands/{operation_token}`：命令原操作者按当前站点和 UUID 查询状态及安全结果定位符；`admin` 可在同站点代查，但必须新增审计事件，其他用户不能代查。

两个 `resume` 都是带 UUID v4 幂等键和 `expected_revision` 的写命令，只允许当前站点具有普通写权限的 `admin/data_manager` 调用，`viewer` 禁止。服务端从导入记录解析 `raw_file_id` 并重新打开已存内容；请求不得上传新工作簿、传入文件路径或指定 `site_id`，恢复不会创建新的 raw file 或导入批次。允许恢复的解析状态固定为 `uploaded`、租约已经过期的 `parsing` 和标记为可恢复的 `parse_failed`；仍持有有效租约的 `parsing` 返回安全冲突或稍后重试，永久解析错误返回原稳定原因且不重跑。`parsed` 幂等返回现有结果：同一或新的合法 UUID 都必须经过 production command claim，并写一条指向既有 import/revision 的 no-op/idempotent effect，以便命令查询恢复和防止 token 被其他语义复用；但不得取得解析 claim 或重新解析。同一 UUID 和命令摘要返回同一结果，不同摘要冲突；真正恢复解析时仍通过解析租约和 fencing token 保证只有一个 worker 写入。GET 端点在所有状态下都保持无副作用，页面必须显式调用 `resume` 才能推进解析。

`review-preview` 与正式 `review` 使用同一决定请求模型；预检响应额外返回 `projection_digest`，正式请求必须回传。入库单详情、库存流水、完工批次和生产订单响应中的来源定位符使用内部 ID，并受相同站点和角色检查。

命令接口使用 UUID v4 幂等键，并由服务端保存命令摘要、状态、`result_kind`、`result_id`、结果修订号和安全响应摘要。状态固定为 `running | completed | outcome_unknown | retryable`，其中只有 `completed` 是有结果终态，`retryable` 表示服务端已经证明原事务没有产生业务效果。每种写命令创建或改变的业务根事实都必须保存该命令 UUID，或由受唯一约束的命令结果关系连接到 UUID，使 reconciler 能以数据库事实证明结果，不能靠时间或行数猜测。同一 UUID 改变语义必须返回冲突，不能静默执行新命令。前端在请求开始后持久保留 UUID，直到 GET 返回 `completed` 或 `retryable`；`retryable` 只能用原 UUID 和原摘要重放。

后端至少分离：Excel 解析、SKU 解析、订单领域服务、完工审核服务、库存记账服务和查询仓储。库存服务只接受已经解析的内部 ID 和整数数量，不解析 Excel，也不信任客户端计算的余额或超额结果。

前端复用现有上传、状态提示、表格、确认对话框和批量审核组件风格。生产订单和库存业务状态由独立 feature 模块管理，不能继续膨胀现有 `ImportReviewFlow` 或把生产状态塞进日报发布 reducer。

## 14. 并发、恢复与失败语义

- 订单确认、订单变更、完工批准和冲销均携带 `expected_revision`；命令还携带 UUID v4 幂等键。
- 审核时按稳定顺序锁定命令、批次、来源行、生产订单头、订单明细、SKU 和库存余额，降低死锁风险并防止批准与取消/关闭并发穿透。
- 自动数据库争用重试只处理 MySQL 错误 `{1205, 1213}`，同一 UUID 和命令摘要最多执行 4 次（含首次），三次重试前分别有界退避 50 ms、100 ms、200 ms；其他数据库错误不进入该循环。每次失败事务必须完整回滚并重新取得租约及最新 fencing token，不能只重放部分 SQL。4 次耗尽后返回稳定 `database_contention_retry_exhausted`：若已证明事务未产生业务效果，命令保持或转换为可用原 UUID 重放的 `retryable`；提交结果无法证明时进入 `outcome_unknown`，不得谎报失败后换 UUID。
- 网络断开或提交结果不确定时，客户端先按命令 UUID 查询服务端结果，不能换 UUID 盲目重放。
- 过期的 `running` 和任何 `outcome_unknown` 都不是可无限停留的展示状态。命令账本保存 reconciliation 种类、租约 token、租约到期时间、fencing token、尝试次数和安全原因码；同一时刻只有持有最新 fencing token 的 reconciler 可以写回结果，旧持有者的写回必须被数据库条件更新拒绝。
- `GET /api/production/commands/{operation_token}` 遇到过期 `running` 或 `outcome_unknown` 时触发或接续对应命令种类的 reconciler。reconciler 只能读取命令账本及该命令应产生的稳定业务事实：若证明原事务已提交，则原子写为 `completed` 并固化结果定位符、revision 和安全响应摘要；若证明原事务未提交且没有任何业务副作用，则写为 `retryable`。仍在有效租约内或数据库暂时不可用时返回 503 和安全重试提示。第一期不新增常驻后台 worker，收敛由持久化 operation token 的客户端/管理员查询触发；记录即使暂时无人查询也不能产生第二份业务事实，下一次查询必须收敛。
- `retryable` 重放使用原 UUID 和原命令摘要，通过 compare-and-swap 取得执行权；不同摘要仍返回 409。reconciler 不得通过补写缺失库存、猜测响应或创建第二张单据把不确定结果“修成成功”。
- 单行业务错误返回稳定原因码；批量命令事务失败时不产生部分库存。
- 原始文件和解析错误可追溯，但前端不显示数据库连接串、SQL、文件绝对路径或内部堆栈。
- 文件进入不可变存储后、业务行解析完成前发生进程退出时，GET 只读返回可恢复的解析状态；客户端通过对应的 `POST .../{import_id}/resume` 安全恢复同一批次，不能因摘要去重留下永久空批次，也不能用 GET 隐式启动 worker。

## 15. 与未来模块和 ERP 的兼容

未来模块必须消费稳定的 `sku_id`、仓库 ID、生产订单号、入库单和库存流水，不通过展示 SKU 字符串重新拼接历史关系。

预计扩展顺序为：

`广州工厂成品仓 → 出货单与工厂库存扣减 → 海运在途仓 → FBA 入库 → Amazon 销售与退货`

库存流水从第一期起支持有符号数量和来源单据，后续出库及仓间调拨可以增加新的单据类型而不修改已有入库事实。若将来独立部署 ERPNext，当前 SKU、仓库、单据和流水边界可通过 API 映射；第一期不为尚未确定的 ERP 集成增加同步任务或双写字段。

## 17. 完成定义

第一期“订单到广州成品仓”只有同时满足以下条件才算完成：

1. 运营能从已批准 P0 商品目录选择真实 SKU，并用标准 Excel 创建和确认多 SKU 生产订单；
2. 系统按站点和订单年度并发安全地生成唯一内部订单号，未知 SKU 必须人工处理；
