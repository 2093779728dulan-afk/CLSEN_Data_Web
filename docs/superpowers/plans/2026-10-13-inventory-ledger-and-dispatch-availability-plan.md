# 真实库存、预计库存与可发库存——库存基础及发货约束实施计划书

编制：2026-10-13；2026-10-14补充独立页面要求。归属：[总主计划顺序8](2026-09-14-current-release-and-java-evolution-roadmap.md#inventory-ledger-foundation-plan)。本文规定后续库存及关联发货的数量、事实、接口与验收基础；当前授权、版本、实施进度只维护[同一执行卡](../../workflow/project-plan-index.md#production-order-shipment-current)。本方案的独立虚构库存账及发货库存校验已按批准范围开发交付，当前体验入口及证据读取执行卡；真实库存启用保持后续前置，不将资料核对旧结果代替本方案的验证。

## 1. 用户要求、目标与范围

用户原话：“请你生成实施方案计划书，要考虑到实际库存与预计库存的区别，例如某产品一共10件，被借走或者消耗了7件，那么实际库存与预计库存就不一样了，发货时就应该考虑到实际可发库存的数据。请你为此打好基础后续的开发都需要围绕这个来”。沿用此前四类行为的讨论及“管理员能够查看各个用户的操作”的要求。

目标是使系统明确回答：现在仓内多少、其中能发多少、被谁借走多少、以后有依据预计会有多少，以及一笔发货为什么允许或拒绝。**销售发货及从合格库存借用/领用，以当前允许量为约束；预计到货、预计归还及订单差额均不能代替当前可发量。**零星几件与大批货使用同一数量规则，常见动作可以手工快速登记。

| 本方案完整交付范围 | 留在后续对应范围 |
| --- | --- |
| 经确认的期初、收发/内部变更/盘点调整、质量及冻结、借出与部分归还 | 完整采购、制造工序、财务成本、费用和赔偿结算 |
| 按稳定SKU/仓库核算在库与可发；显式订单预留；手工和表格发货共同校验 | 全量多仓/FBA/货代/物流平台；无依据的批次、序列号追踪 |
| 有来源和日期的预计收发、借还待办、可读历史及管理员按用户查看 | 可编程库存/审批引擎、独立审计平台、消息中间件 |
| 独立虚构数据连续体验，再按明确范围接入真实身份与期初 | 自动将原库存表、旧出货或试用数据过账，真实迁移和发布 |

首批以花都仓库1号这一业务范围设计，开发只用独立虚构仓库/SKU；数据键保留站点、仓库和货权，界面不提前铺开所有仓储功能。数量按当前服装“件”使用整数，数据库沿现有BIGINT、API沿数量字符串，禁止浮点运算；分数单位转换另有明确需求时处理。

## 3. 数量合同：四个口径分别展示

### 3.1 实盘、账面实际在库、当前可发、预计在库

| 名称 | 定义 | 能否作为当前发货依据 |
| --- | --- | --- |
| 实盘数量 | 某次实地盘点在明确截止时点的观察，附范围和证据 | 用于核对账面；旧盘点不能自动代表此刻 |
| 账面实际在库 `on_hand_units` | 已批准期初加截至当前已过账实际事件所得的仓内数量，合格/待检/次品及质量未核分别列示 | 需进一步扣除不可发状态、冻结及预留 |
| 当前可发 `free_available_units` | 同一库存键下，符合发货条件且未冻结、未被有效预留占用的数量 | 是；服务端确认时重新检查 |
| 预计在库 `projected_on_hand_units(H)` | 指定未来日期H的账面在库加剩余预计入库、减剩余预计出库 | 否；未来事件实际发生并过账后才改变当前可发 |

页面的“实际”指已登记实际事实的账面余额，显示期初截止、最近过账和最近实盘日期；未登记的实物变化不会被系统自动感知。不用旧来源表或整理日期宣称已知实时实物。

同一库存键为`site_id + warehouse_id + owner_id + sku_id`，质量状态分桶。按已启用的身份、仓库及货主范围计算；当前花都仓库按用户要求暂不区分货主，owner_id=1仅为技术分组，货主仍明确未登记，不填成公司自有。采用下述明确仓库表口径的本地范围可计算可发；其他范围保持既有货权边界。某尺码缺失不能用款式合计代替；款式汇总仅用于展示，不跨SKU借量。

**仓库表登记口径（2026-10-16用户明确约定）**：仓库表填写的是正常可发库存；待检、次品、冻结等异常单独登记。适用范围内，表中明确的尺码数量由服务端按合格状态登记并保存NORMAL_DISPATCHABLE_V1依据，不再要求逐规格额外确认质量。显式异常不能靠此口径自动变为可发，异常仍沿对应状态或冻结记录处理；经营报告、退货报告和待检退回不继承自动合格规则。已登记正常货发生异常时作状态或冻结变更，不另增一笔实物；表中未含的异常实物需按实际来源登记，避免重复增量或重复扣减。

已有UNASSESSED期初需衔接这一明确约定时，保留原来源、期初和原操作回执，通过同一事务追加未核→合格的状态调整及人员／时间／原因；各SKU实物净变化为0，不重新开期初。同一来源禁止在其他仓库重复入账。采用口径不自动开放真实收发、订单、借还、预留或发货的写入口。

未采用上述正常可发约定的其他来源，用户明确批准只登记已确认的实物数量、延后货主或质量时，可以将该限定范围记为质量未核（UNASSESSED）期初。它计入仓内实际总数，保留来源修订、原单元格和日期精度；未知货主明确未登记，技术分组ID不代表公司自有。当前可发仍为null／not_ready，不能把未划分质量当作合格，也不能通过默认货主放行；未纳入的规格继续未就绪。精确截止未知不补零时。此类数量登记不自动开放日常收发或发货。

正常状态下的公式：

```text
仓内数量 = 期初 + 已过账入库 − 已过账出库 ± 内部变更净影响 ± 盘点调整
Q = 当前合格在库数量
H = 合格在库中的有效冻结数量
R = 合格在库中的有效预留数量（全部订单）
F = Q − H − R                         # 当前自由可发量
本次发货允许量 = F + 本次可消费的自有预留量
```

待检和次品不进入Q；H与R在正常状态下不重叠，冻结不是再次扣除已在待检/次品桶内的数量。自有预留须对应本次订单行、SKU、仓库及权限；多订单一起发时只加各行实际可消费的预留，每份只加一次。借用/领用等不能使用其他订单的预留。

`not_ready`表示缺少期初、SKU、范围或必要数量/状态，当前可发为`null`并显示缺口；确认已为0才显示0。不完整范围的汇总显示“已就绪部分＋待核部分”，不得用部分合计表示全部可发。单个待核SKU仅阻止依赖它的操作。

真实盘亏、损坏可能使`Q < H + R`。此时允许有依据的实盘/损坏事实进入账面，同一事务将受影响库存键标为`shortage`，列出缺口与受影响预留，当前可发返回`null`，暂停该键新预留和发货；保留原承诺，授权人员通过释放/更正预留、解除不适用冻结或补充实收入库处理。不能把负差额夹成0、拒绝记录实物损失或自动替用户决定订单优先级。正常借出、领用和发货不得主动造成这种缺口。

### 3.2 用户10件例子与预留

以下以期初合格10件为基础，各分支不累计；归还及占用场景接其明确的借出/扣减结果，无其他冻结/预留。

| 场景 | 仓内实际 | 借出未还 | 当前自由可发 | 指定日期预计在库及解释 |
| --- | ---: | ---: | ---: | --- |
| 尚无变动 | 10 | 0 | 10 | 没有后续计划时为10 |
| 借出7件 | 3 | 7 | 3 | 有明确归还日且7件届时预计回来，才可预计10；无日期则预计3，另列7件待归还 |
| 借出7件后归还2件，检验合格 | 5 | 5 | 5 | 余下5件按剩余量和约定日期预测，不能仍预计归还7件 |
| 借出7件后归还2件，但仍待检 | 总在库5，其中合格3 | 5 | 3 | 实收不是自动合格；验收合格后才增加当前可发 |
| 消耗7件 | 3 | 0 | 3 | 没有其他供给时预计3；已消耗的7件不能当成将归还 |
| 借出/消耗后剩3件，其中为订单A预留2件 | 3 | 视实际用途 | 1 | A本次可用最多3件，其他订单或零星领用最多1件；预留本身不减少实物在库 |
| 合格3件、冻结1件、预留1件，二者互不重叠 | 3 | 0 | 1 | 指向该预留的发货最多2件，冻结1件仍不可发 |

请求现在发7件，而本次只允许3件时，拒绝整次确认并列明原因；用户可以明确改为发3件，其余4件保持待完成。系统不默默截断，不把未来预计10件当作现在可发10件。借出7件时公司仍持有仓内3件及外借7件；消耗7件后这些货品已不再是该SKU的库存，借出与消耗不能共用“预计会回来”的解释。

### 3.3 预计库存与预计订单的区别

```text
预计在库(H) = 当前仓内账面在库
              + 在H前有明确安排的剩余预计入库
              − 在H前有明确安排的剩余预计出库
剩余预计量 = 经确认的计划量 − 已关联实际完成量 − 已取消量
```

仅纳入可追溯来源、有目标仓库/SKU/预计日期且仍有效的计划；借出归还作为预计入库的一种来源，尚无日期、逾期未重新确认或来源不足的数量单列待办，不假设今日到货。单纯下单不代表已完工或已收到货，只有明确收货安排才能作为预计供给；订单需求也不自动等于已安排出库。

预测按计划事件ID计一次，订单分配多行不复制供给/出库量；同一实收与其原计划相抵，不能保留计划全额再累加实收。预留不在上述“预计在库”公式里再次减量；已有计划出库也不因其预留再扣一次。初版不另造一个含糊的“预计可发总量”；显示预计在库、当前可发及预计量构成。预测可出现未来缺口并给出原因，仍不能授权超发。订单“预计−累计已发”的差额继续是履约差额。

## 4. 四类行为及借还的处理

| 行为 | 常见用途 | 实际影响及必要关联 |
| --- | --- | --- |
| 入库 | 实际生产/采购/其他渠道收货、退回、借用归还 | 增加指定仓库/状态的在库；有原计划或原出库时关联它并减少相应未完成量；待检不增加可发 |
| 出库 | 销售发货、普通取走、领用/消耗、赠送/送样、借出、退供、确认报废 | 减少来源仓内数量；用途决定履约、货权及归还义务。只有合法订单对外发运才计履约；借出建立未还量，普通领用等不产生借还任务 |
| 内部变更 | 同SKU换库位/受管地点、仓间移转、质量变化 | 来源与目标状态/地点有明确引用，守恒；质量变化可以减少可发。需要运输时间的跨仓移动须分别记录发出/到达和在途，不提前增加目的仓可发；完整物流留在后续范围 |
| 盘点调整 | 有依据的盘盈/盘亏、无法对应某笔原事件的差异 | 保留盘点账面、实盘、差异、截止、原因与证据；不是任意改余额。已知漏登实际收发优先补原事件，不能再次累计已含在期初的旧事实 |

销售发货只能使用符合发货条件的库存；借用/领用合格货品不得动用他单占用。待检退供、次品报废等经授权的专门用途按对应库存桶的实际余额及原关系校验，不将次品转换成订单可发量；各类出库都不得超出对应实物余量。

补录、更正、作废/冲销是上述行为的操作方式，不新增第五类。金额或件数小不改变身份/数据控制；从产品上下文带入SKU/仓库，用少量必要字段完成手工登记，不强制上传表格或逐笔多级审批。

借出记录保存借用人/对象、用途、实际日期、是否需归还及可选约定日期；登记账号和实际领用人分别存储。归还从原借出记录发起，校验同SKU、scope及未还余量，允许部分归还。**归还实物已验收接收即可减少未还量，但只有质量合格才增加可发。**不得因重新提交归还而重复增量，超原未还量须另有真实入库依据，不能伪称归还。

未归还货品明确转为赠送、消耗或损失时，对外借在外数量作有依据的结清/处置并保留原关系；不再从仓内扣一次，也不把赔偿视为货品已经归还。首批不实现财务结算。损坏仍在仓时先改变质量，实际报废出库才减少仓内总量。无可靠原记录的历史退回保留真实来源说明并待核，不编造借出ID。

冻结/解冻和预留/释放是库存可用性的控制动作，不改变四类实物流分类。实际去向、是否需归还和货权不能从“取走”这个词自动推断。

## 5. 期初与真实启用前置

1. 固定拟用来源、review_id/revision、仓库、scope、实际盘点截止时点及时区，确认SKU、货权、合格/待检/次品和未知量；整理日期不能代替实盘截止，空白不能补0。
2. 明确截止前已包含的收发以及截止后待录入实际事件。历史出货若已反映在期初中，不再扣；同一来源不同版本不叠加。截止前发现资料遗漏先更正来源并重新核对，已启用后走显式库存差异处理。
3. 期初作为单独可追溯操作，服务端按范围和来源修订防重复；已过账来源核对单后来更正，只产生待核差异，不能静默改余额。期初未就绪时可保存业务草稿，不允许正式发货。
4. 截止时已经外借的货品若本次纳入管理，另核实外借期初及未还关系，不能把已不在仓的货再算入仓内期初，也不能为建立借还任务伪造今日出库。未核实部分隔离。
5. 开发先用任务所有的虚构身份/可抛弃MySQL；真实启用前按授权核对身份版本合同、小范围影子对账、来源/切换时点、备份及未结单据。影子核对不产生第二套正式账或自动过账。

真实身份写入权威仍为Python。Java与Python跨库不能以两次HTTP查询冒充原子校验；正式确认需沿原MVP7.6实现有效版本合同。本计划不以客户端`_catalog`内容或过期投影替代它。库存与出货事实在同一Java数据库事务内处理，不新增跨库分布式事务。

## 6. 数据模型与唯一写入方

Java业务域负责以下事实，复用当前Spring Boot/JDBC/MySQL。模型是本期库存事实及必要投影，不建设通用事件溯源平台；具体DDL在实施前核对实际迁移head和现有约束。

| 记录 | 最小职责与唯一性 |
| --- | --- |
| `inventory_scope/opening` | 库存范围、未就绪/启用状态、截止、期初来源修订和过账ID；同范围不得重复启用或重复期初 |
| `inventory_document/line` | 四类单据、来源/目标、用途、SKU、正整数数量、质量、货权、日期、对象、原因/证据、原单据关系、状态/修订；借出行保留归还义务与结清关系 |
| `inventory_event` | 不可变已过账的数量事实及每个库存桶的增减，关联单据行/修订、期初或出货来源行；冲销/更正追加关联事件。外部事实键与事件用途联合防重，不能只靠文件hash或同SKU同日 |
| `inventory_balance` | 按库存键/质量桶维护的事务投影、余额修订；从事件可核对重建，前端与Python不得直接编辑。过账与投影更新同一事务 |
| `inventory_reservation` | 订单行、仓库/SKU、有效数量、已消费/已释放量、状态、修订及原操作；不得超自由可发量，不默认每张草稿自动预留 |
| `inventory_hold` | 合格货品中的冻结/解冻数量、原因与操作关系；与预留互斥，影响可发而不减实物；质量桶变化不重复冻结 |
| `inventory_plan/line` | 预计日期、供给/出库方向、剩余量及来源事件，实际完成/取消引用；借还计划引用原借出行，不另造无来源预测余额 |
| 现有`production_command/production_revision` | 复用操作ID、摘要、结果回执及修订模式，加入库存对象类型和可读变更；业务事实事务成功后才返回成功 |

源行与分配分别保存：一笔销售出库引用`production_shipment_source_line`，多个订单allocation不复制库存扣减。新库存单据不得另造第二笔相同销售出库。货品质量、占用及计划各管一种口径；余额字段不承担订单需求或借用人姓名。

库存及修订历史保存稳定actor_id、登记时可辨认的账号/姓名快照、UTC记录时间、实际业务日期、操作/单据/修订、前后变更、依据及结果；用户改名不丢失原身份。借用人/收货人不是自动登录用户。管理员在授权site/仓库范围按用户、时间和动作过滤，普通只读用户按已有权限读取业务结果；回执按原用户权限获取。复用现有机制，不复制成跨模块审计平台。

## 7. 状态与发货事务

库存单据使用草稿→预览→确认过账；草稿修改可撤回，已过账只能关联更正/冲销并保留原事实。预览不占用、不扣减，保存草稿也不改变库存；用户明确预留才占用，确认发货同时消费自有预留并扣减。完成后库存、订单与历史重读同一已提交结果，余额更新失败不返回成功。

### 7.1 所有发货入口共用的确认规则

手工确认、Excel确认、直接API、数量更正均进入原Java命令核。不另写前端/文件/Python库存扣减。库存已经启用的范围，服务端必须执行以下事务：

1. 校验登录权限/site、稳定身份有效性、仓库/货权、单据状态/expected_revision及操作ID；相同ID相同内容返回原回执，不同内容拒绝。
2. 将本次各来源行按库存键合并，固定顺序锁定单据、订单、余额及关联预留/冻结记录；新增余额键用唯一约束及同一锁入口处理。借出/收货/预留/发货遵循同一锁次序，不能各自只锁自己的单据。
3. 锁内重新读取就绪状态、合格量、冻结、他人预留及本次自有预留；校验合并后的总出库量，不让同SKU分成多行分别通过。操作的库存/单据版本已改变时给出冲突及重新预览依据。
4. 本次超可用、错仓库/范围、待检/冻结、来源不明或缺口未处理时整次拒绝；回传逐SKU请求量、当前允许量及限制原因。多行任何一行失败都不写部分库存或部分履约。
5. 成功则同事务写一次出货事实及分配、库存事件和余额、预留消费、修订历史及命令回执；只有对外订单发运更新履约累计。提交后才响应成功，响应丢失通过原命令ID查结果。

两人同时各请求发7件、库存10件，最多一笔成功；余量3件不能被第二笔旧预览消费。借出、领用与发货并发也必须同样限制。不存在“管理员强制忽略库存”的正常发货开关，权限不能把预计量变成实物。

### 7.2 更正、补录与历史兼容

- 只改订单分配/履约归属，不改变实际物品与实际出库量，不产生新库存事件；需求减少或关闭跟踪应显式处理剩余预留，不能抹掉已经出库的事实。发货草稿/订单取消与实物退回分别处理。
- 更正实际数量/SKU/仓库，以原事件及新事实计算净变化，锁内校验并追加冲销/更正；减少既有实收若下游已消费该数量，应阻止无依据逆转并列出依赖。增加实际出库的更正需要足够当前允许量；不能仅改出货行绕开库存。
- 实物已经发出后真正退回，登记关联入库及质量；录错“已发”而实物从未离仓，走有依据的数据更正。二者不可共用一个“作废即全数回仓”按钮。
- 补录保存发生日期和本次登记时间；截止前或是否已包含期初不明的事实先待核。截止后的迟登事件只在核实未过账且未含期初后入账；不自动全量重放历史，不允许缺少前序收货时制造负在库来凑事实。
- 既有未接库存的历史/DEMO出货保留原模式和历史，读取不伪造库存关系。启用由服务端绑定环境与仓库范围；新真实确认必须使用正式账，未准备SKU不能退回无库存模式。请求参数或旧Excel版本不能选择绕过模式，纯物流节点更新不再次扣货。

**销售出货的明确依赖：**当前库存变动的plan_id已有事务结算，销售出货sources尚无计划关联字段。从预计出库登记实际操作时先明确用途：销售用途进入实际出货页，普通取走/消耗/借出等进入库存变动页，不能以普通库存变动复制销售扣减。本批销售用途的“登记实际发货”须一并补齐来源行与原计划的显式事实关联：服务端在原Java出货事务内复核同仓/货权/SKU、OUT方向及剩余数，随确认更新计划完成量；实际数量更正/作废只调整对应计划贡献，分配更正不再次扣减或完成计划。手工、文件和直接API复用同一规则；旧出货没有关联就保留原模式，不按SKU/日期自动回填。需要持久化关联时只补原业务模型及任务虚构库的最小迁移，保持备份、权限和原记录保留；真实库不自动安装。不得交付只有跳转但发货后计划仍不减少的按钮。

**实施顺序与落点：**先完成预测构成和身份读取，再接计划实际操作及确认，最后完整检查历史、反馈与离页恢复；沿用StockWorkspace.tsx、ProductionWorkspace.tsx、ProductionViews.tsx、types.ts、useProductionLeave.tsx及现有Dialog/StatusMessage/Table。必要读字段与计划贡献在原backend/app/api/production.py、production客户端、InventoryService、ProductionService及现有事实迁移中处理，Python仍为商品身份权威，Java仍为数量事实唯一写入方。沿原工作区保留已有修改，不新增通用审计平台、竞争性商品目录或工作树。

**必要验证与交付：**先用独立虚构数据走通“解释预测→由计划登记→预览/确认→刷新→部分取消/释放→更正/冲销→用户历史”及适用恢复；复用原StockWorkspace/ProductionWorkspace目标测试，补预测构成、预填/有效关联、确认前零写入、完整dirty、行明细前后和保存/重读分离的未覆盖行为。涉及销售计划贡献时，补Java任务MySQL中的部分履约、同计划多行合计、更正/作废、并发及事务回滚；原未受影响结果复用。做受影响类型/lint及必要构建，不自动扩大到全仓回归、正式Collect或发布。现场截图访问仍不可用时具体标记未测视觉，不绕过拒绝；开发验证、用户确认和发布验收分别记录。交付同一23010入口、既有账号获取及一段完整体验步骤，不新增逐文件审批。

## 11. 验证与验收合同

正式实施时先用任务所有的虚构MySQL与实际角色走通完整功能，必要构建/启动/缺陷定位检查可先做。复用受影响原测试，只补新规则与关键边界；按[验证策略](../../operations/development-verification-policy.md)普通快检约3分钟、数据库约10分钟，超预算说明具体剩余工作，不强杀迁移、不把未测算PASS。Java沿已有目标合同测试入口及真实MySQL夹具；Python如实际涉及MySQL，使用现有DevelopmentTests目标节点及账户/TLS合同，不扩大到业务库。

| 必要场景 | 必须证明的结果 |
| --- | --- |
| 10−7借出、10−7消耗 | 当前只余3可发；前者未还7且有日期才进入预测，后者不能预计归还；发7拒绝，明确改3可完成 |
| 部分归还/质量/结清 | 归还2仅减未还2；待检不增可发；超归还拒绝；在外转消耗不重复扣仓内 |
| 同SKU内部变更 | 本期即时地点/状态变更两端同步且数量守恒；合格转待检减少可发但不减仓内总量，涉及已占用真实损坏时明确缺口；不支持的跨范围操作拒绝 |
| 不可发桶专门出库 | 次品报废/待检退供只减少相应实际桶，不消费订单预留、不计销售履约；正常销售不能选择此用途绕过质量校验 |
| 预留与冻结 | 3件预留2→自由1、自有最多3；他单不能挪用，冻结/质量不双扣；释放/消费后数量准确 |
| 盘点真实缺口 | 实盘3而预留8→真实在库3、缺口5、该键发货暂停；处理后恢复，原承诺和历史不消失 |
| 同SKU多行/多订单/并发 | 同一扣减源只计一次，合并数量后判断；发货与借出/预留竞争不超量，固定锁次序；中途故障整笔回滚 |
| 重复/文件/结果未知 | 手工和Excel同规则；同操作ID无重复库存/履约/归还；同内容不同入口不能重复同一外部事实；响应丢失查原回执 |
| 身份/权限/未就绪 | 错site/仓库/货权/SKU拒绝，主档版本失效阻止真实确认，viewer不能写；未知是null而非0，客户端不能绕回无库存模式 |
| 期初/资料/历史 | 固定来源修订，期初防重，截止前已含出货不再扣；核对修改不改已过账余额，旧stockless记录无虚假库存链接 |

| 连续使用及历史 | 登录→查款色码→登记→确认→刷新→发货/归还→相关订单/库存/历史核对；冲突/断网/撤权恢复，管理员实际看到可识别操作用户 |

事务、跨进程竞争及真实数据库约束须由任务MySQL边界测试证明，不能仅用mock；可发和预测算术覆盖固定数值与边界，前端覆盖适用冲突/结果未知/权限及窄屏。类型/lint/Token/构建按实际改动执行，必要Storybook只放虚构数据；不机械追加全仓回归、压力测试或完整Collect。新失败/公共接口受影响才扩大到直接消费者，正式发布CI/Collect仍沿原授权及合同。

## 12. 安装、切换与回退

先对任务所有的虚构schema实施新增迁移及合同验证；复用正式脚本的账户、TLS、触发器和清理范围，应用账号不获DDL。真实启用前具备第5节前置及相应授权，记录Java库存schema与Python主档/核对schema的兼容性，不因Java库迁移就假称原Python服务可重启。备份范围包含库存、预留、计划、事件、修订和回执，实际恢复门禁留在相应发布阶段。

切换按明确仓库/scope生效，在库与未结量对账后新实际事件进入唯一Java写入方。未纳入范围诚实显示未启用，不能继续给它展示假“可发”；未准备SKU不通过旧确认路径漏扣。旧来源查看/DEMO演练独立保留，不自动转为正式事实。

回退关闭新写入并保留只读与已发生事实，核对切换后单据及待办；已启用真实范围不能回滚成无库存校验的发货。必要修复与补偿按明确范围处理，不删表、删历史、drop归属不明资源或用旧库存快照覆盖新账。提交、push、merge、真实迁移、服务器部署及正式发布须在各自授权内执行。

## 13. 文档约束与交付状态

本方案的[数量合同](#inventory-quantity-contract)及[发货合同](#dispatch-availability-contract)是后续库存、收发、借还、预留、订单发货及预测开发的共同基础。主档只负责身份，资料核对只负责来源决定，库存只依据实际事件，履约只依据显式订单发运关系。后续扩展需要改变口径时，先更新本合同并核对直接受影响路径，不在各模块另写一套解释。

实施交付须同时给出可用入口、应用版本、实际账号获取方式、数据/初始化范围、简短步骤及未就绪项；`development_complete`、`ready_for_user_review`、`user_verified`、`release_validation`分别记录。本方案的实际实施/体验状态只读取执行卡；不改变既有资料核对确认范围，也不推进真实启用或发布阶段。

本计划采用writing-plans；按现行执行卡、数量/身份合同及B受影响代码编制，复用此前四类行为检索，不重复审查。公开分类依据沿[核对计划第12.1节](2026-10-13-inventory-reconciliation-workflow-plan.md#inventory-movement-categories)，本项目四类是归纳口径，不声称外部ERP原本只有四种操作。本轮只编辑计划及必要路由/稳定约束，检查文档差异、链接、算术与口径一致性；未改应用、运行服务、读取新原件、连接业务库、迁移或发布。
