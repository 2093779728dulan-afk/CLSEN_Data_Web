## 4. 操作入口、角色与页面流程

在现有“资料核对”组增加“人工表格整理”，不增加顶层导航组。页面路由拟为`/production/manual-tables`与`/production/manual-tables/:batch_id`。原“原表与草稿”和所有历史链接保持。

一次操作保持在一个工作区，按状态展开必要区域：

1. **选择资料**：选择库存结存/预下单/装箱、文件及所属仓库等已知上下文。明确人工来源；未识别的信息允许先留空保存资料。
2. **确认字段**：唯一匹配的表头预填；多工作表、多区域、无表头或同名列时展示原表样例并用下拉选择。平常不要求用户逐列点击确认。
3. **核对结果**：显示原行、标准明细、拆分/排除行数、已识别/待核数量、合计及问题。支持“只看问题”、定位原格和从主档下拉选择商品。
4. **保存与导出**：保存草稿、刷新继续；导出标准明细、业务宽表或问题清单。保存明确显示仍未入账。
5. **交给业务处理**：满足条件时进入原资料核对或订单/出货草稿；展示对应目标和处理状态。业务确认按钮及库存影响继续由原模块负责。

| 角色 | 能力 |
| --- | --- |
| admin/data_manager | 所属site内上传、保存整理、选择商品、导出及允许的草稿移交；动作记录真实用户 |
| admin | 另可查看本站点各用户整理历史、维护可共享的列对应方案；不跨站点读取 |
| viewer | 按既有授权查看已交付的业务数据；本期不开放人工批次原件和编辑入口，服务端拒绝绕行 |

普通数据管理员默认管理自己上传的未移交批次；共享对应方案仅共享字段位置规则，不共享其他账号原件。更换账号/站点时复用现有AuthzGeneration清理敏感页面状态。空列表、未启用、读取失败、无权限、未保存离开、旧修订、目录变化及移交结果待确认均有明确中文状态。

批次使用少量明确状态：`NEEDS_MAPPING`（字段待对应）、`NEEDS_REVIEW`（事实/商品待核）、`READY`（所选目标的草稿前置齐备）、`HANDOFF_PENDING`（原操作结果待查）、`HANDED_OFF`（已关联原目标）。另按动作返回`can_export`、`can_create_inventory_review`、`can_create_order_draft`、`can_create_shipment_draft`及中文原因；待核资料可以导出问题清单，READY不等于已入账。它们由当前修订和目标能力推导，不另建通用工作流引擎。

## 5. 最小字段合同与标准明细

### 5.1 公共来源与身份

每批包含`batch_id`、`site_id`（服务端）、人工来源声明、原件digest/存储键/文件名、上传人/时间、解析器版本、字段方案版本、当前修订。每条明细包含稳定的`source_line_key`、工作表/物理行/数量格、原始编码/款色尺码、规范化候选、确认决定和修改原因。拆尺码后的行不能失去原行关系。

`sku_id`可空，匹配时附目录版本和状态；未找到/多候选/冲突/唯一匹配分别返回。商品选择从当前范围内主档检索；正式SKU待补的实体规格仍可按稳定ID核对，不强迫填造Seller SKU。文件内自带的ID、账号和仓库都要重新查范围，不能信任导出的旧ID。

### 5.2 各类字段及必填阶段

| 业务类型 | 整理明细 | 移交/业务前置 |
| --- | --- | --- |
| 库存结存 | 款号、颜色、尺码、数量；仓库、库存日期、结存口径可按批补充 | 创建资料核对可保留未匹配及未知格；正式库存处理需范围、日期、确认商品及覆盖事件口径，并按现有流程预览 |
| 预下单 | 款号/原编码、颜色、尺码、预计数量；来源单号、下单日期、预计出货日期 | 创建有效业务草稿需唯一商品及目标模块所需日期；预计出货日期可空，DELIVERY不自动替代下单日期 |
| 装箱 | 原商品标识、颜色/尺码候选、每箱件数、原总数；ASIN/FNSKU仅来源参考 | 交实际出货草稿前明确实际已发与日期、仓库、稳定商品和所需订单分配；未实际发出仅作为装箱资料 |

名称、性别、图片、材质、箱尺寸、重量等非本次业务必要字段不纳入目标数据；原件中仍可追溯。源SKU与款色尺码矛盾时两边都显示，不能简单选一边覆盖。货主、精确截止沿当前用户已延后的决定，不恢复为本批整理前置。仓库表“正常可发；异常另记”的已确认口径可按原scope带入，不推广到未确认的新仓。

数量传输用十进制整数字符串，稳定ID用字符串，业务日期用ISO日期；时间展示沿所属site时区，文件修改时间不作为业务日期。库存允许明确0，预下单/实际出货有效行须符合各自正数量规则；原0格和未知格可在资料层保留，不猜建无库存商品。

## 6. 提取与格式整理规则

### 6.1 有限适配器和列对应

- 使用有限的三类适配器：`inventory_matrix_v1`、`planned_order_matrix_v1`、`packing_columns_v1`，另接受本模块标准明细版本。按已知字段规则匹配，不用概率模型替用户作业务判断。
- 先列出工作表，默认唯一有明确表头的业务页；多个候选不自动合并。前20行寻找表头，支持“新款号/款号/style”“COLOR/颜色”“QTY/数量/合计”和明确尺码/箱号。合计只是校验字段，不与明细相加。
- 无表头列不能凭ASIN/FNSKU的字符串外形直接正式绑定。像本次装箱单的A/B/C列，先显示候选含义及样例，由用户确认列对应；对应方案可命名保存后复用。
- 用户可选择表头行、数据起止行、业务区域、忽略说明列；一个批次处理一个明确业务范围/文档类型。不同订单/仓库/日期区域分开选择，未选择区域的行数与排除原因可见，不能自动丢掉另一块业务。
- 列对应方案记录site、来源类别、字段表头签名、尺码/箱列、布局及版本。结构或角色范围不符时返回字段确认；不在旧列位置上悄悄套用。不保存商品别名或数量事实。

### 6.2 行、尺码、合并、空值与公式

- 库存及预下单从宽表拆为款色尺码数量；装箱按原行保留箱分配，商品总量由各箱独立求和。相同商品跨箱正常存在，不把每箱与总数重复计入。
- 合并的标题单元格仅帮助识别表头；只对用户选定的身份字段和真实合并区域取左上值，数量格合并须核对。未合并的空白不盲目前向填充。
- 空行、说明行和重复表头明确列入排除摘要。隐藏行含业务值时提示确认包含/排除；合计/小计须由标签及选定区域识别，模糊行留待核，不静默删除。
- 空白、`/`、破折号、0及文本“待核”分别保留。用户已确认的同一仓库表空白和`/`为0可以作为具名规则复用，预览显示依据；其他来源未确认时保持未知。
- 纯展示空格/换行整理记录候选。公共实体规范化和Seller SKU规范化严格按身份合同使用；颜色中英混写只提出候选，不删除中文后直接认可等价关系。
- 明细数量须为明确整数；数量格包含公式时阻止该行移交，提示填写明确值。合计公式可作为来源表达保存，系统按识别到的完整尺码/箱明细重算。缓存值仅供对照，缺缓存不阻止从明细得到合计；不执行任意公式、外链、宏或用总数反推缺失明细。
- 重复商品不静默去重或合并。明确选择汇总时保留全部来源行、前后数量和原因；装箱/订单分配按目标模块粒度判定重复。

### 6.3 文件预算

沿用2MB上传、ZIP最多2000项和解压30MB的已有上限；一期最多10张页，所选区域最多2000行、80列、合计100000个候选格，超限中文说明并建议选择区域/去除无关图片。扫描表头及区域读取受同一预算约束，不因忽略图片放开解压限制。采用现有Python/openpyxl，读取不保存原件，不下载新运行时。数据规模增大后有实测依据再调整，不预设异步任务队列。

## 7. 校验、问题与人工决定

问题结构统一包含`code`、`severity`、`blocks`、中文`message`/`suggestion`、`source_ref`、原值、候选值及关联行。`blocks`按导出标准明细、创建资料核对、创建业务草稿、业务过账分别表达；不能用一个“成功”掩盖后续未就绪。

| 层次 | 必须检查 | 用户可采取的操作 |
| --- | --- | --- |
| 结构 | 类型、表头、必需列、重复列、选定区域、无表头列、官方来源误选 | 选择工作表/字段、修正区域或改走平台入口 |
| 字段 | 标识符文字、整数、缺失、尺码、日期含义及空值规则 | 选择标准值、补上下文；原值与原因保留 |
| 商品 | 当前目录、scope、款色尺码及编码冲突、未确认颜色 | 下拉选择；进入原建档/待处理；不自动批准主档 |
| 数量 | 七尺码合计、箱内数量、原总数、重复/排除行、累计或增量 | 核对事实；提交更正值和理由；不靠调平合计通过 |
| 跨表 | 显式选定同批预下单/装箱/库存的规格与数量、出货后结存覆盖 | 仅在所选三表范围比较，逐问题确认；不自动搜索历史报表或扩大库存盘点 |
| 移交 | 当前身份/目录、目标状态、已有来源、日期、订单分配及写入开关 | 进入既有草稿/确认页面，或继续保留整理资料 |

格式问题可以先保存资料。只含错误的批次也保留原因和原件；“没有可识别商品”不能伪装为0件成功。默认不静默只移交正确行；如用户明确拆分，先预览已选/未选行与数量，并保留独立来源关系。

中文示例采用虚构数据：`库存!H8：款号TEST-01，蓝色/L，旧数10、本次出货5，当前表为7，相差2件。请确认是否另有收发或旧数更正。`；`装箱!A1:C1：缺少字段名称，请选择商品编码、ASIN、FNSKU对应列。`；`第12行：颜色存在多个商品候选，请选择确认，当前未计入可入账数量。`

## 8. 库存、预下单及出货衔接

### 8.1 三种责任

库存整理创建新的来源资料/核对，不覆盖10.14旧来源或库存余额；后续数量处理复用盘点/更正及来源核对流程。预下单只创建预计需求草稿，不增加实物或可发。装箱只在实际已发、身份/日期/订单等前置齐备时转出货草稿；确认和扣减由Java现有事务执行。

整理记录保存“出货前/出货后/未知”的库存口径，以及经确认包含的具体来源/事件。比较须限定相同仓库、规格及期间，日期相同不能证明含同一事件。已包含在结存中的历史出货不能再次扣；如现有领域命令尚不能表达这种历史资料关联，则本批保持资料核对，并在本任务内补必要的显式接入合同及QA验证后使用，禁止用消耗单、虚假入库、重做期初绕过。

不把一张出货后库存表直接重设整仓余额。先展示当前账、资料结存、已知事件、未解释差额与已覆盖事件，按既有库存变动合同处理实际新增事实或更正。库存和出货是否已入账分别记录，避免仅保存了来源就显示已扣库存。

### 8.2 目标适配接口

`inventory_review.py`拟新增独立的`start_from_manual_batch(context, batch_id, revision, operation_token, ...)`，接收服务端存储的规范明细及来源引用，复用核对服务的权限、修订、预览和保存；不改旧start/已配置source解析含义。

预下单/装箱由新薄适配器生成现有生产命令字段，通过原网关使用稳定SKU创建`DRAFT`，不得直接写Java业务表。无法匹配商品的资料留在人工批次；目标模块不支持的字段留来源引用。真实环境写入开关关闭时只可整理/导出，不尝试借新API创建订单或出货。

移交使用每批固定操作token；保存目标类型/ID、原批次修订与回执。库存同控制库的创建可在现有事务内完成；跨Python/Java移交先持久化token及意图，调用原幂等命令，成功后登记回执。超时显示“结果待确认”，先查`/api/production/commands/{token}`，再续接同token；不盲重发或换token，不引入分布式事务平台。

每批默认只关联一个目标。更正已移交资料时链接原目标并走其修订/更正流程，不另建第二个单据；已发生的目标业务不能靠删除批次撤销。跨库成功而链接保存失败须可用原token找回目标并补齐关联。

## 10. 架构、持久化与操作历史

### 10.1 最小职责划分

- React/Vite负责文件选择、字段下拉、问题定位与决定；复用现有设计系统、`writeApi`、`StableOperationKeyStore`、RequestGate及未保存保护。
- FastAPI/Python负责文件读取、三个适配器、规范明细、列方案、验证、资料保存与导出。业务主档通过现有接口读，Python主档继续唯一写入权威。
- Java继续订单、出货、正式库存的唯一事实写入；只在原服务端能力允许时接收新来源的有效草稿/命令。
- 沿现有存储边界复用`app/imports/storage.py`的不可变字节存储能力，用新的人工资料配置根；不把人工文件注册为官方日报/发布数据集，不访问项目根`data/`。不引入新服务、队列或依赖。

### 10.2 拟新增三类控制库记录

| 记录 | 必需字段/约束 | 作用 |
| --- | --- | --- |
| `manual_table_batches` | batch UUID、site/owner、人工来源/kind、原件digest/storage_key/大小、解析版本、当前revision、当前规范结果/决定、target_ref及移交token/状态、时间/操作者 | 有权限的可恢复资料与唯一目标关联 |
| `manual_table_operations` | site、batch/方案引用、operation_token、request_hash、expected/result_revision、动作、决定/结果快照、actor、时间、原因 | 保存/方案修订/移交幂等回执与管理员历史；资料变更追加修订，导出事件不改变数据修订 |
| `manual_table_profiles` | site、方案ID/版本、名称、适用kind、表头/布局签名、显式字段/空值规则、作者、共享范围、停用标识 | 复用人工确认的结构；新版追加，不回写历史批次 |

保存用数据库行锁或CAS校验expected_revision，不能仅靠进程内Lock；`(site, operation_token)`唯一，相同token内容不同拒绝。快照和原件digest不可被修改命令覆盖；补传修正文件形成有显式前序关系的新来源。决定与原值分开，操作历史可查每次差异，旧修订可读。

相同文件按site＋owner＋kind＋digest返回原批次；不能跨账号泄露“别人已有该文件”。管理员按本站点权限查询已有批次。不同文件但业务相同继续由来源/目标确认防重复，文件hash不成为业务唯一依据。

新增schema只在后续获准实施的B任务所有可抛弃MySQL先验证。迁移使用当时下一可用Alembic编号（当前读到0034，不在方案中占用0035），同步维护schema revision/兼容和迁移合同测试，不改已应用迁移。真实23040或其他库安装另按其授权；不能对共享A或线上库试迁移。此为必要的资料持久化，不另建通用任务/审批系统。

## 11. API与能力合同（拟新增，不表示已存在）

新router使用`/api/manual-tables`，统一现有认证、CSRF、CatalogWriteContext/ReadContext及中文错误。`site_id`和actor取服务端上下文；所有batch/profile/目标读取逐项鉴权。

| 方法与路径 | 输入/结果 | 写入边界 |
| --- | --- | --- |
| `GET /capabilities` | enabled、可处理kind、预算、可移交目标及原因 | 不等于打开生产写入 |
| `POST /batches?kind=...&filename=...` | 原始XLSX请求体＋稳定操作ID；返回批次、识别建议/问题及摘要 | 只保存人工来源与初始资料；不使用multipart新依赖 |
| `GET /batches`、`GET /batches/{id}` | 分页/状态/修订/问题/历史入口 | 按所有权或本站管理员范围 |
| `POST /batches/{id}/preview` | expected_revision、工作表/区域/字段、具名空值规则、上下文及行决定 | 返回原值/新值、数量、问题、preview_hash；不写业务 |
| `POST /batches/{id}/save` | 同一内容、preview_hash、expected_revision、operation_token、修改原因 | 服务端重算并保存一个新修订，原子写回执 |
| `GET /batches/{id}/history`、`GET /batches/{id}/operations/{token}` | 历史/原操作结果 | 解决刷新/超时，不换ID重做 |
| `POST /batches/{id}/handoff` | revision、目标类型、操作token、必要业务决定 | 重新检查当前目录/权限/开关；仅创建允许的资料核对或DRAFT |
| `POST /batches/{id}/export`、`GET /batches/{id}/source` | 导出用途、筛选、固定revision/原件；返回下载 | 记录导出范围/操作者，不改库存或数据修订 |
| `GET /profiles`、`POST /profiles`、`POST /profiles/{id}/versions` | 方案名、适用kind、显式字段配置、结构签名、预期版本 | 方案自己的修改权限及幂等操作；共享由管理员维护 |

预览摘要覆盖原件digest、批次修订、解析/schema/方案版本、字段选择、业务上下文、行决定，以及实际使用的目录版本；改变上述内容须重新预览。导出请求固定修订，避免前端混出两个版本。客户端不能通过构造preview_hash或提交sku_id绕过服务端校验。

示例行：`{source_line_key, source_ref:{sheet,row,quantity_cell}, raw:{style,color,size,code,quantity}, normalized:{style,color,size,units}, match:{status,sku_id,catalog_version}, decision:{...}, issues:[...]}`。`raw`永不被normalized覆盖；只有确认值进入目标适配器。

HTTP含义沿现有信封：422字段/格式问题，409旧修订或幂等内容冲突，403无权限/能力关闭，413超预算；业务前置不足返回具体原因。英文异常只在服务端日志对应request_id，页面看到中文位置和下一动作，不吞错报成功。

## 13. 按可用结果组织实施

### 任务一：上传原表后得到可信的统一明细

实现三类适配器、字段schema、结构/数量校验和来源位置，含无表头的显式列选择及官方来源分流。先构造匹配本次布局的虚构XLSX，复用已有正常样例提取形状，不复制真实商品明细进测试。

验收：三种人工布局均能正确提取和合计，图片/说明不影响明细；未知和冲突可见，无隐藏丢行或凭相似名称匹配。旧三个解析函数保持原结果，新人工路径成功不靠改旧断言。

### 任务二：资料可保存、继续处理并追溯操作者

实现新控制库记录、不可变文件存储、权限、预览/保存/版本/操作回执、字段方案及管理历史。完成页面选择资料→字段确认→问题处理→保存→刷新继续的完整路径；窄屏沿用现有组件的可访问行为。

验收：刷新/重启能恢复资料；旧修订拒绝覆盖；同token并发只保存一次，错内容拒绝；其他账号/站点不能取原件或改批次，管理员能查本站操作人及前后值。保存不改变任何业务余额、主档或官方日报。

### 任务三：导出可读、可回导且不丢明细

同schema生成模板、标准明细、业务宽表及问题清单，固定批次修订、筛选和全部分页，保留文字编码和未知状态。通过新入口再导入本模块输出并比较语义，不要求样式字节完全一致。

验收：三类型的导出/回导保持规格、数量、箱分配、日期口径及来源引用；问题清单可定位；含公式样式文字的编码不执行；未修改的再次移交不产生第二笔业务。旧模板与旧导出文件保持原合同。

### 任务四：沿现有业务流程完成虚构闭环并交付体验

实现库存资料标准明细接入，以及允许环境的订单/装箱草稿移交和结果恢复。用独立任务库/虚构账号走通库存来源核对、预下单→分批出货、可发校验、刷新汇总及更正；核对来源已覆盖库存时不重复扣减。当前领域不足的历史覆盖表达在本任务明确补齐并测试，不能用新页面遮掩。

验收：整理→现有目标→原确认事务的直接关联结果一致；未知SKU/颜色/日期和业务关闭不越过。真实23040仍按原范围，未授权的订单/出货不能移交或确认。交付包含可用入口、实际账号获取方式、虚构样例、3–5步体验和未就绪数据清单。

任务依赖一→二→三/四，按同一完整路径集中实现验证，不逐文件审批或自动提交。正常当前代理内联执行，不新开工作树/组队，不重做已完成审查。先交付人工资料整理可用结果；真实业务事实与授权未齐的部分明确保留。
