## 3. 样本准备：保留业务关系，控制体量

### 3.1 最小样本包

建议 3–6 份格式完整的原报告副本，覆盖 10–20 个有代表性的款式。数量是起步建议，不强制截断大文件；若原报告更大，应由数据提供者制作能独立解释的子集，并提供对应子集核对数，不能保留整份汇总冒充子集汇总。

| 样例 | 需要观察的真实情况 |
| --- | --- |
| 普通商品 | 至少一款有多个颜色/尺码，确认只显示实际变体。 |
| N:1 映射 | 至少一个稳定 SKU 对应两个 Seller SKU，确认不是重复变体。 |
| 待分类与人工标准值 | 有未分类或分类不明确的商品；已有名称/颜色/尺码不被后续来源静默覆盖。 |
| 长字段 | 长商品名、长 Seller SKU、长说明，观察卡片、表格和冲突页。 |
| 跨日与退货 | 同一商品连续日期的经营/退货记录，用于追踪来源及分析口径。 |
| 重复与异常 | 已知重复记录、未匹配或缺失字段，用于理解系统判断与修正路径。 |

缺少某种真实案例时标记“样本未覆盖”，不要修改真实副本造出一个案例后仍声称是自然真实数据。必要时另外提供明确标注的派生或合成案例，结论分开记录。

### 3.2 脱敏与完整性

- 用户或授权的数据提供者在提供副本前脱敏；代理不得为制作副本自行进入 `data/` 或读取真实数据库。
- 保留报表结构、编码、日期、数量、金额与币种、关联关系、重复关系及来源版本。订单等敏感标识采用跨文件一致的一对一替换，保留空值区别；不能将所有标识替换成同一个值，否则会改变去重结果。
- 站点/账号/Marketplace 和 Seller SKU 等关联键是否原样保留由数据范围授权决定。需替换时使用一致映射，不能破坏跨日、跨报告、N:1 关系；不要求提供还原映射或真实人员身份。
- 客户姓名、地址、联系方式、客户留言等非必要内容移除或替换。会参与业务去重的敏感字段应保留可比关系；无法保留时标注该场景不能用于确认真实去重质量。
- 接收后只对授权文件建立清单：样本代号、哈希、报告类型、覆盖日期、行数、币种、脱敏/抽样说明。原副本只读保留；上传、下载和用户修改文件存放工作副本区。
- 数据提供者给 3–5 个已知核对点，例如某日报告的数量/金额、某款实际变体数、一个确定的别名关系。每个值注明范围、来源和计算口径；不得只拿同一 API 的两个界面相互验证。没有独立基准时只评价体验，不宣布业务数字正确。

## 5. 用户体验安排

建议拆成两次 20–30 分钟体验，之后一次 10–20 分钟复体验；这是用户操作时间建议，不是修复时长承诺。每次只给 3–5 个步骤，遇阻塞即记录，不要求继续绕行所有页面。

### 第一轮：查看数据与理解结果

| 步骤 | 用户操作 | 预期与关注点 |
| --- | --- | --- |
| 1 | 查看总表与指定日期的明细，切换日期/经营或退货口径 | 范围和来源明确；与独立核对点相符；不把不同币种或目录版本的数字直接比较。 |
| 2 | 搜索一款熟悉的商品，打开款式和变体 | 编号、分类、实际变体容易理解；N:1 Seller SKU 展开后不增加虚假变体。 |
| 3 | 从一个商品查看来源，再返回筛选列表 | 能追溯报告和记录；长名称/标识不遮挡操作；返回保留上下文。 |
| 4 | 查看待处理项及已知重复案例 | 系统说明为什么待处理、为什么判重；同值副本与真正字段差异表达清楚。 |
| 5 | 按平时习惯完成一次跨页面查找，记录最费力的一处 | 入口符合日常工作；缺少数据/功能与 UI 不好用分开记录。 |

这一轮不修改主档或发布状态。环境准备中必要的导入/发布种子操作必须属于已确认的测试写入范围，记录由谁完成，不能当作用户体验通过。

### 第二轮：少量真实业务修改（仅隔离副本）

| 步骤 | 用户操作 | 预期与关注点 |
| --- | --- | --- |
| 1 | 为一款商品改名称或分类，保存草稿，查看差异并批准 | 保存与生效分清，新目录版本明确，其他商品保持不变。 |
| 2 | 处理一个别名/新变体候选，或忽略一条误报后恢复审核 | 不双重归属；操作原因与当前用户可解释；恢复后待办重新出现。 |
| 3 | 导入一份授权报告，确认日期、解析、生成草稿及重复决定 | 从上传到校验的路径清楚；冲突有业务解释，失败保留可恢复状态。 |
| 4 | 核对校验与预览，按授权批准测试目录/发布测试日报 | 权限、版本反馈和审计正确；试用库数字能按核对点解释。未做该操作就记未覆盖。 |
| 5 | 下载标准 XLSX，只修改一个允许字段，再上传校验/预览 | 旧/新模板边界清楚；修改范围准确。若本次授权包含批准，可完成测试版本往返，否则保留“止于预览”。 |

前三步按用户重点至少选择两个；未经覆盖的步骤明确列出。初次建档在 S0 做一次小样本正式导入/批准路径，日常修改在 S1 做；不要频繁销毁环境。没有已发布来源时先说明该前置，不以手写数据库记录代替初始化体验。

重复发布/草稿改期/重新解析/废弃仅选择真实业务需要的一条，不强制把全部危险操作串起来。测试库“发布日报”和“批准目录”均不代表生产发布，更不代表应用部署。Stage 5 的历史生效日、追溯重述、结账冻结尚未实现，不纳入本轮可用功能承诺。

## 6. 反馈记录与变更处理

### 6.1 一个清单即可

用户可以口头或直接留言，代理整理到同一反馈表，不要求逐项填写模板、不建立新审批系统。可定位到样本的现场证据放任务目录；仓库只保留脱敏摘要、优先级和状态。

分类限四种：使用阻塞/错误结果、交互体验、源数据问题、范围新增。数字不一致先核对来源、筛选、时区、币种、事实/目录版本，不未经诊断改数据或业务计算。重复反馈合并一个条目，保留样本差异。

### 6.2 修订规则

- **数据错误、越权、丢失、重复批准或版本冲突失效**：先停止受影响写入、保留现场并定位；其他独立只读路径可继续。这类问题未解决不能把对应功能记为通过。
- **已有功能的布局、文案、操作步骤问题**：同一使用路径集中修改，目标检查后一次复体验；不为每条小建议重跑所有组件或要求用户重复整套体验。
- **源数据缺失或脱敏破坏关联**：修正副本/范围及核对点后重试，不靠补猜产品属性或放宽校验让页面通过。更新样本哈希和派生关系。
- **新的业务语义**（例如改变批准范围、身份归属、计算口径、历史有效期）：先给出影响、建议和可审阅变更说明，用户明确选择后才修改相应规格；若属于 Stage 5，保留现状并登记到 Stage 5，不偷偷扩大本轮。
- 用户明确要求修复即为相关修复授权，不重复询问；本轮只编制计划。试用期间的代理诊断和代码调整只在用户发起执行/提出修复后开展，仍不自动提交、合并或部署。

计划安排一轮集中修订和一轮复体验。复体验仍失败时只继续未解决的受影响路径，报告剩余问题；不以轮次数为由强行关闭，也不自动无限增加新功能。新的非阻塞建议可与用户明确约定延后；未回复不等于接受延期或通过。
