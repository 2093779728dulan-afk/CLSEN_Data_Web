## 原方案正文（历史设计，不是当前执行入口）

本计划供用户审阅。批准计划不自动授权实施、访问真实数据或迁移；只有明确启动对应批次后才执行。执行者按项目 AGENTS.md 内联推进，不使用子代理、不自动提交。writing-plans 仅用于组织模块、业务依赖和检查范围，通用技能中的逐步红绿、提交和执行选择不适用。

**目标：** 让用户在不改写历史目录和原始发布事实的前提下，按明确生效日期提出商品归属修正，查看影响，遵守结账约束，批准、追溯和前向撤销修正。

**技术基础：** 沿用 FastAPI/Python、MySQL、React/TypeScript、现有目录审批、身份冲突、分析查询、审计和共享 UI。建议增加独立且不可变的修正记录及结账记录，复用已有目录版本，不把历史治理变成重写报表的导入工具。

## 2. 待用户决定的业务语义

以下是审阅选项，不是系统默认规则。没有决定时，仅可在明确授权后实现不依赖该决定的部分；受影响的批准与结果查询入口保持不可用并解释原因。

| 决定 | 可选语义与建议 | 影响/最晚决定点 |
|---|---|---|
| D1 修正范围 | 首版仅支持 Seller SKU 的错误归属、纳入/解除忽略；或同时追溯商品名称/分类。建议首版限定归属，名称/分类仍用原版本快照。 | A 的字段/影响预览；扩展属性修正需补对应差异与冻结规则。 |
| D2 生效范围与日界 | 指定起始日到开放区间；或允许显式起止区间。建议按站点报告时区的业务日期、起日包含止日不包含，禁止隐式默认“从最早数据起”。是否允许未来生效也需确认。 | A 的日期验证及区间冲突；页面把不包含的止日转为清晰业务说明。 |
| D3 事实归属日期 | 经营报告按报告日；退货按事件日、报告日，或随所选查询口径。建议修正适用日期规则独立固定并留存，不能因为用户切换图表口径而悄悄改变治理决定。退货事件日缺失时选择阻断、单列未决或明确回退报告日。 | A/B/C；示例先展示不同选择的影响，不擅自回退。 |
| D4 三种口径与日常默认 | 保持日常“当前事实”不叠加追溯修正，另选“修正后结果”；或允许修正成为日常默认。修正后的事实基线选固定发布集合还是最新发布事实。建议独立模式+明确基线，先不改当前默认。 | A 锁定预览输入，C 落查询合同；最新基线必须标明随新发布变化。 |
| D5 结账边界 | 按站点+账号/来源范围结账，月度或任意日期段；冻结全部期间还是仅选定产品。建议站点+来源范围月度整期冻结，避免产品间移转绕过结账。 | B；范围、时区、退货跨期归属须与D3一致。 |
| D6 已结账后如何修正 | 严禁当期变更、下期开调整记录；或管理员明确重开再审批重述。是否允许只读模拟冻结期修正？建议可模拟但不生效，禁止自动解冻。两种正式处理方式必须选定。 | B/D；“下期调整”不是伪造销量/金额，若需会计分录则另立范围。 |
| D7 分工与批准 | data_manager提案、admin批准；是否禁止申请人自批？谁能冻结、重开、撤销？viewer可否查看未批准模拟及敏感来源？建议提案与批准分离，治理操作限admin，viewer只读已批准结果。 | B 权限矩阵；现有完整管理员体验不等于批准其可自批新历史修正。 |
| D8 重叠、撤销与后续修正 | 同一来源区间重叠拒绝并要求显式替代，或提供拆段合并预览。撤销恢复原归属还是仅取消被选修正？建议拒绝隐式最后写入覆盖，撤销走补偿版本，受后续修正影响则重新预览。 | A 区间检查、D 前向撤销；不得全目录回滚覆盖其他人的新改动。 |

审阅回复可按 D1–D8 逐项指定。全部“建议”在确认前保持建议；计划审阅中若改变语义，应先更新本表和对应样例，再冻结批次范围。

## 3. 三种查询口径（拟议合同）

当前只确认已有 `fact_basis=current/catalog_snapshot` 合同存在；下表的历史治理模式是新增设计。不得给旧参数换含义，也不能允许现有接口已拒绝的“旧目录+current”组合而不显式升级合同。

| 用户看到的口径 | 固定/解析内容 | 应回答的问题 | 禁止的混用 |
|---|---|---|---|
| 当前事实 | 沿用当前接口的有效发布事实与当前批准目录；每次响应固定读取基线 | 现在发布的数据按现行目录怎样归属？ | 不自动附加追溯修正，不冒充当时账面结果。 |
| 历史目录快照 | 指定目录版本及它记录的事实成员/覆盖范围，使用原快照字段 | 该历史目录版本保存的结果是什么？ | 不把最新报告偷偷放入旧快照；缺覆盖/成员时明确不可重现，不显示假零。 |
| 修正后结果 | 显式基础目录/事实集合，加指定已批准治理版本，按D2/D3逐行解析 | 同一批事实按指定修正规则重算后怎样变化？ | 未批准模拟不可与已批准结果共用标签；冻结期不得绕过D6。 |

拟新增业务查询参数 `history_view`（`current`、`catalog_snapshot`、`corrected`）及 `governance_version_id`；实际命名在C落实并同步生成客户端。历史快照要求目录ID；修正模式要求治理版本及明确事实策略；不允许未知参数静默退回current。保留旧客户端不传新参数时的原行为。

每次响应返回：站点/来源范围、显示日期范围、退货口径、治理适用日期规则、目录ID/修订、不可变事实集合ID或成员摘要、治理版本、结账修订、读取时间、覆盖/未决状态。表格、汇总、趋势、分页、下载/返回链接共用同一基线；翻页基线变化要求刷新，缓存键包含全部模式及基线。

**虚构对照样例：** 同一SYN-A有1日2件、3日1件原归商品甲，提案从3日起归商品乙。未冻结且D1–D4同意该语义后，同一固定事实集修正后甲2/乙1、合计3；原快照仍甲3/乙0。事件日2日、报告日4日的退货另列，用D3决定适用侧；无事件日不能自行推断。新发布一份报告后，固定基线结果保持原值，最新基线模式须显示新基线差异并重新预览。

建议记录最小字段：提案ID/站点/来源范围、稳定来源身份、原目标/新目标或忽略决定、生效区间、原因、依据引用、创建人时间、业务日期规则版本、基础目录/事实引用、提案revision。不得只用SKU前缀定位，不跨账号合并同名SKU。

### 写入协议与结账竞争

提案为 `draft → previewed → submitted → approved`；拒绝/撤回是保留记录的终态。编辑使旧预览失效。批准后不允许编辑；撤销另建补偿提案，不把approved改回draft。状态名为拟议，应映射现有公共风格，避免并行审批系统。

每次写入携带operation_token/idempotency key及expected_revision；同键同载荷重放返回原回执，不同载荷冲突。批准在单事务重新校验权限、冻结状态、提案revision、预览时效、目录/事实/治理基线和来源预占；任一变化返回可理解的冲突并要求新预览，不能后台自动合并。

冻结与批准按同一站点/来源范围采用一致锁顺序，锁期间治理修订后再校验。并发冻结先提交则批准拒绝；批准先提交则冻结基线必须包含新治理版本。冻结记录保留期间、事实集合、目录/治理基线、操作者、原因及修订。失败全回滚；结果未知按operation token查回执，不盲目重复创建版本。

所有可影响已结账结果的入口都需要约束：历史修正、补偿、原目录批准对current的影响、日报更正/重发、未来生效修正跨入冻结期。不能仅禁用治理页面按钮。冻结的“账面结果”固定快照；current是否还能显示后续原始发布变化由D4/D6决定，页面须区分，不悄悄改已结账结果。

## 5. 四个可独立交付业务批次

依赖顺序A→B→C→D；A只提供模拟，B提供可审计治理和固定结果明细，C再接入经营分析，D支持有审批的前向撤销。所有批次当前均 `not_started / awaiting_plan_review`。

| 批次 | 交付业务路径 | 依赖/决定 | 目标退出（未来） |
|---|---|---|---|
| A 生效日与影响预览 | 商品卡→提案→指定生效范围→看影响，不生效 | 明确启动A，D1–D4/D8 | development_complete / ready_for_user_review，批准按钮不开放 |
| B 审批与结账冻结 | 预览→提交/批准→治理版本→冻结保护 | A，D5–D7 | 同上；治理版本可追溯，结账竞争目标验证通过 |
| C 三口径查询 | 产品总表/详情切口径→核对差异→返回筛选 | B，D4最终确认 | 同上；旧查询不变、新模式可解释 |
| D 前向撤销与治理闭环 | 选修正→补偿预览→批准→核对旧版本未变 | B/C，D6/D8 | 同上；不执行数据库回滚，不声称发布验收完成 |

### A：生效日与影响预览

**目标/模块：** 以`history_models/service/repository/preview`和商品卡入口完成一条可保存、可审阅的提案路径，先不提供正式历史生效。新增持久化结构随此批落地于可抛弃库；预览和后续查询共用解析器合同。

**输入/输出：** 输入来源身份、原/新归属、日期规则和范围、固定基线；输出提案ID/revision与预览ID/摘要、分日期/商品/币种差额和阻断原因，供B批准使用。

- [ ] 确认D1–D4/D8，画出上述虚构例在起止边界及跨期退货的期望结果；无决定不写默认历史规则。
- [ ] 提案保存校验稳定身份、目标存在、来源范围、区间合法及重叠；未改变目标、零影响、缺事件日分别显示原因。
- [ ] 提供影响预览，覆盖mapped/unmatched/excluded转移，按固定事实集计算，展示未决来源和不支持的历史范围。
- [ ] 在商品卡接入提案/预览，保存与模拟清楚分开，返回时保留原筛选，业务失败保留输入。

**数据边界：** 独立虚构库中甲/乙两个商品及至少两个来源账号；不使用1202真实行，也不批量导出真实目录。不修改已批准目录和日报。

**定向验证：** 优先复用目录冲突、快照测试模式，新增`backend/tests/unit/catalog/test_history_preview.py`仅覆盖起日/止日前后、重叠、跨站点同名SKU、缺失日期、币种隔离和守恒；新增`frontend/src/features/catalog/CatalogHistoryPage.test.tsx`验证编辑导致预览失效及无生效按钮。必要单MySQL用`test_catalog_history_workflow.py`验证提案幂等和revision；这些新增文件名是计划，不是现有通过证据。

**用户体验：** 1.打开虚构商品甲并选一个来源；2.选择生效日和乙；3.看日期边界两侧及总量差异；4.保存退出再打开，原经营页结果仍未变化。

**退出：** 定向检查通过且独立入口就绪后`development_complete / ready_for_user_review`；用户确认才记本批`user_verified`。D项未决或预览不可解释时不进入B。

### B：审批、权限、审计及结账冻结

**目标/模块：** 在A的提案页接入`catalog_history`API、`history_repository`批准事务、`period_close`、现有权限/审计与相关写入口冻结校验，交付可查看的治理版本及固定基线明细，不依赖C的整套分析页面。

**输入/输出：** 输入A预览ID/摘要和全部expected revision；输出治理版本ID、基线/影响摘要、审计回执或明确冲突。冻结/重开命令独立有理由与revision，供C/D读取。

- [ ] 按D7落实权限矩阵：查看、提案编辑、模拟、提交、批准、冻结、重开、补偿各自校验；所有写入口会话/CSRF，服务端重新检查角色撤销。
- [ ] 按D5/D6落实结账状态及对日报/目录/治理入口的保护；冻结期模拟可用性按决定展示，但不得用模拟接口生效。
- [ ] 批准重新验证基线、预占、冻结与摘要，在同事务追加治理版本和审计；重放不产生第二版本，审计失败不能无审计生效。
- [ ] 提供版本明细：申请/批准人、理由、业务生效日和记录批准时刻分别显示；审计来源展示沿用安全引用和脱敏，不存密码或整份原件。

**数据边界：** A独立库，至少未结账与已结账两个虚构期间。跨账号/权限拒绝用无效目标和预置小样例，验证后核对无新增版本；不连接现有真实副本。

**定向验证：** `backend/tests/integration/test_catalog_history_workflow.py`目标节点涵盖自批规则、预览过期、目录/报告变更、同键不同载荷、两人批准、冻结与批准竞争、审计原子性和跨站点拒绝；复用`test_catalog_projection_expiry.py`、`test_catalog_concurrency.py`、`test_product_catalog_permissions.py`中受影响节点。单MySQL显式目标即可，不双版本全矩阵。前端仅权限按钮/冲突提示与结果刷新目标组件。

**用户体验：** 1.数据管理账号提交模拟提案；2.审批账号查看差异并批准；3.查看治理版本和审计；4.冻结该期后再次尝试覆盖，预期被明确拦截；5.按已选D6演示重开或维持阻断，无默认解冻。

**退出：** 定向权限/原子性/竞争目标通过且交付入口就绪；拒绝路径无副作用有证据。用户确认限本样例，正式冻结期真实写入仍需单独范围授权。

### C：三口径查询与经营结果解释

**目标/模块：** `history_resolution`接入`analytics/style_*`和`api/style_analytics.py`，前端总表/详情与来源/返回链接使用统一模式；旧`current/catalog_snapshot`行为不变。

**输入/输出：** 输入B治理版本、D4事实策略和合法范围；输出三口径值与完整provenance。不支持的组合返回明确错误，不把旧目录证据不足转成空表成功。

- [ ] 三种模式采用同一归属解析和固定基线，处理纳入/忽略、退货日期及零/缺失/部分覆盖。
- [ ] 锁定分页分母、趋势与表格的基线，更新客户端、URL、缓存与下载元数据；只有实际支持该口径的下载才开放，不默默导出current。
- [ ] 总表/详情展示口径、治理版本与冻结状态，差异解释可回到提案；切换无过时响应，返回列表保留日期/搜索/排序/口径。
- [ ] 使用虚构Storybook场景表示当前、历史、修正及证据不足；需要新UI确认时只复体验受影响路径。

**数据边界：** A/B同一虚构事实集合；另加一份新发布版本验证固定与最新模式的区别。不用新功能声称重现V35历史金额。

**定向验证：** 新增`backend/tests/unit/catalog/test_history_resolution.py`与`backend/tests/integration/test_catalog_history_queries.py`，复用`test_style_analytics_consistency.py`和`test_style_analytics_reconciliation.py`受影响节点；同基线总量守恒、日期边界、缺快照拒绝、不同币种、权限与缓存隔离。前端仅产品列表/详情及口径选择器目标测试，验证翻页分母和返回URL。

**用户体验：** 1.同一日期看当前事实；2.切到旧目录快照；3.切到批准修正后结果，甲/乙分配与A预览一致；4.打开详情再返回，口径和筛选不丢；5.打开一个缺历史覆盖范围，看到“无法重现”而非零。

**退出：** 三模式的来源和差异可解释、旧客户端兼容目标检查通过，交付`ready_for_user_review`；确认后仅升级C体验，不宣称所有页面都支持新增口径。

### D：前向撤销、后续冲突与历史不变

**目标/模块：** 在B治理版本页提供补偿提案，复用A预览/B审批/C查询；不增加物理删除或覆盖旧版本的“回滚”。

**输入/输出：** 输入被撤销治理版本及当前基线；输出新的补偿治理版本、被撤销引用、范围差异和审计链。撤销理由和批准权限不弱于原操作。

- [ ] 检查被选修正后的其他修正/目录/结账变化，仅补偿被批准范围；有依赖则阻断并说明需重新预览/显式替代。
- [ ] 按D6处理已冻结期，不允许撤销入口绕过冻结；未批准提案可以撤回但保留记录。
- [ ] 补偿批准的幂等与未知结果查询复用B；生成新版本，旧事实/目录/治理记录不改。
- [ ] 以本轮虚构样例在首次批准前保存规范化全量mapping/exclusion及事实成员摘要，批准与补偿后比较；这是新证据，不倒推V35。

**数据边界：** 独立虚构范围内加入第三个不相关商品，证明补偿不会覆盖他人变更；不执行数据库恢复、数据删除或真实账期重开。

**定向验证：** `backend/tests/integration/test_catalog_history_reversal.py`覆盖重复撤销、后续修正冲突、跨冻结期、原记录摘要不变和无关商品保留；与B共用原子性/幂等节点，不重复无关检查。前端治理页补偿预览/失败提示/刷新目标测试。

**用户体验：** 1.选一条已批准修正申请撤销；2.核对只影响该来源区间；3.批准生成新治理版本；4.三口径查看补偿结果，并打开原修正/旧目录；5.尝试撤销有后续依赖或已冻结记录，核对明确阻断。

**退出：** 补偿闭环和旧记录不变目标证据齐全，用户确认D后汇总Stage5.1各批状态；仍不自动标记accepted、进入5.2或部署。

## 6. 验证与交付纪律

- 本轮只做文档diff/格式和链接检查，不执行下列未来测试。
