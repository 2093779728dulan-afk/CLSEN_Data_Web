# 商品身份与业务关联约定 v1.1

生效日期：2026-09-17。性质：用户要求的项目开发约束；约定已建立，不表示历史数据已清理或未来模块已实现。

v1.1审查补强：测试身份切换、过账时重新校验、手工输入幂等、跨语言一致性及权限范围；这些是未来实现要求，不代表已有代码全部具备。

适用商品主档、导入导出、生产、库存、物流、销售退货、分析及未来Java/Python接口。纯文案或不涉及身份/关联的任务可注明“不适用”，无需全量盘点。当前执行状态仍以[计划索引](project-plan-index.md)为准。

## 1. 身份的唯一含义

| 对象 | 规则 |
| --- | --- |
| 款式 | 使用现有稳定style_id；款式编号是可展示、受控修订的业务编码，不充当跨模块唯一主键 |
| 变体 | 使用现有稳定sku_id，关联款式和确认的颜色/尺码；关联时携带所属site/租户范围，不假定裸ID在所有环境中全局唯一 |
| 外部标识 | Seller SKU、工厂编码、旧款号、FNSKU、ASIN分别定义；按来源和适用账号/站点限定，不能把ASIN当唯一库存身份 |
| 分类 | 独立属性，不改变稳定SKU；不得用分类、名称或图片相似度自动合并商品 |
| 工厂/仓库 | 组织与仓库分别编号；花都/广州为用户确认的同一工厂别名，其他相似名称不能据此自动合并 |
| 单据与事实 | 订单、单据行、收货批次、出库行、箱、货件、接收事件各有独立ID；SKU只能标识商品，不能代替业务事件ID |

现有Python商品主档在明确迁移前保持唯一写入权威。Java或其他新模块使用接口/版本投影引用，不直接改主档表，不另建可独立编辑的竞争性主档。未来迁移必须明确切换时间、唯一写入方和历史引用兼容。

当前代码参考：业务开发工作树`stage4-1-app-shell`的`catalog/approval.py`、`scope_service.py`、`identity_conflicts.py`、`normalization.py`。现有P0范围仍限定amazon_us；多平台、多仓规划不能冒充已实现能力。每次涉及这些规则的开发须核对当次实际版本，不把本段当实时部署证明。

导入/导出的长期来源分流、字段、原件追溯、中文问题、模板及回导规则同时遵守[导入导出数据约定](import-export-data-contract.md)。人工表格整理不改变本合同的稳定身份、映射权威、scope和过账校验；平台官方原始报告继续按原来源规则处理。

## 2. 外部编码解析与映射

- 原文、来源范围、规范化结果和算法版本分别保留。引用现有公共规范化实现，禁止各新模块自行trim/lower后关联。
- 当前`seller_sku_match_v1`不做casefold，而`catalog_identity_key_v1`做casefold；两者不能互换。大小写、Unicode、空白处理的更改必须评估历史键兼容和冲突，不能用“清洗”名义静默改身份。
- 同一外部键在同一适用范围和有效目录版本内不能同时归属两个SKU，映射与忽略决定不能同时生效；不同范围不凭相同文字自动合并。
- 映射保留确认人、原因、证据、版本及适用范围。未映射、冲突、已批准忽略分别表达；分析显示未归属影响，不能静默丢弃。
- 不根据命名习惯自动修正`12218`为`2218`，也不按颜色同义词直接合并；候选建议经过现有确认流程才生效。
- 过账业务单据保留确认时的SKU和必要版本；若分析采用最新目录重算，应明确展示口径，不得伪装成原始历史事实。重归属通过显式更正处理。

## 3. 业务关联与数量

单据行保存上游引用、SKU、组织/仓库/账号范围、数量、状态和证据。支持分批、多对多分配；不能只按SKU和日期做JOIN，造成一对多重复汇总。

- 入库、出库、装箱、实收的分配量应守恒；跨SKU分配禁止，替代商品需明确单据处理。
- 外部事件ID/业务键与作用范围用于幂等，文件hash只解决完全重复文件，不能替代事件去重。累计报告先按版本核对差额，快照不累加。
- 草稿、确认、过账分开；已过账不能覆盖或硬删除，冲销须检查下游依赖。版本冲突拒绝覆盖，重试不能重复入账。
- 预留不等于出库；销售日报不等于实物出库；退款不等于退回可售；未收数量不自动认定损失。
- 无法识别的库存进入独立待识别记录，不伪造可售SKU。平台资料未提供批次关系时不得声称已精确追溯到生产批次。

## 4. 新功能必须进行的轻量核对

### 过账前不可遗漏的控制

- 只读投影可能过期。确认过账时由服务端重新校验SKU存在性、所属范围、当前允许状态和适用映射版本；被停用、归属变化或版本冲突时返回明确待处理结果。不得只依赖页面打开时的校验；主档不可用时可保存草稿，不能凭过期副本默认允许正式过账。权威读取或有有效性保证的版本契约由实现选择。
- 手工代录也需要幂等：一次逻辑提交使用稳定操作ID，相同ID/相同内容返回原结果，相同ID/不同内容拒绝。断网后先查原提交结果，不能换ID盲目重试；同一SKU同一天的两次真实收货必须能够并存，不能粗暴按日期/SKU去重。
- 单据、行、仓库、SKU的归属及操作权限必须服务端逐项检查；不能信任请求里的site/账号，不能凭知道ID访问其他范围。引用的上游状态和可分配余量与写入在适当事务/锁控制下复核，避免校验后被并发改变。
- Java适配不得按默认字符串处理重写Python规范化。首批对大小写、Unicode、空白、前导零和跨范围相同代码使用少量固定契约样例；稳定ID经JSON跨语言传递时约定无精度损失的表示（必要时字符串），不能未经评估更改旧API。
- 数量守恒指同一事件/分配口径的守恒，不要求下单、累计入库、出库和实收始终相等。部分完成、待检和在途差异是合法状态，不得为了校验通过强制补齐。

### 测试数据转正式的边界

DEMO ID、演示订单和试用库存不得直接混入正式账。授权接入时列出样本身份到正式身份的核对清单、期初截止点和未结单据处理；默认仅迁移确认需要的主数据引用和已批准期初，不复制试用流水。确需保留的真实试用单据必须逐项核对来源、幂等键和已计入期初的数量，防止期初与流水双计。不能把测试环境的数字ID直接当成正式ID。

### 任务记录

开工时只核对受影响范围，在现有任务记录中填写下列信息，不另建审批系统或重复台账：

1. **身份**：使用哪个稳定ID、范围和映射版本？是否误用显示编号？
2. **关联**：上下游引用及一对多/多对多关系是什么？是否可能重复汇总或丢失未匹配项？
3. **责任**：哪个模块唯一写入？其他模块如何只读引用？
4. **兼容**：是否改变旧接口、规范化、目录版本或历史解释？涉及哪些现有路径？
5. **处理**：异常如何隔离、确认、更正和追溯？重复提交、并发冲突如何处理？
6. **接入**：当前仅独立体验、只读关联还是业务写入？授权范围和退出办法是什么？

建议记录格式：`范围/版本｜身份及来源｜上游与粒度｜写入责任｜核对结果及处理｜定向验证｜关联状态`。结果为通过、待处理或不适用；未实现的控制只能写计划，不能写已通过。

交付前对照实现复核一次。优先复用受影响测试；仅针对实质风险补充范围隔离、重复提交、分批数量、版本冲突或历史兼容检查。无关模块不跑全量测试，正式验收按原发布规则执行。

## 5. 不符合约定时的处理

| 发现问题 | 必须采取的措施 | 可继续范围 |
| --- | --- | --- |
| 缺失/不明确映射 | 保留原始证据，列为待处理，不写正式关联或库存 | 不依赖该身份的页面、虚构样例开发 |
| 一个键多个归属、跨账号误连 | 阻止受影响批准/过账，定位范围与既有决定，人工确认 | 独立无冲突记录；不得静默覆盖已有映射 |
| 旧接口或规范化不兼容 | 明确版本兼容策略，准备最小适配和定向验证 | 隔离环境内实现，不切换现有消费者 |
| 重复入账、数量不守恒、并发超分配 | 阻止相关过账，保留证据，定向修复并核对影响 | 无关功能；不通过修改真实库存掩盖问题 |
| 历史数据需要更正 | 提出范围、预览差异、审计及冲销/迁移方案 | 可准备方案；未授权不改业务数据 |
| 接入会扩大旧功能影响 | 缩小接入范围，优先只读，保留旧路径和关闭办法 | 独立体验；等待用户明确关联指令 |

用户已给定的授权不反复询问；缺失的业务身份决定或扩大的数据写入范围须说明具体缺口。未知项只阻塞依赖它的部分，不默认停止整个项目。

## 6. 独立体验与渐进关联

默认独立工作树、任务数据库和虚构样例；真实样本副本需明确授权，保留原稳定ID和来源版本，不产生新主档权威。不得因核对本约定就访问data/或真实数据库。

开发完成、用户体验通过、允许关联、正式发布分别记录。用户确认稳定不自动授权关联，上一批接入不自动授权下一批。接入前明确范围、版本、读写权限、受影响路径与退出方案；写入控制必须在服务端实现，不能只靠隐藏菜单。关闭模块保留已发生事实，不用删除数据实现回退。

当前已知待核项沿用[供应链计划](../superpowers/plans/2026-09-17-production-inventory-fba-evolution-plan.md)第2、8节，不重复建单。该约定不重开旧阶段、全量映射盘点或正式Collect。
